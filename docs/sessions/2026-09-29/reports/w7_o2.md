## Levers found (idiom candidates)

- **An enum-typed local stops the compiler from reusing a global load (dwc_gdb.o).** The object
  loads `s_tbl.process` in the entry block for the success switch, but both error paths reload
  `s_tbl.process` after the state test. With `int process = s_tbl.process;` at the top, the
  compiler reuses that entry load in the error paths (166 bytes differ). Moving the read into the
  success block gets the right size but schedules it too late. The fix: the field and the local
  are both enum typed, as DWARF says (`enum @enum process`). `DWCGdbProcess process =
  s_tbl.process;` then matches, and the `s_tbl.process` reads in the error paths stay separate
  loads. A `((Tbl *)&s_tbl)->process` cast also matches; `(&s_tbl)->process`, a `Tbl *` local
  and an `(int)` value cast do not.
- **SAKE request callbacks take six arguments (dwc_gdb.o).** DWARF lists only result, outputData
  and userData. The object reads result from r2 and the last two from `[sp,#0x20]` and
  `[sp,#0x24]`, so the prototype is `(sake, request, result, inputData, outputData, userData)`.
- **Chained assignment gives store, reload, store (jpegdec.o).** A DC-only IDCT column or row
  written as `a[0] = a[8] = ... = a[56] = expr;` stores the last element first, reloads it with
  `ldrsh` and stores the rest in reverse order, exactly as the object does.
- **IDCT workspace indexed directly, no row pointer (jpegdec.o).** In pass 2, a
  `short *ws = &mtx[2][i*8]` local hoists `&mtx[2]` out of the loop. Writing
  `mtx[2][i*8 + k]` gives the object's per-iteration `ldr mtx; add (i*8)<<1; add #0x100`. The
  `limtbl` local must be initialised at its declaration (DWARF r11 is loaded in the entry
  block). That also pushes `i` onto the stack (DWARF `[fb+0]`).
- **Operand order of one add (jpegdec.o).** Both passes need `tmp4 = tmp5 + tmp10`. The IJG
  order `tmp10 + tmp5` swaps the `add` operands.
- **Local order sets the stack slots, and initialiser order sets the store order
  (gpibuddy.o).** `decodedLen`, `numKeys`, `i`, `index`, `checkKey` declared in that order put
  decodedLen at sp+0x2c and checkKey at sp+0x24, and give numKeys/i the object's r8/sb. The
  initialisers are then written `decodedLen = 0; index = 0; checkKey = 0;`.
- **Tail merge needs an if/else, not an early return (gpibuddy.o).** The `numKeys == 0` path
  jumps into the shared `gpiAddCallback`/`gpiPeerRemoveOp` tail of the keys path. That happens
  only when it is written `if (numKeys == 0) {...} else {...}` with one `return 0` at the end.
  A `return 0` inside the first branch makes a separate epilogue and costs 36 bytes.
- **Struct fields assigned in the object's order.** The GPGetBuddyStatusInfoKeysArg fields
  (`profile, keys, values, numKeys`) are assigned `keys, numKeys, values, profile` in the empty
  paths, and `numKeys, keys, values, profile` in the filled path (which gives the `stmib` pair).
- gpiSendLogin matched on the first compile, in the plain GameSpy shape (a partnerBuffer
  sprintf, a user chosen from authtoken, then uniquenick, then nick@email, and an MD5
  response).
