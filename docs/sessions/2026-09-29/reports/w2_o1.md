## Near misses

- 0x0217DE94 gsLargeIntSquareMod: 6 instructions, prologue scheduling only. The
  image stores squareLen = 0 after the mod/dest spills and the carry/oldShiftBit
  moves; ours stores it straight after `mov r6,#0`. Everything from the
  TimerEnter call on is identical. Tried all 24 statement orders of the four
  initialisations, decl-init versus statement, chained assignments, volatile,
  other dsi builds (header notes list them).
- 0x0217E504 gsiLargeIntMultM: 59 instructions. The prologue, the epilogue and
  most of the loop body match. The remaining difference is register colouring in
  the Montgomery inner loop. The image uses tiptr r7, carry sl, mi sb and
  zero-hi r8, and keeps the post-loop carry in sl/r3. Ours uses r8, r7, sl and
  sb, and copies the carry to r1. There is also a 3-instruction Sub argument
  schedule.

## Shape notes (new idioms)

- Inline zeroing of a local array in the middle of a function, as an `stm`
  r0-r3 loop with no memset call, is `__builtin__clear(arr, sizeof(arr))`.
  None of our dsi or 2.0 builds inline memset, so memset always compiles to a
  call. The vendor object for gsiLargeIntMultM shows this pattern. It is likely
  the same thing behind the gsiLargeIntDiv pending note ("the object inlines the
  zeros"). The wave is worth an idiom page.
- When a local is zeroed after a call (`= {0}` stm loop after the bl), declare it
  as C99 `= {0}` in an inner block after the call (SubDivide, SquareMod).
- gsiLargeIntSubDivide reads quotient from the 6th argument slot
  ([sp,#0x24c]), although DWARF lists 5 parameters. An unused int parameter
  before quotient reproduces it. The caller (gsiLargeIntDiv pending draft) also
  passes 6 arguments.
- SubDivide's clamp only matched in the order `mData[0]=lo; mData[1]=hi;
  if (mData[1]) { mData[0]=0xFFFFFFFF; mData[1]=0; } mLength=1;`. A brute force
  over statement permutations found it.
- gsiLargeIntMult: store `*lenout = temp.mLength` before the memcpy and
  write the strip loop inline. A call to the static gsiLargeIntStripLeadingZeroes
  is not inlined by 1.1p1.
- The gslargeint.o `.comment` stamp is 4.0.0.1025, and no local build writes it.
  1.1p1 still matches every row tried so far.
