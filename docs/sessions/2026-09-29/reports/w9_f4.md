# w9_f4: tools/provenance.py

## What was added

- `tools/provenance.py`: read-only provenance report for the built ROM. `--json`, `--per-overlay`, `--verify`, `--assets`, `--cache-only`, `-j`.
- One paragraph in `docs/MATCHING.md` (under "What is spliced today", after the csrc/build command block). No figures.
- Nothing under `src/*/ov/` or `sdk/` was touched or read. No git commands were run.

## Method

Inputs: `extract/manifest.json`, `layout/layout.json`, `asm/` listings, `layout/matched/` shards, `build/pack/` (the recompressed ARM9 and overlay containers), `build/pokeblack.nds` (only for `--verify`). Sizes and counts only; no game bytes are printed or stored.

1. Region set: `build.region_specs` (twl excluded, it is never packed). Each ARM9 region and overlay is reassembled from its listing, so its bytes are classified from the listing.
2. Listing classification: a location-counter walk (`.org`, annotated instructions, `.inst*`, `.word`, `.byte`, `.hword`, `.space`). An annotated instruction line is code, its width from the annotation; `.word/.byte` is data words. Bytes the listing does not cover would count as gap fill (0 today). Re-syncs against annotated addresses and unknown directives are reported (none today).
3. Compiled C: `csrc.select`, `csrc.compile_entry` and `csrc.resolve_overlaps`, attached to regions with the same owner rule as `build.attach_c_sources`. A spliced range overrides whatever the listing said there. Compiling all 16,686 entries takes about 9 minutes with 12 threads, so the extent (size) of each entry is cached per entry (hash of the manifest entry plus its source file) under `<tmp>/aletheia/provenance_splices.json`, outside the repo. A run after a normal edit recompiles only changed entries (seconds). A wholesale invalidation by mtime was tried first and dropped: other lanes edit `src/` continuously.
4. BLZ: the ARM9 image and the overlays are counted on the decompressed image (681,920 B and 3,256,320 B). Table A separately sums the stored (compressed) bytes to exactly the ROM size, so both views are visible. The ARM9 image tail after the last autoload payload (64 B, autoload info table) is copied from extract and counted with the copied binaries.
5. Everything else comes from the manifest: fs files, ARM7, ARM7i, ARM9i (the DSi block; build.py only verifies twl, the ROM carries arm9i copied), FNT, FAT, y9, residue as copied; header, header_ext, banner, digest tables as header/signature/banner; padding is ROM size minus placed content (stored sizes from `build/pack`), split into interior gaps/container slack and the tail after the used ROM size.
6. `--verify`: every manifest region and residue blob in the built ROM is compared with the file it was copied from (`build/pack` for ARM9/overlays, `extract/` otherwise). Today 497 of 497 identical, 0 differ (so no header CRC/FAT/y9 patching was needed in this build).

## Converter round trip (`--assets`)

Round-trip claims in `tools/assets/` and `docs/ASSETS.md` are per sub-file inside NARCs; there is no file-level encoder and no NARC container re-serializer. The tool therefore reuses `verify_all.verify_subfile` (LZ77/LZ11 re-encoded, format layer parse+encode byte-identical) and counts a filesystem file only if it is a NARC and every sub-file passes, nothing written to the repo (results cached under the temp dir).

- 111 of 247 files (31,769,476 of 198,008,820 bytes, 16.0%) are NARCs whose every sub-file round-trips byte-identically today.
- Over all 237 NARCs: 29,018 sub-files pass, 25,036 skipped (no recognised format or Huffman/RLE without an encoder), 0 fail; passing sub-files total 67,254,049 bytes.
- Limitation: NARC framing (headers, BTAF/BTNF, padding) is not re-checked, so this is "content round-trips", not "file rebuilds". A full run takes about 20 minutes on this machine, then cached.

## Caveats

- Percent "of ROM" for image categories uses decompressed bytes over the ROM file size; that is why Table B's total exceeds the ROM size. Table A is the exact partition.
- The C column includes SDK and runtime entries that are spliced (as the build does), not only game code.
- Reported code vs data words depends on the disassembler having classified literal pools and jump tables as data; a spliced range overrides that.
- Cold cache costs about 9 minutes of compiler time; use `--cache-only` for an instant (possibly stale) answer.
