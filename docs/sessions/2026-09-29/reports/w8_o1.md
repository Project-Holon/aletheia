## Near miss / blocker

- **ov016 0x021D486C DWCi_ARClInit: MATCH.** Every byte matches. The only open relocation is
  the ABS32 pool word for cbWrite (0x021D4B60), an 8-byte static in archive.o
  (`mov r0, #1; bx lr`). cbWrite has no symbols_sdk.json row, and nothing in ov016 references
  it outside this function, so no evidence class attests it. The layout also runs that
  extent on into the next function at 0x021D4B68 (it shows a 64-byte extent). A catalog row for
  cbWrite, or a witnessed function start at 0x021D4B60, would unblock the function. The
  string literals ("rom:/dwc/utility.bin", "%s:/") are checked against the image and resolve
  as templates. FS_ChangeDir resolves as a veneer.

## Levers

- **A memcmp from a header named string.h (CheckAccessPoint).** The object hoists
  `pOldList->NumberOfItems` and `SsidLength` out of the inner loop across memcmp calls. That
  happens only when memcmp comes from `../arm9_sdk/libc/memcmp/string.h`, not from a prototype
  in the .c file. With the local prototype, 418 bytes differ. With the header, only the stack
  slots differ.
- **Split live ranges of one variable decide the stack slots (CheckAccessPoint).** The DWARF
  gives `i` in r6. That is the stealth scan over the old list, which reuses `i`, not `j`.
  With `i` in that loop, the other ranges of `i` share the object's slot at sp+0xc. With
  `j` in that loop, the slots swap with the compiler's cached-count temp. flagNew and
  flagOld are function-scope.
- **Unsigned sizeof product blocks strength reduction (keywrap_encrypt).** With
  `dest + i * 8`, the compiler strength-reduces the offset into a second induction register,
  spills `i`, and grows the function by 20 bytes. `dest + i * sizeof(iv)` keeps `i` in r4
  and recomputes `i << 3` in each iteration, as the object does. `(i << 3)` and `&dest[i * 8]`
  do not help.
- **The OR chain evaluates its last term first.** The 64-bit byte swap matched only with
  its terms written low byte first (`(x & 0xff) << 56` first, `>> 56` last).
- **Store, then increment, as separate statements (CloseShutdownClientSC).**
  `validPid[validPidLen] = x; validPidLen++;` in both list-building blocks gives the object's
  coloring (senddataLen r6, validPidLen r7, i r8, bRet sb). The `a[n++] = x` form rotates the
  four registers and adds a `movne` copy. No declaration order changes the coloring: I tested
  all 24 permutations and all gave the same result.
- **Duplicate the shared tail (WCMi_BssDescCopy).** The object's `bne; b copy` chain comes
  from two copies of the copy block, one per branch (`if (id in set) {copy} else if (id == 0xdd)
  { if (match) {copy} }`). The compiler merges the two tails. A goto, a switch or one merged
  condition all give a different chain.
- **Late template initializers need an inner block (WCMi_BssDescCopy).** wpaTag and wmmTag
  are copied from their templates after the length store. This compiler rejects a
  declaration after a statement, so the two arrays open an inner block. The DWARF has them at
  function scope. The file notes this.
- **The TWL-branch zero extension.** `length += (u16)(ieLength & 0xffff)` in the deviceId==1
  arm reproduces the object's `lsl #16; add ..., lsr #16`. A plain `(u16)ieLength` folds
  both arms together, so the post-loop deviceId reload and the spill of `w` disappear.
- **Precompute before the test (moveFocus).** The object computes `clear + 4` unconditionally
  before `cmp dir, #1`. A second local `next = clear + 4;` reproduces that. The DWARF lists
  only move and clear.
- **Move the error tail with goto (DWCi_NdGetFileAsync).** The AddPostData failure block sits
  after the success path in the object (`beq` forward). A `goto error` to a block after the
  final return reproduces it.
