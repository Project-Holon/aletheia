## Levers found

- Named local holding a strlen result before an integer-cast add (DWC_GetCommonValueString).
  `pSrcBegin[strlen(key) + 1]` in every spelling gave `add r0, r5, r0`; the image has
  `add r0, r0, r5`. `len = strlen(key); if (sep == *(char *)(len + (int)pSrcBegin + 1))` fixes it.
- Success block first, failure tail last (DWC_GetFriendStatusSC): `if (ok) {...; return state;}
  zero outputs; return 0;` reproduces the out-of-line failure tail.
- Locals in reverse of the sdkobj variable listing fixed the register swap in
  DWCi_RefreshFriendListAll (index, pid_i, i, j) and the stack slot order of the three char
  arrays in DWCi_GPGetInfoCallback (second block's pseudo_name declared first, username last).
- Unused parameter in the middle: DWC_LoginAsync takes callback and param in r2/r3, so the C
  prototype is (ingamesn, int reserved, callback, param) although DWARF lists three parameters.
  `if (!ingamesn || ingamesn[0] == 0) len = 0; else {...}` yields the predicated `moveq r6, #0`
  before the `beq`; `len = 0` before an `if` does not.
- `volatile u8` member (DWCi_GPRecvBuddyMessageCallback): the image reloads `ldrb [r1,#0x364]`
  for each of the two compares; only a volatile member reproduces it. This is a modelling
  choice, not proof the original was volatile.
- Inlined MATH_Rand32 half: `u64 x = rand->x; x = rand->mul * x + rand->add; rand->x = x;`
  matches the ldm/umull/mla sequence exactly (other spellings differ in load order).
- ProcessMaploop / ProcessAdHocData: memcpy from string.h inlines the 2 and 4 byte copies, and
  the copy order matters (`memcpy(&ip, buf, 4)` before `memcpy(&port, &buf[4], 2)` matches the
  image's load order). A `u8 *dst = (u8 *)&msglen` pointer variable reproduces `add r5, sp, #0`
  and the absent `sub sp`. The 4-byte swap needs `(u32)` casts to get lsr instead of asr.
- DWCi_RemoteLogin: DWCi_Acc_SetPlayerId takes a u32; the argument is the high word of
  tick * 0x5D588B656C078965 + 0x269EC3 (inlined MATH_InitRand32 plus MATH_Rand32 with max 0),
  written `(u32)((OS_GetTick() * 0x5D588B656C078965ULL + 0x269EC3) >> 32)`.
- ServerListConnect: SOCSockAddrIn with an unassigned length byte, port stored as the
  pre-swapped constant 0xEE70 (28910), hostent address copied with
  `memcpy(&saddr.addr, hent->addrList[0], 4)`.

## Near miss: 0x021685CC DWCi_GetMathRand32 (DIFF, 108 B differ, 276 B)

The whole function is right except register allocation and one literal-pool word. The
MATH_Rand32 half matches exactly and the MATH_InitRand32 half matches in instructions. Image:
ctx pointer in r6, &seed in r4, max in r5, zero in r7; the x block store `ldm r4 / stm r0` uses
a fresh literal load (second pool word at +0x104; the first at +0x100 feeds r6 and the Rand
half's r1), while the mul/add stores use r6. Ours: ctx r4, &seed r5, max r6, a single pool
word, stm through r4. About 20 spellings tried: inline helpers versus open-coded, ctx local
pointer, seed declared in the block, `mac` pointer local, tick in a temp, operand order of the
seed expression, nested versus `&&` checks, direct field stores versus helper, mul * x versus
x * mul. None moves the allocation. Suggestion: the original probably stores x through a
different pointer expression than the mul/add stores (two distinct `&stRandContext32`
values); a next pass could try a struct-typed copy or a non-inlined helper boundary.
