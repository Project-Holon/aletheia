# w9_f5: typed data generator, stage 1 (registry, datagen, round trip)

Read-only with respect to src/, layout/matched and the build. New files: tools/datareg.py,
tools/datagen.py, layout/data_objects.json; .gitignore gains /build/data/ (build/ was already ignored).
Committed content is addresses, sizes, kinds, counts and names only. The generated C (which contains
the initialiser values) lives in build/data/ and is never committed.

## Registry: layout/data_objects.json

Extends the existing layout/data_objects.txt idea (starts only) into a sized, typed map. The .txt file is
untouched and still feeds match.py; datareg.py reads it only as one source of ARM9 object starts.

```
{ "regions": { "<region>": {
    "base": "0x...", "range": ["0xLO", "0xHI"],
    "objects": [ {"addr","size","kind","name", + per kind}, ... ],   one object per line
    "externs": [ {"addr","name","kind": "func"|"data"} ] } } }
```

Per kind: `string` (size only), `zero` (size), `raw` (size, byte array), `numeric` (elem u8/u16/u32 and
count), `pointer_table` (count, targets: list of hex addresses with 0 for null, thumb bit kept in the
value), `struct` (fields: runs [["u32"|"ptr", n], ...] in word order, targets: the ptr words in order).
Default name g_XXXXXXXX; names are the editable field (datareg.py keeps a non-default name across
regeneration, keyed by address). `externs` are targets outside the region's tail (func_XXXXXXXX from
the listing labels, g_XXXXXXXX for other labelled addresses); an overlay region also sees ARM9 func_ labels.

Generation (python tools/datareg.py): tail range = first data line after the last code line to the end
of the listing (ARM9 fixed to the scout range). Object boundaries: tail start, every listing label
inside the tail, layout/data_objects.txt starts (ARM9), every `.word` value in the listing that falls
in the tail; strings additionally split after each NUL-terminated run. Classification, first match wins:
all zero, string (scout rule), pointer table (every non-zero word is a named target, at least half of
the non-zero words), struct (at least 20% of words are named targets), raw (over 16 B with no stride found
by the scout column test), else numeric with element width chosen from value magnitudes and alignment.
A word counts as a pointer only if it names a registry object or extern (Thumb bit aware); anything
else stays numeric, so unresolvable pointers to other regions are emitted as integers.

## Generator and round trip

`python tools/datagen.py gen|check [--region R]`. gen writes build/data/<region>_data.c: C using
unsigned char/short/long arrays, `char[N]` string literals with octal escapes, `void *[N]` pointer
tables, one struct type per struct object (arrays per field run); pointers as
`(char *)&target + addend` (addend 1 = Thumb bit); extern declarations first, definitions in address order.
check compiles the file with match.compile_tu (mwccarm 1.1p1, -O4,p, c99), reads every object by symbol
from the ELF (.data; explicit zero arrays land in .bss and are treated as zeros), applies the ABS32
relocations by resolving the relocation symbol through the registry (name to address) plus addend, and
compares with the image bytes.

| region | kinds (objects) | byte-identical |
|---|---|---:|
| arm9 | string 560, numeric 311, pointer_table 51, struct 31, zero 36, raw 65 | 1,054 of 1,054 |
| ov203 | string 88, numeric 126, pointer_table 2, struct 157, zero 6 | 379 of 379 |

Every kind is 100% in both regions. Sanity: the ov203 object has 16,928 B of .data and 322 ABS32
relocations; a negative test that corrupts the expected byte of five objects reports exactly those
five as failures, so the comparison is live. Both files compile in under a second. No failures, so
there is no failure list.

## Limits (what this stage does not prove)

- The round trip proves typed C plus relocation resolution reproduces each object's bytes. It does not
  prove the section layout (order, padding, .rodata vs .data, string pooling) matches a linked build:
  objects are compared by symbol, not by placement. That is the integration risk from the scout.
- Boundaries are heuristic. ov203 shows 157 small "struct" objects (2,272 B), probably single words
  made pointer-like because a listing `.word` (often a literal pool word) equals an in-tail address,
  which forces a start there. Harmless for bytes, wrong for structure. ARM9 raw is 28,940 B in 65
  objects: the scout's high-entropy tables and the misflagged 8 KB block.
- Numeric element type is a magnitude guess (u8 count is high because small-valued word tables look
  like bytes); signedness and struct-vs-array are not recovered.
- Function externs are declared `extern char f[]` and referenced with an explicit +1 for Thumb; the
  real link must define the symbol at the even address, or datagen must emit the odd value differently.
- Zero objects are emitted as zero-initialised arrays and land in .bss; in the ROM image they are file
  bytes. Whether they belong to .data (explicit padding) or .bss is unknown.
- Cross-region pointers (overlay data to other overlays, ARM9 data to overlays) stay integers.
- ITCM and other autoloads, and .bss objects, are not covered.

## Plan to integrate into the build

1. Registry hardening (1 lane): stop forcing starts from literal pool words that point mid-table,
   merge single-word structs into neighbours, add `align` and `section` (data/rodata/bss) fields, extend
   to all regions by tail size (ov021, ov009, ov093, ...); hand-typed names and struct overrides keyed
   by address in the same file.
2. Symbol map: emit build/data/symbols.json (name to address, all regions) from the registry plus
   layout/symbols_sdk.json so any data reference, including cross-region ones, resolves.
3. Splice: compile build/data/<region>_data.c and place each object's bytes at its registry address in
   the region image, as csrc.Splice does for functions (never fall back: compile failure, size mismatch
   or unresolved relocation is a build error). Resolve ABS32 relocations through the symbol map with the
   Thumb rule above. Placement by address needs no linker script or section model for the first
   integration; the placement question stays open until code and data are linked together.
4. Verification: extend `manifest --verify` with per-object rows (EXACT = compiled bytes equal the
   image), shards keyed by region, so coverage can count data objects. This moves the coverage figures:
   flag the denominator (tail data plus .bss, no pools) before switching it on.
5. build.py: a `--gen-data` step running datagen before the region build, off by default until the ARM9 and
   ov203 files are byte-identical inside the full ROM build, then default on. The listing stays the byte
   source for everything not in the registry.
6. Matched C: emit a header per region from the same registry so consumer code and data share one type per
   object, replacing the ad-hoc per-file `extern` declarations (3,228 symbols).
