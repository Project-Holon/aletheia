## Key findings
1. **Part 1 of this cluster is NitroSystem G3D texture and palette binding.** func_0206E62C is NNS_G3dGetResDataByName(dict, name). The old residues were not register ties the allocator was free to pick. They came from how the old sources were declared: raw offsets and volatile hacks instead of the real resource structs and static inlines. Rewritten with NitroSystem-shaped types and inlines, each function closed in one to three compiles:
   - **3CC:** `plttBase` and `vramOffset` are u16 locals. The key address comes from an inline `(key & 0xffff) << 3` followed by `>> 3`. 2.0 folds that pair into the odd `bic #0xe0000000`. GetMatDataByIdx is an inline with an `if (mat)` guard.
   - **2CC and 4AC:** GetMat(mdl) has to be an inline written as `if (mdl && mdl->ofsMat) return ...; return 0;`. The same guard written as a ternary is exactly the 9-byte r8/sb swap. This was found in an 8-spelling hand sweep, which took priority over the permuter because the permuter was already known to be flat on this residue.
   - **19C:** the NitroSystem shape was EXACT on the first compile.
2. **0x0206AB18:** the first natural source was 520/520 with 17 bytes out, a three-register rotation around the elimination-row counter.
   - The required permuter runs did not move it: `--explain`, hill (252 singles), and anneal (700 compiles; budget cut from 2000 to stay under 5 minutes on a shared, loaded machine).
   - About 20 hand spellings also did not move it.
   - A sweep of which variable plays each loop role (90 of 1728 assignments) found 10 EXACT. In every one, the elimination-row variable is the same variable as an earlier role. The filed source stores the pivot row in `j` and then reuses `j` as the elimination row.
   - Recorded as a new idiom: docs/idioms/reusing-a-loop-variable-across-phases-changes-the-allocation.md.
3. **Compiler:** the ../2.0/sp2 pin is confirmed for 0x0206AB18. Every 2.0 service pack gives the same 17 bytes. 1.1p1 and every 1.x build tried compile the wrong size (504 to 516 bytes).
