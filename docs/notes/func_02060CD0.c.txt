The size is right, the control flow is right, every call site and both stack
regions are in the right place.  Two deltas remain, four bytes each, in
opposite directions, which is why the total lands back on 352.

1.  The free-list search is one instruction long.  The original predicates the
    advance under the break's negation:

      cmp   r6, r0
      ldrne r6, [r6, #0xc]
      cmpne r6, #0
      bne   loop

    the compile emits a separate branch for the break instead:

      cmp r8, r0
      beq out
      ldr r8, [r8, #0xc]
      cmp r8, #0
      bne loop

    Four spellings were tried, all four giving the identical 205-byte diff:
    the guarded `while (fr != 0) { if (fr == end) break; fr = fr->next; }`
    above, the conjunction `while (fr != 0 && fr != end)`, the plain
    `for (fr = head; fr; fr = fr->next) if (fr == end) break;`, and the same
    loop with the break written as the `else` arm of the advance.

2.  The shrink arm is one instruction short.  The original re-reads the block
    size for the region's end even though it already holds it in r7:

      add r0, sb, r4        region.start = ptr + newSize
      str r0, [sp]
      ldr r1, [r8, #4]      <- the reload
      add r0, r8, #0x10
      add r0, r1, r0        region.end = blkSize + (block + 0x10)
      str r0, [sp, #4]

    The compile reaches for the cached r7 and drops the load, and it also
    swaps the two stores so that region.end is written first.  The two are one
    decision: a store into a local whose address escapes (the region is passed
    to func_02060B6C) kills a cached field load, so the reload only appears if
    the compiler is not free to move the end computation above the start
    store.  With the value already in a register it is free, and it moves.

    Tried, all still 205 or worse: the end expression as plain pointer
    arithmetic (`(u8 *)block + 0x10 + block->size`), the two assignments in
    the other source order (208), and splitting the block pointer and the
    cached size into separate declarations initialised after the fact (209).
