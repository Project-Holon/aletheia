func_02051838  0x02051838  72 bytes  ARM  pkt_02051838  verdict DIFF

Three-word vector rebuild through a doubly-indirect table:

  push {r4, lr}
  ldr lr, [r0, #0x20]        ; the table pointer, loaded ONCE
  ldr r4, [r1]               ; q[0]
  ldr r2, [lr]               ; the inner pointer, re-read per statement
  ldr r3, [r1, #4]           ; q[1]
  ldr ip, [r2, #4]
  ldr r2, [r1, #8]           ; q[2]
  add r1, r4, ip
  str r1, [r0, #0x28]
  ldr r1, [lr]               ; re-read ...
  ldr r1, [r1, #8]
  add r1, r3, r1
  str r1, [r0, #0x2c]
  ldr r1, [lr]               ; ... and again
  ldr r1, [r1, #0xc]
  add r1, r2, r1
  str r1, [r0, #0x30]

The pointer at p+0x20 is common-subexpression-eliminated (one `ldr lr`), but
its pointee is re-loaded after every store, because a store through p may alias
it - the mirror image of
docs/idioms/const-pointer-lets-a-field-load-survive-a-store.md.

What the source has to be: `*(u32 *)(*(u32 *)((u32)*(u32 **)(p + 0x20)) + k)`
spelled per statement.  Spellings tried and the byte count each gave:

  u32 *t = *(u32 **)(p + 0x20); sum over t[1..3]          60 bytes, no frame
  *(u32 *)(p + 0x28) = q[0] + *(u32 *)(*(u32 *)(p + 0x20) + 4)   56 bytes (the
      inner +4 folds into one load with displacement)
  u32 **t = (u32 **)(p + 0x20); ... *(u32 *)(*t + 4)     56 bytes
  ... *(u32 *)((u32)*t + 4)                              56 bytes
  ... *(u32 *)((u32)**t + 4)                             68 bytes, 4 away:
      right load count but the compiler keeps the three q loads in its own
      order and needs no frame, where the original interleaves all three q
      loads ahead of the first store and spends `push {r4, lr}` on it

The 68-byte form is the closest; the remaining four bytes and the register set
are the scheduler deciding how early the independent q loads issue, which the
sources above do not control.
