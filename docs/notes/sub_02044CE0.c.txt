What the function is
--------------------
An 8bpp tiled-surface rectangle fill.  The surface descriptor is

    +0x00  u8 *pixels
    +0x04  u16 width      (pixels)
    +0x06  u16 height     (pixels)

and the pixels are stored as 8x8 tiles of 64 bytes, eight bytes per tile row.
The rectangle is clipped on the right and bottom against the surface size,
but the left and top are only tested per pixel, which is why the
`if (j >= 0 && i >= 0)` guard sits inside the inner loop.

The address arithmetic is written multiply-then-mask throughout, which is
what the pool constant 0x00007FC0 at 0x02044D84 is for:

    (v * 8) & 0x7fc0    is  (v >> 3) * 64,  the tile index scaled to bytes
    (v * 8) & 0x38      is  (v & 7) * 8,    the row inside the tile

`(v * 8) & 0x38` is not the compiler's own rendering of `(v & 7) * 8`: that
form compiles to `lsl #0x1d` / `lsr #26` instead.  Writing it as a multiply
and a mask is what produces the original's `lsl #3` / `and #0x38` pair, and
0x7fc0 is the same idiom one field wider.  Both were confirmed by compiling
each spelling.

The closest C
-------------
    typedef unsigned char  u8;
    typedef unsigned short u16;
    typedef signed int     s32;

    struct Surface {
        u8 *pixels;
        u16 width;
        u16 height;
    };

    void sub_02044CE0(struct Surface *s, s32 x, s32 y, s32 w, u16 h, u8 value)
    {
        s32 right = x + w;
        s32 bottom = y + h;
        s32 tilesWide;
        s32 i;
        s32 j;

        if (right > s->width)
            right = s->width;
        if (bottom > s->height)
            bottom = s->height;

        tilesWide = (s->width + (s->width & 7)) >> 3;

        for (i = y; i < bottom; i++) {
            for (j = x; j < right; j++) {
                if (j >= 0 && i >= 0) {
                    s->pixels[((i * 8) & 0x7fc0) * tilesWide
                              + ((j * 8) & 0x7fc0)
                              + ((i * 8) & 0x38) + (j & 7)] = value;
                }
            }
        }
    }

What is settled
---------------
- `value` is u8, not u32: a u32 parameter costs an extra `and #0xff` hoisted
  out of the loop.  The original loads the stack slot with `ldr`, so the
  parameter still occupies a full word; only its declared type matters.
- The clip, the tilesWide computation and both loop tests are byte-identical
  in the compiled output, as is the whole inner-loop guard.
- `(s->width + (s->width & 7)) >> 3` and not `/ 8`: the original has a bare
  `asr #3` with no rounding correction.

The one remaining instruction
-----------------------------
The original keeps the two loop-invariant i-derived terms in two separate
registers across the inner loop:

    and r6, r8, r2, lsl #3     ; (i * 8) & 0x7fc0
    mul r5, r6, r4             ; * tilesWide          -> r5, the tile row
    lsl r6, r2, #3
    and r6, r6, #0x38          ; (i * 8) & 0x38       -> r6, the row in tile

and spends r6 as the base register of the final `strb r7, [r6, sb]`, so the
inner loop needs three `add`s to build `sb`.  Every spelling tried makes the
compiler fuse the two invariants into one value before the inner loop, which
costs one `add` (or one `mla`) outside and saves one `add` inside, for a net
loss of four bytes:

  - flat sum, rowInTile last          -> mla r6, r4, r6, r8   (168 bytes,
                                          73 bytes differ, closest by size)
  - flat sum, rowInTile first         -> same fusion
  - two named locals in the outer loop-> add r5, r5, r8 hoisted (168 bytes)
  - `u8 *p = pixels + ...; p[rowInTile] = value;`
                                      -> same fusion, pointer arithmetic is
                                         reassociated (168 bytes)
  - `tilesWide * ((i * 8) & 0x7fc0)`  -> operand order swaps in the `mul`
                                         but the fusion stays (164 bytes)

The multiply's operand order is itself informative: the original's
`mul r5, r6, r4` has the masked value on the left, which this compiler
produces from `((i * 8) & 0x7fc0) * tilesWide` (it emits the source's second
operand as the left register), so the source order of the multiply is
settled even though the fusion is not.

The likely answer is that the address is computed by a small inline helper
whose body the compiler expands per site rather than by one flat subscript
expression, which would explain both the surviving separation and the
right-associated `add` chain (`pixels + (j & 7)`, then `+ tileX`, then
`+ tileRow`).  That shape was not reconstructed here.  Anyone picking this up
should start from the C above and attack only the fusion.

re-measured and ADVANCED, appended 2026-09-21 (bmp.c family wave)

The note above is CORRECT on semantics and still the right starting point,
but its "164 bytes, closest by size" floor has been beaten.  The size is now
RIGHT (168/168) and the mismatch count is down from the note's implied ~73 to
81, with a named source-level lever.

THE LEVER: the subscript is written on the ROW-IN-TILE term, not on the
pixel pointer.  The note's flat form

    s->pixels[tileRow + tileX + rowInTile + (j & 7)] = value;

always lets mwcc fuse the two i-derived invariants into one `mla` before the
inner loop.  Writing the same address as

    rowInTile[s->pixels + (j & 7) + ((j * 8) & 0x7fc0) + tileRow] = value;

(an integer-subscripts-a-pointer expression, legal C and exactly the same
value) keeps `rowInTile` OUT of the address sum and hands it to the `strb` as
the register offset, which is what the image's `strb r7, [r6, sb]` is: r6 is
rowInTile as a BASE, sb the rest of the address.  That alone takes the
compile from 164 bytes to a correct 168 and drops the diff to 108.

Hoisting the two invariants into named locals in the OUTER loop body is
required alongside it -- inlining both expressions at the subscript goes back
to 164 bytes.  So the shape that reaches 168 is:

    for (i = y; i < bottom; i++) {
        s32 tileRow = ((i * 8) & 0x7fc0) * tilesWide;
        s32 rowInTile = (i * 8) & 0x38;
        for (j = x; j < right; j++)
            if (j >= 0 && i >= 0)
                rowInTile[s->pixels + (j & 7) + ((j * 8) & 0x7fc0) + tileRow]
                    = value;
    }

Declaration order then moves it the rest of the way.  Three permuter passes
(hill, budget 35/40/45, 119 compiles) took 108 -> 89 -> 85 -> 81 purely on
`decl-swap`/`decl-reverse` of the local block, and the run PLATEAUS at 81:
the whole top ten of the third pass are 81 and DIFF.  The 81-byte source is
the one above with the locals declared

    s32 tilesWide; s32 i; s32 right = x + w; s32 j; s32 bottom = y + h;

Operand order inside the address sum is INERT at this point: three orderings
(tileRow last, tileRow first, the pointer parenthesised with (j & 7)) all give
exactly 168/108 before the declaration sweep.  Reading s->pixels into a local
inside the guard is worse (92 vs 85).

WHAT IS STILL WRONG, and it is one thing: the original pushes TEN registers
(`push {r3, r4, r5, r6, r7, r8, sb, sl, fp, lr}`) and keeps `fp` live to hold
the base pointer read (`ldr fp, [r0]`), while mwcc pushes EIGHT and re-uses
r8.  Every remaining mismatch is downstream of that one extra live value: the
compiler still folds `tileRow + rowInTile` at +0060 (`add r5, r8, r5`) where
the image keeps them in r5 and r6 to the end.  So the residue is a register-
pressure decision, the same class the rest of this family is stuck on, and no
longer an address-shape question.

0x02044EBC IS CONFIRMED STILL IDENTICAL.  `show` on both was re-run this
wave: 168 bytes each, instruction for instruction the same, same pool
constant 0x00007FC0, only branch displacements relocated.  Whatever closes
one closes the other, and the source above is the one to start from.
re-verified 2026-09-21: no recoverable source in this note

diagnosis -- "a register-pressure decision ... no longer an address-shape
question" -- is right about the mechanism but wrong to treat it as
unreachable from C.  Getting the tenth register is easy; getting it while
keeping the other nine correctly coloured is the open problem.
