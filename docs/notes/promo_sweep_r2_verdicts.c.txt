Why none of them can close yet
-------------------------------

Every unresolved site above is capped by the honesty rule in docs/MATCHING.md
(no witness outside the compared range) and the graduation path in
src/pending/README.md.  Step 1 (a cut) is already exhausted -- each range is one
function wide and the only branch to the target is the site inside it.  Step 2
(the `matched` class) needs the target address to be an entry of an EXACT
manifest shard, and it is not: 0x020911A0, 0x02072E8C, 0x02022490, 0x020253D4,
0x0205CF24, 0x0207FBBC, 0x0207FC48, 0x02089754, 0x02089774, 0x02089398,
0x020896AC, 0x020896CC, 0x0208A38C, 0x02084DA4, 0x020913E8 and 0x020913BC have
no shard entry in layout/matched/arm9/, and `matched_index()` over all shards
returns None for each of them.  0x020911A0 (CTRDG_DummyInit) is named by
layout/symbols_sdk.txt but is not in layout/symbols_sdk.json and is not in
layout/runtime_arm9.txt, and no attest class trusts a name alone; the note in
src/matched/unit_02005430.c already records that its only reference image wide
is the park's own pool word.  Step 3 (a second caller) has not happened either.
So the parks stay parked; each is worth re-running after every wave.

The mechanism itself is live and was re-checked as a control:
src/matched/func_02096670.c, promoted by the earlier pass, still prints EXACT
with "+0020 PC24 func_020965B4 -> 020965B4 [matched x1]", i.e. a park does turn
EXACT with no C change the moment its target has its own EXACT shard entry.
The r2 parks simply have no such entry.
