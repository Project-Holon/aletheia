Reading of the shared residue, for the next wave:

* func_021C18C4 / 021C1A84 / 021C1AD4 / 021C1AFC / 021C2194 all begin with the same
  `movs rX,#0x6b; lsls rX,rX,#2; ldrb rY,[r0,rX]` count load and then walk a record
  array with a constant stride (0x14, 0x18 or 0xd4).  Ours matches the arithmetic
  and the stride every time but colours the count / accumulator / induction webs
  differently (the image puts the byte count in a callee-saved register, ours in a
  caller-saved one, or vice versa).  This is the same class of residue as the ARM9
  bands: a two-colour tie driven by web numbering, not by an expression shape - a
  loop-counter or declaration-order variant did not move it in two rounds.

* func_021C28CC / 021C28DC / 021C28EC are the same three instructions twice:
  `ldr r3,[r0,#4]; ldr r0,[r0,#8]; adds r3,#K; strh r3,[r1]; subs r0,#8; strh r0,[r2]`.
  The image hoists BOTH loads above the first store, which the front end only does
  when it can see that *a and *b do not alias the fields; a two-local spelling does
  hoist but then assigns the fields to the opposite registers (w -> r0, h -> r3).
  The residue is that register swap plus the load placement.

* func_021C2630 and func_021C29B4 are the same block copy from src to p+8 / p+0x20,
  but only 021C29B4 closed: the 12-byte copy wants `adds r2,r0,#0; adds r3,r1,#0`
  (destination first) while every spelling of the struct assignment emits the source
  copy first.  Same trap for func_021C1A64, whose three s16 reads the image orders
  2, 0, 4 (the middle element first).

2. The recipe (one compile each, once the target is witnessed)

   * kind comes from the POOL WORD's parity, not from the target's region:
     odd -> `thumb`, even -> `arm`.  Six of the 60 target ARM9 addresses
     (02040DA8 x6 callers, 0204B3B4, 02040804, 0209C0A4, 0204B1CC,
     02030EAC) and one target inside ov217 (0x021C3F60) are EVEN.
   * the symbols: line carries the EVEN target address plus the region
     token, and match.py adds the Thumb bit:
         func_021C0EC0  0x021C0EC0  thumb  ov217
   * argument setup maps straight through the expression builder:
     `movs rN,#imm` -> literal, `lsls rX,rX,#s` -> `x*2^s`,
     `ldr rN,[rM,#K]` -> `*(u32*)((u8*)p + K)`, `adds rX,rY,rZ` ->
     `base + index`.  Two mwcc constant-materialisation idioms to expect
     rather than copy: `movs r1,#0x4b; lsls r1,#2` is just 0x12c, and
     `movs r2,#0xa; lsls r2,#6` is just 0x280.
   * 35 of the 60 closed on the first spelling, on the symbols line alone.

1. What actually limited O29, measured

   inv29.py did decode `.inst` (0 undecoded left in its output) - the loss was
   in its ENGINE, not its decoder.  It set a call's result as a pending
   expression and then dropped the statement: `bl X; adds r4,r0,#0; bl Y`
   came out as a body with one call and no locals (O29's own results file shows
   func_021B9AF8 compiled to 8 bytes against a 16-byte original).  Two
   structural faults, both fixed here:

   * a call result is a LAZY value that stays in r0 and is inlined into
     whatever consumes it - the next call's argument list, a store's rhs, a
     local initialiser, the return.  `bl X; movs r1,#0; bl Y` is `Y(X(), 0)`,
     and that is the only spelling that reproduces the image order.  A pending
     value that is never consumed is flushed as a plain statement.
   * `is_plain_call()` must balance parens: `func_X(*(u32*)(a0+40))` is a
     statement, and a regex like `[\w]+\([^()]*\)` says it is not, which moves
     the call into a hoisted `u32 t0 = ...;` declaration and reorders the whole
     body.  That single regex cost every body with a load-fed call.
