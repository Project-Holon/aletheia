cap record -- two targets, both MATCH-capped before any C was written
=====================================================================

both of these are capped by the same structural fact: the only witness in the
whole image for a data address the function loads is the function's OWN literal
pool word, and that word sits inside the compared range for any byte-identical
compile.  No source shape can close them, so per the brief the bodies were NOT
written; the screen below is the finding.

1. PRIMARY  0x0206CB8C  func_0206CB8C  (pkt_0206CB8C, 1868 code bytes + 16 pool)
--------------------------------------------------------------------------------

extent:        listing extent 1884 bytes, 0x0206CB8C..0x0206D2E8 (next label
               func_0206D2E8); code ends 0x0206D2D8, pool 0x0206D2D8..0x0206D2E8
isa:           arm    (push {r4-r8,sb,sl,fp,lr}; pop {...,pc})
relocations:   inferred from the original: 7 external branch sites (8 `bl`
               instructions, 0x0207D8E0 reached twice) + 2 R_ARM_ABS32 data
               sites (the two hardware words 0x04000440 / 0x04000450 are spelled
               as constants in this project's convention and need no witness;
               both attest anyway, literal x57 / x2)

every branch target attests cleanly:

  0206CBD0 bl 02082AC0  label x102   0206CEB0 bl 0207DC98  label x20
  0206CBD4 bl 0206DB80  label x57    0206CED8 bl 0207D934  label x3

  pool_0206D2E4 = 0x0214A1F4, loaded once, by the `ldr r1, pool_0206D2E4`
    at 0x0206D038 (imm 0x2A4: 0x0206D040 + 0x2A4 = 0x0206D2E4)

  evidence().pool_words[0x0214A1B4] -> {0x0206D2DC}   (5 index entries, 1
                                                       distinct address)
  evidence().pool_words[0x0214A1F4] -> {0x0206D2E4}   (5 index entries, 1
                                                       distinct address)
  raw u32 scan of the whole arm9 region (0x02004000..0x020A9E80):
    0x0214A1B4 occurs exactly once, at 0x0206D2DC
    0x0214A1F4 occurs exactly once, at 0x0206D2E4
  both addresses are OUTSIDE the arm9 image (0x0214A1B4 > 0x020A9E80): RAM,
    so no `func_` label and no string/veneer/literal-from-elsewhere is even
    possible for them, and no `matched` entry can cover data
  match.attest(0x0214A1B4, 'data', 0x0206CB8C, 0x0206D2D8) -> ('literal', 5, 0x0206D2DC)
  match.attest(0x0214A1B4, 'data', 0x0206CB8C, 0x0206D2E8) -> None
  same for 0x0214A1F4: witness 0x0206D2E4 appears at hi=0x0206D2E0, None at
    0x0206D2E8

why this cannot be cured by any C, any cut, or any source spelling:
`resolve_relocations(fb, place, ...)` is called with size=None, so the compared
range is [place, place + len(fb.data)) -- the compiled section, pool included.
mwccarm puts each function's constant pool at the end of that function's own
section (observed directly: a 40-byte probe function compiled at 0x0206CB8C put
its two ABS32 words at +0x20 and +0x24 of its own section).  The pool word for
0x0214A1B4 must be at 0x0206D2DC in any byte-identical build, because the load
at 0x0206CC28 reaches it PC-relatively; the section must be at least 1884 bytes
to hold body + pool; therefore 0x0206D2DC is always strictly inside the compared
range.  A cut cannot separate a function from its own pool.  --suggest-split
therefore has nothing to offer and was not run.

This is the class docs/MATCHING.md already records as still open for
0x02008CF8 ("0x020A70C4 and 0x0209DDB4 are each named by one pool word, its
own"), and the same class as the parked private-table files.

two ways to get bytes that match anyway, both refused here on purpose:
  * declare a *base* symbol whose pool witness IS outside the range and spell
    the address as base + offset.  This resolves, because resolve_relocations
    attests the declared SYMBOL address and then writes (target + addend); the
    addend is then chosen to make the word come out.  Since every address in the
    image is some pooled address plus a constant, this defeats the witness rule
    in general and was not used.  (Worth knowing for the tool: the attestation
    is on S, not on S+A.)
  * write 0x0214A1B4 as a raw numeric constant so no relocation exists.  That is
    reading the answer out of the compared bytes and confirming the compared
    bytes contain it, which is the tautology the honesty rule exists to refuse.

--------------------------------------------------------------------------------
3. verdict for both
--------------------------------------------------------------------------------

no C was written: a body reaching either function cannot be anything better than
MATCH, and the brief says to report that and move on rather than spend the run
on it.  Nothing was placed in src/matched/ or src/pending/ and no shard was
written (a shard entry requires an EXACT verdict).

what would close them, and it is not source work:
  * 0x0206CB8C: a second pool word holding 0x0214A1B4 or 0x0214A1F4 anywhere
    else in arm9 -- i.e. a second function in the original that referenced the
    same RAM object (it would have to be matched first, or simply exist in the
    image; it does not exist today).
  * 0x0206BA18: same, for 0x02148DB4 (a second referencing function) and for
    0x020A1954 (a second pool word for the blend-mask table).
  Both are evidence questions about the rest of the image, not about these two
  functions.

and the search for such a witness is exhausted, not merely ARM9-local: a raw
u32 scan over EVERY region in the file (all 242 -- arm9 plus all 241 overlays,
72 MB, via match.load_all_regions()) finds each of the four addresses exactly
once in the entire ROM:

  arm9 0206D2DC  value 0214A1B4
  arm9 0206D2E4  value 0214A1F4
  arm9 0206BE8C  value 02148DB4
  arm9 0206BE94  value 020A1954

i.e. the four occurrences are the four blocking words themselves.  So no
widening of the `literal` class to overlays, and no other class, can attest
them: the addresses are simply never mentioned anywhere else in the ROM in any
encoding.
