==============================================================================
addendum, wave 7 pseudo-families (pkt_02074A34): the pin closes func_02074E10,
and takes func_02074CD0 from 67 bytes out to 2
==============================================================================

This note's two conclusions about the 24-bit header field were BOTH right, and
both were measured against the wrong front end.  Under `--cc ../2.0/sp2` (the
cluster pin, docs/families/cluster_02074A34.h):

  0x02074E10  now EXACT, 140/140, filed as src/matched/func_02074E10.c.
  0x02074CD0  now DIFF at 320/320 with 2 concrete bytes out (was 316 vs an
              oversized-and-skipped judgment; this note never reduced it).

WHAT THE NOTE HAD RIGHT.  The body it recovered reproduces exactly, and the
bitfield reading of the value is required: `(w << 8) >> 8` folds to
`bic r0, r0, #0xff000000` under both front ends and loses the image's
`lsl r0,r0,#8` / `lsr r0,r0,#8` pair.

WHAT IT MISSED, and why the pass stalled.  The note reports that moving the
flag test to a plain `(o->w >> 24) & 1` while keeping the bitfield view for the
value "costs the whole function: 132 bytes compiled, 67 concrete bytes differ,
because the two views stop sharing the header load".  The two views stop
sharing the load because they were written as two POINTERS.  Written as ONE
UNION they share it:

    union Hdr {
        unsigned w;
        struct { unsigned v : 24; unsigned flag : 1; unsigned rest : 7; } b;
    };
    ...
    if ((o->w >> 24) & 1) r = func_020750EC(o->b.v, c, d);
    else                  r = func_02075080(o->b.v, c, d);

That is the whole fix for the two bytes at 0x02074E3C the note could not move.
The remaining 8 of the 140-vs-132 gap is the front end: 1.1p1 -O4,p hoists the
second and third call arguments above the branch and cross-jumps the two arms
onto one call sequence, where the image computes `mov r2, r4` / `lsr r0,r0,#8`
separately INSIDE each arm (0x02074E50/0x02074E54 and 0x02074E60/0x02074E64).
No source spelling of the arms moves that; the compiler does.  Under the pin
the same C is 140 bytes, 0 mismatches.

0x02074CD0: THREE LEVERS BEYOND THE UNION, then a two-byte register wall.

  1. func_02074450 TAKES ONE ARGUMENT, not four.  The image's `bl 0x2074450`
     at 0x02074D48 has NO argument setup before it at all -- r0 still holds the
     halfword the `cmp` just tested.  Declaring it `(u32,u32,u32,u32)` makes the
     compiler emit `mov r1,sl` / `mov r2,sb` / `mov r3,fp` and costs 16 bytes.
     Attested outside this cluster by src/matched/func_02028C50.c,
     src/matched/unit_020064B8.c and src/matched/unit_020067E0.c, all EXACT.
  2. THE func_02074E10 GUARD RETURNS THAT CALL'S OWN RESULT, not 0.  The image
     pops straight out at 0x02074D84 with no `mov r0` before it, so it is
     `r = func_02074E10(...); if (r != 0) return r;`.  Writing `return 0` costs
     a `movne r0, #0`.
  3. THE LOOP COUNTER IS `int`.  `blt` at 0x02074DF0 is signed; `u32` gives
     `blo`.

With all three the compile is 320 bytes against the original's 320 and exactly
TWO bytes differ, both the destination register of one conditional load:

    02074DFC (+0100)  ldrne r2, [sp, #4]     original
                      ldrne r0, [sp, #4]     compiled
    02074E00 (+0104)  cmpne r2, #0           original
                      cmpne r0, #0           compiled

Everything else -- the ten-register `push {r3,r4,r5,r6,r7,r8,sb,sl,fp,lr}`, the
pooled 0x0000ffff sentinel at 0x02074E0C, all six call sequences, all seven
early exits, the `tst`/`cmpne` guard pairs -- reproduces byte for byte.
