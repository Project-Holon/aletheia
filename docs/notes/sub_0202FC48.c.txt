The control flow, the instruction selection, the scheduling and the pool
layout are all reproduced.  The whole delta is one instruction and the
register names that follow from it:

  original                         compiled
  r4  = hoisted constant 0         sb  = hoisted constant 0

  sb  = total (count + 0x18)       r8  = &g_EnvModule
  (sb reloaded with 0 at +0x114    sl  = total
   by `mov sb, r4`)                (no such copy needed)

  push {r3, r4, r5, r6, r7, r8, sb, lr}   vs   push {r4..sl, lr}

The original spends six callee-saved registers and therefore has to
re-establish the constant zero for the final loop with `mov sb, r4` (r4
holds the just-initialised loop counter, which the value numberer knows is
0).  The compile spends seven, because the hoisted zero and `total` never
share a register, so the copy is not needed and the function comes out four
bytes short.

Equivalently: in the original the zero's live range ends at the clearing
loop and is coalesced with the following loop counter; in the compile it
stays live to the end of the function and is coalesced with nothing.

Ruled out, each re-verified as byte-identical output (376 bytes, 121 diffs):

  - all 24 permutations of the four local declarations
    (total / i / mem / slot), including making the clearing loop share the
    counter with the two later loops (that one is worse: 368 bytes);
  - binding the stored zero to its own named local defined at the top of the
    function, so its definition point precedes the clearing loop's counter;
  - spelling the null pointer store as `(void *)0` versus `0`;
  - binding the heap id and the trailing `return 0` to a named local set to
    zero late, so the final loop's zero is nominally a different object;
  - `0u` versus `0` on the allocator's heap argument.

The compiler treats a zero-valued local as a rematerialisable constant in
every one of those spellings, so none of them changes the allocation order.
Whatever fixes this is not a local declaration or a constant spelling; it is
something that makes the clearing loop's stored zero a value the allocator
must rank ahead of the loop counter.  That is the thing to look for next.

     r4  clear-loop stored zero (+0x20..+0x0AC), then the ids counter

   one dies.  The compile reuses only two, because its zero is a single value
   live from +0x20 to the last call site, which overlaps `total`'s range and
   forces `total` into a seventh register.  The original's zero dies at the
   clearing loop and is re-materialised twice.
