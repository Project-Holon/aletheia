The original spends six callee-saved registers and therefore has to
re-establish the constant zero for the final loop with `mov sb, r4` (r4
holds the just-initialised loop counter, which the value numberer knows is
0).  The compile spends seven, because the hoisted zero and `total` never
share a register, so the copy is not needed and the function comes out four
bytes short.

Equivalently: in the original the zero's live range ends at the clearing
loop and is coalesced with the following loop counter; in the compile it
stays live to the end of the function and is coalesced with nothing.

The compiler treats a zero-valued local as a rematerialisable constant in
every one of those spellings, so none of them changes the allocation order.

something that makes the clearing loop's stored zero a value the allocator
must rank ahead of the loop counter.  That is the thing to look for next.
