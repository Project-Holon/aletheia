VERDICT: not decompilable, and not worth any further agent time.  This
packet is not game code and not compiled C at all.  It is the mwccarm /
MSL ARM runtime helper library (the `runtime.a` soft-float and 64-bit
integer support routines), linked in as hand-written assembly.  The
worklist ranks 0x0209C0A4 as the single most-called open function in the
image (fan-in 549) purely because every integer division in the game
calls it; that fan-in is a property of the helper, not a sign that a
core game layer lives here.

Recommend the integrator mark the whole range non-C (the same way SDK
library ranges are handled) and drop it out of the open pool, so it stops
dominating `worklist.py --targets`.

WHY IT CANNOT BE C
------------------
Three independent structural proofs, any one of which is sufficient:

1. Multiple entry points branch into the middle of another entry point's
   body.  0x0209C00C and 0x0209C018 are two twelve/sixty-byte entries
   that set r4 to 0 and 1 respectively and then both fall into the same
   shared body at 0x0209C020; 0x0209BE4C sets r4 |= 1 and branches into
   0x0209BE6C; 0x0209CB8C's third instruction is `bmi #0x209C968`, a
   backward branch into the middle of 0x0209C95C.  mwccarm emits one
   section per function and cannot produce a displacement branch between
   two functions at all (see
   docs/idioms/tail-call-is-a-pool-word-and-bx.md), let alone into
   another function's interior.

2. Register usage outside the C ABI: `push {r4,r5,r6,r7,fp,ip,lr}` at
   0x0209BE4C and 0x0209C00C saves ip (r12), which compiled C treats as
   the intra-procedure scratch register and never preserves.

3. Dead prologues that compiled C would never emit: 0x0209C054 does
   `push {r4,r5,lr}` for a leaf, then `pop {r4,r5,lr}; bx lr` rather
   than `pop {r4,r5,pc}`.
