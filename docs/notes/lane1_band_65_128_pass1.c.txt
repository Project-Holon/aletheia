Levers that closed these, kept for the next pass
------------------------------------------------
* `0x02022CEC`: the family's 5th argument is a byte, not a word - the two
  allocator arms differ only in `0x604` versus `0xc08` and the loop seed is
  the loop index, not zero (`str r5, [r2, r1]` where `r5` is the counter).
  Writing `= 0` produced the same instruction count with the counter in the
  wrong register; writing `= i` reproduced the original's `r5` reuse.  The
  loop counter must also be `int`, not `u32` (`blt`, not `blo`).
* `0x0201A374`: the two guard bytes must be read through `a0[2]` / `a0[3]`
  expressions, not through `u8` locals: hoisting them into locals makes the
  prologue save `a0` differently and pre-loads both, four bytes short.
* `0x02023B74`: one volatile read-modify-write per arm, and the merge value
  is a 32-bit `u32 v`, not a `u16 v` - a `u16` local makes the compiler
  re-truncate with `lsls/lsrs #0x10` after the `bics`.
* `0x02025FC8`: the first arm must FALL THROUGH to the shared `return -1`
  (`if (a0[8] == 1) { if (m & 0xf3) return f(a0); } else if ...`).  Written
  with an explicit `return -1` in the first arm the two -1 exits do not
  cross-jump and the function is four bytes long.
* `0x020261E4`: the element pointer needs its own `base = p + 0x3c` local
  declared after `p`; that is what puts `p` at `sp+8` and the base at `sp+4`.
* Whole-slice note: `EXACT*` appears whenever the follower has no label, and
  the harness then reports the compiled size as the floor (94 of 96, 82 of
  84, 74 of 76, ...).  It is never a byte difference.

DIFF residues (no home in src/matched/, C kept below)
-----------------------------------------------------
Five rows of the slice reached a real `DIFF` - same instruction sequence,
concrete bytes differing in a register number, a stack slot or an operand
order, and no lever found inside this pass' budget.  Their C is kept in
`scratch/lane1/diff/` for the pass that brings a new lever.

### 0x02023AF4 (82 compiled, 84 original) - flag register
The whole body matches except that the original keeps its fill flag in `r7`
and the loop's 0/1 constants in `r3`/`r6`, while this lane's compiles put the
flag in `r2`/`r3` and the constants in the saved registers.  Two things were
established and are worth keeping:

* the split point must be two statements, `q = a2 * (int)(hi - lo) / a3;`
  then `mid = q + lo;` - as one expression `a2 * (int)(hi - lo) / a3 + lo`
  the compiler emits `adds r0, r6, r0` (lo first) where the original has
  `adds r0, r0, r6`;
* `lo` and `hi` must be `u32` - the band test is `bhi` (unsigned), while the
  divide is `_s32_div_f`, so the multiply operand carries the `(int)` cast.

### 0x0202590C (110 compiled, 112 original) - prologue scheduling
Byte for byte identical from `+0x10` to the end; only the first five
instructions differ: the original spills `a1` and `a2` to `sp+0`/`sp+4`
BEFORE it loads the row bound, while every spelling tried here
(`int i, j`, `s8`, explicit `u32 x = a1; y = a2;`, `s16 xy[2]` inside or
outside the loop) loads `a0[0xcb]` first.  Everything else - both loop heads,
both truncations, the stack-built source rectangle and the call argument
order - is already right.

### 0x0202570C (100 compiled, 102 original) - one extra live register
The instruction sequence matches end to end once the offsets are shifted by
the two bytes of a `push {r3, r4, r5, r6, r7, lr}` that this lane's compiles
do not need: the original keeps a second copy of the outer index in `r7`
(`adds r7, r6, #0; adds r4, r7, #0` before the inner guard), so its inner
loop has a separate pre-test instead of the merged `cmp r6, r0; bhs`.
`j = i`, `k = i; j = k`, and `j = 0` all compile to the shorter, correct
form.  Semantics are not in doubt (both spellings free the same cells).

### 0x02023E9C (84 compiled, 88 original extent) - prologue register order
The body matches; the difference is `adds r4, r1, #0` (save `a1`) placed
before the `a4` load in the original versus after it here, and with it the
temp register (`r1` there, `r0` here) for the `(u8)` casts.  A struct-typed
pointer parameter and a local `u8 *p = a0;` both reproduce the same wrong
order.  Cost so far: five spellings.

### 0x02017CC8 (98 compiled, 104 original) - parameter save order
Same story at six bytes: the original saves `a1` to `r6`, `a2` to `r7` and
`a0` to `r5` and keeps the field value in `r4`; every spelling tried saves
`a1` to `r4` first, which then shifts the whole function.  The two-call
`func_0201AE1C(func_02019C54(x, (u16)v), 0x14)` shape and the
`if (A == 1 && y != 0xff) return;` guard both reproduce exactly.
