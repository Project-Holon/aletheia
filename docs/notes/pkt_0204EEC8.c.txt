Open row worked: func_0204EEC8 (0x0204EEC8, ARM, 132 bytes, 2 calls, 3 pool
words).  Listed as `ready` in the band screen, but it can never be EXACT:
every one of its three literal-pool words is data whose only occurrence in the
image is inside this function, so all three sites stay unresolved whatever the
C is (MATCH at best, and the screen's "ready" only ever covered call targets).

What the original says that this C must be adjusted for.

  * The two index fields: `and r4, r2, #0x70` + `asr ip, r4, #4` is an
    *arithmetic* shift, so the bank is signed in the original (a signed 3-bit
    field at bit 4, or `(s32)` somewhere on the fmt path); the sub-field is
    `and r7, r2, #7` and stays unsigned.  With `u32 fmt` the compiler emits
    `lsr`, which is 1 byte of residue.
  * The two tables are 8-byte records, not u32 arrays: `ldr ip, [r8, ip,
    lsl #3]` and `ldr r5, [r6, r7, lsl #3]`, and the second pool word is the
    first one + 4 (0x020A14D8 against 0x020A14D4), so the source reads two
    fields of one 8-byte record type through two different symbols.
  * Register pressure: the original needs r4-r8 (5 callee-saved), this C gets
    r4-r6, which is why most of the byte diff is register names after the
    first two instructions.

The 5-argument shape is settled: [sp, #0x18] is the fifth argument after six
pushed registers and it is read with `ldrb`, which names it a u8; the fifth
argument of the second call comes back off the caller's own stack with a plain
`ldr` (u32) and the sixth with `ldrh`.  The two calls both go to
func_0209C0A4 (0x0209C0A4, [label x280]), which is attested.

Nothing here is a dead end for a later pass: fix the signedness of the bank
field, make the tables 8-byte record arrays, and it is byte-correct but still
MATCH for the three unwitnessed data words - so it belongs in src/pending/
with `literal` as the blocking class, not in a shard.
