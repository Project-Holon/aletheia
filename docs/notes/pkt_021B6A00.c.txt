## The two rules that closed this batch

1. **A DATA target that is contested wants the ABSENCE of the region token, not the
   token.**  `func_021B6A00` and `func_021B65D8` each failed first compile with
   `021C88E8: the ov172 hint is contested (another overlay in the window starts an
   object there)`.  Deleting `ov172` from the `symbols:` line and re-compiling with
   no other change flipped both to EXACT.  This is brief rule 8 restated for the
   ov172 data page: `g_021C88E8  0x021C88E8  data` compiles, `...  data  ov172`
   does not.  The converse also held here: `g_021C6E9C`/`g_021C6EA8`/`g_021C4D20`
   resolve `sole-ref` *with* the token, so try the token first and drop it on the
   contested message rather than guessing.
2. **An index kept in a variable is what produces `ldr r0,[r5,r4]`.**  `func_021BDC70`
   releases five handles at +0x1dc..+0x1c8.  Written as literal offsets
   (`*(u32*)(p + 0x1d0)`) CW folds base and offset into an immediate and the function
   compiles frameless (`push {r4,lr}`) where the image has `push {r3,r4,r5,lr}` and
   register-indexed loads.  Written as `u32 *a0` indexed by a *variable* slot
   (`i = 0x77; v = a0[i]; ... i = 0x76; f(a0[i]); f(a0[i-2]); ...`) it reproduces the
   image byte for byte in one compile, including the `movs r4,#0x77 / lsls r4,r4,#2`
   scale and the `adds r0,r4,#0 / subs r0,#8` offset arithmetic.

## ISA conflicts are a one-line fix, and the message names the answer

`func_021BDC70` stopped at `ISA conflict for func_0202F038 at 0202F038: the source
declares arm, the image says thumb (the func_0202F038 label in asm/arm9)`.  The
image distinguishes `bl` (thumb) from `blx` (arm) per call site; reading that column
and fixing the four `arm` tokens to `thumb` on the `symbols:` block was the whole
fix.  Do not "resolve" the conflict any other way.
