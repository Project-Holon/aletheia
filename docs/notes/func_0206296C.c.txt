func_0206296C (0x0206296C, arm9, ARM, pkt_0206296C) -- near miss, 120 of 124 bytes

Same class of miss as docs/notes/func_02046110.c.txt: the original re-loads a
struct field after storing to it, and -O4,p forwards the stored value instead.

    +0004  ldr r1, [r0, #4]     ; bank->array
    +000C  add r1, r1, r0
    +0010  str r1, [r0, #4]
    +0014  ldr r1, [r0, #8]     ; bank->nodeBase, strictly after, same scratch
    +0018  add r1, r1, r0
    +001C  str r1, [r0, #8]
    +0020  ldrh r1, [r0]
    +0024  ldr r4, [r0, #4]     ; <-- fresh load of the value just stored

Every spelling tried compiles the two fixups in parallel (two scratch
registers) and materialises r4 from the stored value, four bytes short.
Tried: plain member assignment; u32-typed fields; pointer-typed nodeBase; an
inlined `static void unpackOffset(u32 *p, void *base)` helper taking the
field's address; and a fully type-punned `*(u32 *)((u8 *)bank + 4) = ...`
store. Swapping the declaration order of `i` and `array` does fix the
register allocation (lr for the counter, r4 for the array) but not the
forwarding.

Everything else is byte-identical, including the u16 loop counter's
lsl#16/lsr#16 pair and the reload of bank->numMultiCell and bank->nodeBase
inside the loop. The format reading this function establishes is certain and
is written up in src/matched/func_020629E8.c's header.
