WHAT IT IS
----------
MT19937, the reference `genrand_int32` with its state regeneration inlined.
Everything lives in one heap object reached through the pointer at
0x021469F8:

    +0x000  u32 mt[624]      the state vector, N = 624
    +0x9c0  int mti          the cursor, signed (the guard is `blt`, not `blo`)
    +0x9c4  u32 mag01[2]     { 0, MATRIX_A }, indexed by y & 1

M = 397 is read straight off the two far offsets: +0x634 (= 397 * 4) in the
first loop and -0x38c (= -227 * 4 = (397 - 624) * 4) in the second.  The
loop bounds 227 = N - M and 623 = N - 1 are the reference implementation's.
The untouched-state sentinel is N + 1 = 625 and the default seed is 5489;
the compiler does not spend a pool word on 5489, it derives it as
`625 + 0x1300` from the pool word it already loaded for the sentinel
compare, which is why the listing shows `add r0, r0, #0x1300` right after
the `cmp r1, r0`.

func_0203F034 is `init_genrand`.

The tempering tail is the textbook one, with 0x9d2c5680 and 0xefc60000 in
the pool, and the cursor post-increment `mt[mti++]` written back before the
element is read because the store may alias the global pointer itself.

The state pointer is reloaded from 0x021469F8 on every iteration of both
loops, for the same aliasing reason: the store into mt[kk] may write the
pointer.  Caching it in a local is shorter and wrong.
