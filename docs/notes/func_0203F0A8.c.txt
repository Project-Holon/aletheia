WHAT IT IS
----------
MT19937, the reference `genrand_int32` with its state regeneration inlined.
Everything lives in one heap object reached through the pointer at
0x021469F8:

    +0x000  u32 mt[624]      the state vector, N = 624
    +0x9c0  int mti          the cursor, signed (the guard is `blt`, not `blo`)
    +0x9c4  u32 mag01[2]     { 0, MATRIX_A }, indexed by y & 1

M = 397 is read straight off the two far offsets: +0x634 (= 397 * 4) in the
first loop and -0x38c (= -227 * 4 = (397 - 624) * 4) in the second.  The
loop bounds 227 = N - M and 623 = N - 1 are the reference implementation's.
The untouched-state sentinel is N + 1 = 625 and the default seed is 5489;
the compiler does not spend a pool word on 5489, it derives it as
`625 + 0x1300` from the pool word it already loaded for the sentinel
compare, which is why the listing shows `add r0, r0, #0x1300` right after
the `cmp r1, r0`.

func_0203F034 is `init_genrand`.

The tempering tail is the textbook one, with 0x9d2c5680 and 0xefc60000 in
the pool, and the cursor post-increment `mt[mti++]` written back before the
element is read because the store may alias the global pointer itself.

The state pointer is reloaded from 0x021469F8 on every iteration of both
loops, for the same aliasing reason: the store into mt[kk] may write the
pointer.  Caching it in a local is shorter and wrong.

WHAT IS LEFT
------------
Both loops, at the load of mt[kk]:

    original                           compiled
    add r3, r0, r1, lsl #2             add r3, r0, r1, lsl #2
    ldr r2, [r3, #4]                   ldr ip, [r3]
    ldr ip, [r0, r1, lsl #2]           ldr r2, [r3, #4]
    bic r2, r2, #0x80000000            and ip, ip, #0x80000000
    and ip, ip, #0x80000000            bic r2, r2, #0x80000000

The original addresses mt[kk] with the scaled-register form
`[r0, r1, lsl #2]`, the same form its own store uses, and keeps the
compiler-built base `r3 = &mt[kk]` for the two accesses that carry a
non-zero displacement (+4 and +0x634 / -0x38c).  Every compile folds
mt[kk] onto that base as `[r3, #0]` instead, and that dependence on r3 is
what drags the load of mt[kk] ahead of the load of mt[kk+1] and swaps the
two masks with it.  The registers are right, the instructions are right,
only the base of one load and the resulting issue order are wrong.

The addressing mode is invariant under every spelling of the three
subscripts that does not also introduce a named pointer local, and the
named pointer local costs a register.  By
docs/idioms/a-materialised-shift-temporary-is-not-reachable-from-c-or-from-flags.md
this is the instruction-selection residue class: a form present in the
original and absent in the compile, with no C-level name for the choice.
The one lever that class allows, giving the value an extra consumer that
cannot take the folded form, does not apply here because the value in
question is an address, not a datum.
