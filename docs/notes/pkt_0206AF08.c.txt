0x0206AF08 is a linked-list walk: for every node with `idx < count` (u16 array
at +0x1a, count byte at +0x19, next at +0x10) whose entry has (v & 0x300) ==
0x100 and a non-null callback at +0x0c, call cb(a0, node, v & 0xff) and
remember 1; returns 0 if the list is empty or nothing fired.  `idx` must be
`u32` and `count` a `u8` so the `idx < count` test is the unsigned `bhs` the
original has; with an `int` counter the comparison comes out signed.

0x0206AF74 is the one row in this packet that needed a type qualifier rather
than a different spelling: with `s32 *dst` mwcc groups the `if (flag)` arm
into three hoisted loads + three adds + three stores, while the original is
strictly sequential (`ldr r1,[r0] ; add r1,r1,r2 ; str r1,[r0]` three times).
Spelling `dst` as `volatile s32 *` reproduces the sequential form and leaves
the `else` arm (ldr src, ldr dst, mul, add, str) byte-identical, so the file
is EXACT with that qualifier.  `src` must stay plain: making it volatile too
reverses the two loads in the else arm.  Same lever family as
src/matched/func_0206AF08.c's packet-mate note above.

Same node walk as 0x0206AF08 in the packet note (count byte at +0x19, u16
array at +0x1a, next at +0x10, callback at +0x0c), but it ORs the callback's
result into the caller's word and it compiles as a do-while: the entry falls
straight into the body with no null test and the tail is `n = n->f10;
cmp n,#0; bne body`.  Every instruction from +0x24 to the epilogue is already
identical; the only residue is the order of the first seven instructions.

    typedef unsigned char  u8;
    typedef unsigned short u16;
    typedef unsigned int   u32;

    struct Node {
        u8  pad_00[0xc];
        void (*f0c)(u32 *out, struct Node *self, u32 mode);
        struct Node *f10;
        u8  pad_14[5];
        u8  f19;
        u16 f1a[1];
    };

    int func_0206B3D0(u32 *out, struct Node *n, u32 idx)
    {
        u32 v;
        int r;

        *out = 0;
        r = 1;
        do {
            if (idx < n->f19 && (n->f1a[idx] & 0x300) == 0x100 && n->f0c != 0) {
                n->f0c(&v, n, n->f1a[idx] & 0xff);
                *out |= v;
                r = 1;
            }
            n = n->f10;
        } while (n != 0);
        return r;
    }

`r = 1;` inside the if-body is the load-bearing detail: it is what keeps the
constant 1 live across the `blx`, which is what buys the seven-register push
`{r3, r4, r5, r6, r7, r8, lr}` plus the 4-byte frame.  `return 1;` at the end,
`r` assigned before the loop, `r = 1` at the top of the body, and a
`for(;;)`+`break` loop each lose r8 and one instruction.

Residue, the seven prologue instructions:

    original:  mov r7, r0 ; mov r0, #0 ; mov r6, r1 ; mov r5, r2 ;
               str r0, [r7] ; add r4, sp, #0 ; mov r8, #1
    compiled:  mov r7, r0 ; mov r0, #0 ; str r0, [r7] ; mov r0, #1 ;
               mov r6, r1 ; mov r5, r2 ; add r4, sp, #0 ; mov r8, r0

The store to `*out` is scheduled before the argument moves instead of after
them, and 1 reaches r8 through r0 instead of being moved straight in; the loop
body then rides the resulting 4-byte displacement, which is why the raw byte
count (113) overstates the residue.  Tried and ruled out: `int r = 1;` with
the initialiser on the declaration (both declaration orders), `r = 1;` before
the loop, `r` assigned at the top of the body, `*out = 0` placed before and
after r's initialisation, `u32 v` against `u32 v = 0`, and `return 1` with r
unused.  All eight give the same prologue order.
