Everything else in the source recorded above is unchanged and was already
right.  That one token is the whole nine bytes.

WHY IT WORKS, which is the part worth carrying to other functions.  The residue
this note describes is an INCOMING parameter's home store sliding from the front
of the prologue's register shuffle to the back:

    original                     u32 heap
    adds r5, r0, #0              adds r5, r0, #0
    str  r3, [sp, #4]    <-      adds r7, r1, #0
    adds r7, r1, #0              ldr  r0, [r5, #0x50]
    ldr  r0, [r5, #0x50]         ldr  r1, [r5, #0x54]
    ldr  r1, [r5, #0x54]         adds r4, r2, #0
    adds r4, r2, #0              str  r3, [sp, #4]    <-

With a `u32` parameter, r3 already holds exactly the value the allocator call
will want, so the home store is pure bookkeeping and mwcc is free to sink it to
the end of the shuffle; it does, and the prologue comes out in declaration
order.  With a `u8` parameter the home slot holds the NARROWED value, which is
not what r3 holds, so the store has to be emitted before anything can clobber
r3 - and that restores the original's order, which is first-use order (the heap
id feeds the allocator, `a` and `b` are read only at the very end).  This note
had already spotted that the original's order is first-use order; what it was
missing is that a narrow parameter type is how you ask for it.
