pkt_020729C0 - a four-statement arm that this front end predicates
==================================================================

Packet 0x020729C0..0x02072A08, arm: 0x020729C0 (68 bytes) only.  A leaf, no
calls, one relocation (g_0214DEC0, resolves as `literal x30`).

Reconstructed body:

    int func_020729C0(void)
    {
        u32 m = 1;
        int i;

        for (i = 0; i < 8; i++) {
            if ((g_0214DEC0.f4 & m) == 0) {
                g_0214DEC0.f4 |= m;
                return i;
            }
            m <<= 1;
        }
        return -1;
    }

The loop skeleton, the increment order (`add r0,r0,#1` / `cmp r0,#8` /
`lsl r3,r3,#1` / `blt`), the `mov r3, #1` before the loop and both pool loads
of 0x0214DEC0 are all reproduced.  The residue is the guard's arm:

    ORIGINAL                              COMPILED
    tst r1, r3                            tst r1, r3
    bne  <increment block>                ldreq r1, [pc, #0x24]
    ldr r1, [pc, #0x24]                   ldreq r2, [r1, #4]
    ldr r2, [r1, #4]                      orreq r2, r2, r3
    orr r2, r2, r3                        streq r2, [r1, #4]
    str r2, [r1, #4]                      bxeq lr
    bx lr                                 add r0, r0, #1
    add r0, r0, #1                        ...

This front end converts the whole five-instruction arm (load, load, orr, str,
return) into a predicated block and saves four bytes; the original branches
over it instead.  Note this is the *opposite* direction from
docs/notes/pkt_02072EA8.c.txt, where the original predicates a two-statement
arm and this front end will not: here the original refuses to predicate a
longer arm than ours will.  Spelling the arm as a `goto` to a label after the
loop, as an `if/continue`, with the store through a named local, and with the
return value hoisted into a local were all tried; every one predicates.

lane6 addendum (independent run, same address, same verdict): the cached-local
spelling was tried too -

    int i; u32 m; u32 v = g_0214DEC0[1];
    for (i = 0, m = 1; i < 8; i++, m <<= 1)
        if ((v & m) == 0) { g_0214DEC0[1] |= m; return i; }
    return -1;

and it predicates as well (ldreq/ldreq/orreq/streq/bxeq), with the same
`tst r1, r3` + hoisted value the file above records.  Also tried: the raw cast
`(*(u32 *)0x0214DEC4)` instead of the extern array - same predication, and it
moves the pool word to 0x0214DEC4 with a zero displacement, so the extern-array
spelling is the one that keeps the original's `ldr r1, [r1, #4]` encoding.
Compiled 64 bytes vs 72 original in every spelling tried here.

lane6 addendum 2 (same address, third run): putting the shift in the for
increment rather than at the end of the body restores the *72-byte* size and
makes the increment block byte-identical to the original:

    u32 m = 1; int i; u32 v = g_0214DEC0[1];
    for (i = 0; i < 8; i++, m <<= 1)
        if (!(v & m)) { g_0214DEC0[1] |= m; return i; }
    return -1;

compiles to 72 bytes with `+0004..+0010` and `+002C..+003C` matching
byte for byte (`add r0,r0,#1` / `cmp r0,#8` / `lsl r3,r3,#1` / `blt`), so the
ONLY residue is the five-instruction predicated arm
(ldreq/ldreq/orreq/streq/bxeq vs `bne` + the block).  Separately, this spelling
keeps `ldr r1, [pc, #0x24]` + `ldr r2, [r1, #4]` exactly as the original does,
i.e. the volatile second read is preserved (drop the volatile and the reload is
CSE'd into `v`).  (My own run of the cached-local spelling printed the site as
`~ +0040 ABS32 g_0214DEC0 [wildcard]` rather than `literal x30`; that is a
pool-position artefact of the 4-byte-shorter predicated body - the word lands at
+0040 instead of the original's +0044 and never lines up for comparison - not a
missing witness, so a byte-perfect body would be EXACT here.)
