WHAT THE FUNCTION DOES

f->unk84 (typed here as `struct GlyphDir *d`) is a resource-embedded table
with three *offsets*, not pointers: d->tableOff, d->hashOff and d->recOff are
u32 values added to `d` itself to get each sub-table's address (the packed
resource keeps everything self-relative).  d[0..2] (the struct's own first
three bytes) are the three "common" glyph classes.

  - A 2-bit-per-glyph table at d+d->tableOff classifies glyph `v`: index
    v>>2, 2-bit field at (6 - (v&3)*2) counting from the top of the byte.
    0..2 selects d->direct[kind] directly; 3 means "uncommon", fall through.
  - The uncommon case hashes v into 9 bits: `(v & 0x1FF) ^ (bit << 3)`,
    where `bit` is the XOR-parity of bits 9..12 of v, then masks the result
    back to 9 bits.  A signed byte table at d+d->hashOff is indexed by that
    hash.  A non-negative entry is the glyph value directly.
  - A negative entry n means "skip -(n+1) variable-length records before the
    matching chain starts."  The record table at d+d->recOff is a run of
    variable-length records, each a length byte followed by that many
    3-byte entries (2-byte big-endian glyph code, 1-byte value); skip
    len*3+1 bytes per record to advance the cursor.  Once positioned, scan
    the chain's entries for one whose 2-byte code equals v and return its
    value byte; falling off the end (or an empty record) falls back to
    f->unk58[6] (== f->unk5E, the same fallback byte func_0201DD58 returns,
    docs/notes not needed there, it's already EXACT in unit_0201DD58.c).

WHAT IS LEFT: THE FOUR-TERM XOR SCHEDULE

`(v>>9) ^ (v>>10) ^ (v>>11) ^ (v>>12)` (left-associative, the natural way to
write it) does not reproduce the original's register schedule for the parity
bit.  The image computes, in order:

    lsrs r1, r6, #0xa   ; r1 = v>>10
    mov  ip, r1
    lsrs r2, r6, #0xc   ; r2 = v>>12
    lsrs r1, r6, #0xb   ; r1 = v>>11
    eors r1, r2         ; r1 = (v>>11) ^ (v>>12)
    mov  r2, ip         ; r2 = v>>10
    lsrs r7, r6, #9     ; r7 = v>>9
    eors r1, r2         ; r1 = (v>>11)^(v>>12)^(v>>10)
    adds r2, r7, #0
    eors r2, r1         ; r2 = (v>>9) ^ [the above]

i.e. v>>10 is computed and parked first (spilled to ip because r1 is needed
again immediately), then v>>12 and v>>11 are combined, then the parked v>>10
is folded in, and v>>9 is folded in last.  The flat left-associative
expression instead has mwcc compute v>>11 first (into the register that
becomes ip), then v>>9, v>>10 (eors), restore, v>>9 again... in a
still-wrong order (verified: `((v>>9)^(v>>10)^(v>>11)^(v>>12))` gives
11,9,10 for the first three shift amounts against the image's 10,12,11).
Nesting the parens right-associatively as `(v>>9) ^ ((v>>10) ^ ((v>>11) ^
(v>>12)))` does reach the image's grouping of "(v>>11)^(v>>12) combined
first" but changes the *overall function's* register allocation (the
push set moves from {r4,r5,r6,r7} to {r3,r4,r5,r6} and the entry sequence
that was already byte-correct, offsets 0x00-0x30, stops matching), so it
overcorrects.  Introducing named temporaries for the sub-expressions
(`t = v>>10; t ^= (v>>11)^(v>>12); t ^= v>>9;`) has the same
overcorrection: it changes register pressure enough to flip the whole
function's allocation, not just the local schedule.

This needs either the exact source grouping mwcc's scheduler treats as
free (rearranges without touching global allocation) or a companion
technique from a similarly-shaped chain elsewhere in the tree; nothing
tried holds the entry sequence steady while also fixing the shift order.
Whoever picks this up should treat "keep offsets 0x00-0x30 unchanged" as
the constraint to satisfy first before touching the parity expression.

Four spellings the source above does not have, each one needed:

 1. the `v` parameter must be u32, not u16 and not int-from-u16.  A u16
    parameter promotes to SIGNED int and every hash shift compiles `asrs`
    where the original has `lsrs`.  The note's own C already has u32 here,
    which is why its first 0x30 bytes were right.

 2. the hash xor chain's operand order is fixed:
        ((v >> 12) ^ (v >> 11)) ^ (v >> 10) ^ (v >> 9)
    The flat `(v>>9) ^ (v>>10) ^ (v>>11) ^ (v>>12)` above swaps the first two
    `lsrs` (docs/idioms/
    the-accumulator-of-a-commutative-chain-is-its-second-operand.md).

 3. the `& 1` must be an explicit mask and the `<< 3` must go through a u16:
        (u16)(parity & 1) << 3
    folding the two together loses the original's `movs r1,#1 / ands r1,r2`
    and its `lsls #0x10 / lsrs #0xd` pair.

 4. in the chain walk, the decrement must be bound to its own local and
    applied AFTER the pointer advance:
        u8 m = *rec; u16 d = (u16)(n - 1); rec += m + m*2 + 1; n = d;
    The note's `rec += len*3 + 1; n--;` costs an extra `cmp rN,#0` before the
    `bne` (the original's narrowing `lsrs` sets the flags itself).  Writing
    `len*3` rather than `m + m*2` also matters: the original is
    `lsls r2,r4,#1 / adds r2,r4,r2 / adds r2,r2,#1`, a shift-and-add, not a
    multiply.
    And `n` must be initialised BEFORE `rec`; the other order moves
    `ldr r2,[r5,#0xc]` and costs four bytes.
