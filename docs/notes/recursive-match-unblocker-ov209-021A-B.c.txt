Recursive MATCH unblocker, overlay blocker targets in 0x021A0000..0x021BFFFF
=============================================================================

Lane scope: find the unresolved targets named as blockers by src/pending/
files whose target lies in 0x021A0000..0x021BFFFF, match each target (and its
non-SDK deps) bottom-up in the correct region, re-verify the blocked file and
promote it if it turned EXACT.  Every address below is a Black-image address.

Method: every non-twl src/pending file was compiled with `match.py one` using
its own header region/isa/flags, and the per-site report's unresolved
relocation sites were collected.  Across the whole tree only five unresolved
sites name a target in the band.  Everything else in the band that reads
"blocked" is either already carried by `label`/`sole-ref`/`matched` or is a
codegen/ISA DIFF with no unwitnessed relocation, so no target can move it.

Target 0x021B941C (blocks func_021BE658, ov209) -- RESIDUAL, needs a seed

resolved).  The +011E site to func_021B940C resolves `label x2` from ov210.

0x021B941C is 0x10 bytes into func_021B940C in ov133: it is the
`strb r0,[r2]; adds r2,#1; subs r1,#1; bne loc_021B9418` body of the 12-byte

carries no code label in ANY of the ten overlapping overlays (ov016, ov021,

holds 0x021B941D either (checked match.evidence().pool_words).  So `label`,
`sole-ref/code`, `literal` and `matched` all refuse; a region hint does not
help (tested `thumb ov133` on the symbols line, still unresolved).

FIX (outside this lane's write set): seed 0x021B941C as a Thumb `func_` start
in ov133 (layout/function_starts.txt).  With the seed, the symbols line

Target 0x021B6200 (blocks ov218_func_021BA0B0, ov218) -- RESIDUAL
-----------------------------------------------------------------
Callers ov213 (0x021B994E, 0x021B9B66, 0x021B9DB8) and ov218 (0x021BA1DE)
pass one argument in r0 (`adds r0,r5,#0; bl 0x021B6200`).

0x021B6200 is an interior code address in every one of the sixteen overlays
whose window holds it (ov016, ov017, ov021, ov067, ov070, ov071, ov090, ov093,
ov098, ov101, ov133, ov172, ov173, ov174, ov179, ov180).  In particular:
  * ov180: it is the second half of func_021B61FC (`cmp r0,#0; bne; ldr
    r0,=...; bx lr`) -- an EXACT entry at 0x021B61FC but at the wrong address;
  * ov090: it is inside func_021B61FC (matched in ov090), which uses r4 set by
    its own prologue at 0x021B61FE, so a one-arg entry there cannot be right;
  * ov067/ov173: it is `.word` data; ov016/ov021: mid-function.
No `func_` label names 0x021B6200 anywhere (only `pool_021B6200` in ov070) and
no pool word holds 0x021B6201, so every class refuses.

The blocked file is DIFF on codegen independently (144 compiled vs 136
original, 103 bytes differ, shared-tail placement), so even a witness would
not promote it.  Its other one-time-unlabelled targets now resolve
(0x02024004 and 0x021B9C88 as `matched`).

Targets 0x021B821C / 0x021B8234 (block func_021B7F38, ov180) -- RESIDUAL
-----------------------------------------------------------------------
Both are `data` (a two-entry 0x18-byte record table).  In ov180
in_overlay_data() is True but _overlay_start_attested() is False for both:
disasm emits the pair as one `.word` run whose only start is 0x021B821C, and
the only pool referrer of either address is the one inside func_021B7F38
itself (0x021B8008 / 0x021B800C, sites +00D0/+00D4), so the sole-ref/data
demand that a start be carried from OUTSIDE the compared range fails.
0x021B8234 is data in four overlays (ov067, ov105, ov173, ov180) so a hint
cannot choose one; 0x021B821C is now an EXACT ov021 entry (a different object
-- the ov180 table's only referrer is the ov180 pool word).  func_021B7F38 is
DIFF (148 bytes, loop scaffolding) so it cannot promote regardless.

Targets 0x021A4568 / 0x021A458C (block ov009_func_02189780, ov009) -- RESIDUAL
-----------------------------------------------------------------------------
Both are the `RECV...` GSIDebug format strings, declared `data`.  They are in
data section only in ov009 (ov021 is the other window), but neither is a
listing object START (they sit inside the 0x021A44C8... printable run) and the
only pool referrer of each is inside func_02189780 (0x0218997C / 0x02189984),
so sole-ref/data refuses.

Notably `attest_sole_ref_overlay_self()` DOES accept both when handed the
original site: the ov009 ROM word at 0x0218997C/0x02189984 already names
0x021A4568/0x021A458C, so the correct class is sole-ref/self.  It fails only
because the function is 4 bytes short (520 compiled vs 524 original) at the
GSIDebug raw-dump call, which shifts the compiled pool site four bytes early
and makes the self word check miss.  This is therefore a codegen blocker
first, evidence second; the file stays DIFF.
