THE PIN IS REAL AND IT IS NOT THE PROBLEM.  Under dsi/1.1p1 the two literal
zero arguments CSE into a hoisted `mov r4, #0` reused as `mov r1, r4` at both
call sites, which widens the frame to `push {r3, r4, r5, lr}` and shifts p from
r4 to r5: 43 concrete bytes out.  Under ../2.0/sp2 the literals are
rematerialised, the frame is the image's bare `push {r4, lr}`, p lands in r4 and
EVERY INSTRUCTION THE COMPILE EMITS IS THE IMAGE'S, IN THE IMAGE'S ORDER.  The
compile is simply one instruction (four bytes) SHORT.  So this is the same
kept-constants pin the rest of the cluster takes (docs/FRONTEND-PINS.md,
docs/families/cluster_020726D0.h), correctly applied, with a second and
independent residue underneath it.

THE RESIDUE, DIAGNOSED.  The permuter's --explain names it exactly:

    register substitutions (image -> compiled), by count:
      r1   -> r2    x2
      r2   -> r1    x1

i.e. ONE SWAPPED PAIR, not a reshuffle.  The image spills the second argument
out of r1 into r2 before the guard and then tests the copy (`cmp r2, #0`); the
compiler leaves n in r1, uses r1 itself as the guard's `ldrb` scratch, and
tests r1 afterwards -- which is legal only because it reloads nothing, and
which is exactly four bytes cheaper.  Per
docs/idioms/cmp-operand-order-names-the-temporary.md and the "guard scratch
register is the arity" finding in docs/notes/pkt_02072EA8.c.txt, a copy like
this normally means the value is live across something that clobbers r1 -- a
FORWARDED ARGUMENT.  That reading was tested and does not hold here (below).
