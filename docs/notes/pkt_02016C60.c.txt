WHAT THE FUNCTION IS.  `func_02016C60(struct McssWork *w, struct McssTask *t)`
(the prototype docs/families/mcss.h already carried, confirmed by the two
call sites in func_020163C4 / func_02016630).  It is a 4-bit-per-pixel
BLOCK STAMPER over the cell bitmap:

  * guard: `w->fb0` (+0xb0, inside the 0x9c..0xc0 nested object) must be 3.
  * `scale = _d2s(pow(2.0, _s32_to_double(w->fa8 + 2)))` -- the row stride
    in bytes.  The three calls are the runtime soft-float triple that
    src/matched/func_0202B154.c spells the same way:
        _s32_to_double   0x0209B750  arm   (runtime_arm9.txt)
        func_0209AB80    0x0209AB80  arm   (the LINKER VENEER to
                                            0x020979BC, the MSL double
                                            kernel; declare the extern AT
                                            the veneer per
                                            docs/idioms/a-veneer-call-is-an-
                                            ordinary-extern-at-the-veneer-
                                            address.md)
        _d2s             0x0209C508  arm
    The constant handed to the kernel is `2.0` (r0=0, r1 = 1<<0x1e), so the
    C is `func_0209AB80(2.0, _s32_to_double(w->fa8 + 2))`: a power of two,
    4/8/16/32/... -- a bytes-per-row for a 2-pixels-per-byte bitmap.
  * `base = ((u8 **)t->f00)[5]` -- the byte array everything indexes.
  * outer loop `k` over `w->f2c[0]` records of stride 0x30, UNSIGNED
    (`cmp r1,#0 / bhi`, and `cmp r1,r3 / bhs` at the back edge), which is
    what makes the `while ((u32)k < (u32)w->f2c[0])` form necessary -- see
    the first finding below.
  * PER RECORD, TWICE OVER.  The same 8-loop block-stamp runs once on
    (w=f14>>12, h=f18>>12, sx=f1c>>12, sy=f20>>12) and, if f2c != 0, again
    on (w2=f2c>>12, h2=(f30>>12)<<1, sx2=f34>>12, sy2=f38>>12).  The >>12
    everywhere says these are the family's 12-bit fixed-point values
    (MCSS_FX_ONE).  `h2`'s extra <<1 is in the image at 0x02016E48.
  * `step = ((w->f140 << 4) >> 0x1c) + 1` -- the block size, from the
    4-bit field at bits 28..31 of the flag word docs/families/mcss.h
    adjudicates.  Same extraction func_02016880 and func_020163C4 use.
  * inside: tile the (w x h) area in step x step blocks, clipped at the
    right and bottom edge; for each block, SCAN for the first non-zero
    nibble, then WRITE that nibble into every cell of the block.  Two
    nested loop pairs per block, one scanning, one writing.

FOUR THINGS THE BYTES SETTLE, worth keeping whatever happens next:

 1. THE OUTER LOOP MUST BE A TOP-TESTED `while`, NOT A GUARD + do-while.
    Written `if (count == 0) return; do { ... } while (...);` the compiler
    TAIL-MERGES the first guard (`w->fb0 != 3`) into the second one's
    `b` to the epilogue and emits a 2-byte `bne` where the original has the
    4-byte `beq +2 / b far` pair at 0x02016C6E.  The whole function then
    sits 2 bytes out of phase and 568 concrete bytes differ.  With the
    `while` form the top is byte-identical.  This is the third entry of
    docs/idioms/guards-separated-by-statements-share-an-exit-only-through-
    goto.md's decision procedure seen from the other side: `goto done;`
    does NOT prevent the merge here, only the loop's own shape does.

 2. THE ADDRESS ARITHMETIC IS SIGNED `t / 2`, NOT A SHIFT PAIR.
    The image's `lsrs r0,r5,#0x1f / adds r0,r5,r0 / asrs r5,r0,#1` is the
    signed-divide-by-two idiom.  Written literally as
    `(t + ((u32)t >> 31)) >> 1` the `(u32)` makes the whole sum unsigned
    and the last shift comes out `lsrs`, not `asrs`.  `t / 2` on a signed
    `t` reproduces all three instructions.

 3. THE BYTE LOAD MUST NOT BE BOUND TO A LOCAL.  `b = base[addr];` then
    two uses of `b` schedules the `ldrb` before the `tst`; writing
    `base[addr]` at each use puts it where the image has it.  This is the
    mutation tools/permuter.py named as `expand(b x2)` on its first hill
    run (622 bytes-out for its own version of it; applied by hand to the
    readable source it took 662 -> 573).

 4. THE TWO NIBBLE TESTS ARE SPELLED ON DIFFERENT VALUES.  The SCAN loop
    tests the inner LOOP COUNTER (`tst r5, r3`, r3 = c) and the WRITE loop
    tests the SUMMED INDEX (`tst r1, r5`, r1 = sx + x + c).  They are
    numerically equal only when `sx + x` is even; the image spells them
    differently and so must the C.

RESIDUE: 109 of 870 bytes, all of it allocation.  88 diff lines, of which
80 are a stack-slot number and 8 are the `mov rN, ip` copy landing one
instruction late:

    +00FA    mov r5, ip                | adds r5, r1, r0
