Three things in that spelling are shape rather than semantics.  Each was
measured against a variant differing only in one qualifier or one
declaration, and each moves the function 4 bytes or more:

 1. `u32 * volatile unk00` - the table pointer.  Without `volatile` mwcc
    common-subexpresses the two arms' `ldr rX, [r0]` into one load and hoists
    it into the block ending in `bne` (the word arm then starts with
    `mov r0, r5` at +0x20 instead of +0x24, and the record arm reuses the
    hoisted register instead of loading its own).  A volatile field load
    cannot be CSE'd, so each arm reloads; the emitted instruction is an
    ordinary `ldr` either way.  Effect: 88 bytes (right) versus 76.

    The tell that the original did NOT share the load is structural: the
    pre-branch block is `ldr r0,=g ; ldr r1,[r0,#8] ; cmp ; bne` and each arm
    has its own `ldr`, so the two loads are four bytes apart in the layout
    but in different blocks.  No non-volatile spelling of the two arms found
    in fifteen variants kept them apart: `g.unk00` read as `u32`, as `u32 *`, as
    `char **`, a union member with both names at +0x00, a non-volatile field
    with a named `tbl` local, and both arms reading the field through
    separate locals all CSE to one hoisted load.

 2. `volatile u32 end` in the extent type - the high word of the 8-byte
    record.  Without it mwcc merges the record's two field loads into
    `ldm r2, {r1, r2}` (4 bytes short, and it re-tiles the low word onto the
    materialised address).  This is the same `ldm`/`stm` merge the earlier
    revision of this note hit from the `struct ArcRecord *r = base + a1;`
    form; making the second field a volatile lvalue is what stops it, because
    a volatile access is not mergeable.  Effect: 88 bytes versus 84.

 3. `u32 *tbl` bound before the record pointer - purely a register-allocation
    lever.  With the pointer expression inlined into the subscript
    (`(struct ArcRecord *)g_02146A68.unk00 + id`, and the same with
    `rec[id].start` / `rec[id].end`, and the `u32 range[2]`-style array form)
    the record arm comes out as

        ldr r1, [r0]              /* table into r1, not r3 */
        add r2, r1, r4, lsl #3    /* address into r2, not r1 */
        ldr r1, [r2] / ldr r2, [r2, #4]
        sub r2, r2, r1

    i.e. every register off by one slot, 88 bytes and still DIFF.  Binding the
    loaded table to a named `u32 *tbl` first makes mwcc keep the table in r3
    and the address in r1, and the low word is then re-tiled off r3 as
    `ldr r1, [r3, r4, lsl #3]` - the original's exact four-instruction record
    arm.  This is the same "declaration order / naming decides the register"
    family as docs/idioms/declaration-order-decides-which-register-a-local-gets.md.

Also tried and rejected for the record arm, grouped by how far each got:

  (a) with only the GLOBAL volatile (each 84 bytes, i.e. one instruction short
      and still merged: the two field loads become `ldm r2, {r1, r2}`) -
      `rec->start` plus `rec->end - rec->start` as one expression; a `void *end`
      field; the same arm with the pointer as `u8 *` and explicit `id * 8` byte
      arithmetic; the fields read through `*(u32 *)((u8 *)rec + 4)`.

  (b) with the volatile `end` field as well (each 88 bytes: size right, but the
      record arm's registers or addressing are off, and match.py still says
      DIFF) - the inline expression form; `u32 end` / `u32 start` locals in
      both orders; the three-local `end`, `start`, `size` form;
      `u32 end = rec->end;` with `rec->start` left inline;
      `rec[id].start` / `rec[id].end` subscripts;
      `(u32)rec->end - rec->start`; the volatile cast
      `*(volatile u32 *)&rec->end - rec->start` over a plain record type; and
      `*(&rec->end) - *(&rec->start)`.  All of these need the `tbl` binding of
      item 3 to become EXACT.

  (c) `volatile` on the LOW word instead (`struct ArcRecord { volatile u32
      start; u32 end; }`) is wrong in the other direction: the volatile low
      load can no longer be re-tiled off the table register and the function
      is 92 bytes.  A pointer-to-volatile record type hits the same wall at
      92 bytes.

The parameter-register question from the earlier revision ("the original holds
a0 in r5 and a1 in r4, every compile here holds them the other way round") is
not an allocator constant: it flips with the shape above, and the closing
spelling reproduces `mov r5, r0 ; mov r4, r1` for free.

What did NOT change it, for the record: the struct-vs-u32 type of the global,
the position of the arms, the presence of a third parameter, and the
declaration order of the two locals inside the arm.

Three details that cost a compile each:

  - local declaration order is stack order with the LATER declaration at the
    LOWER address (docs/idioms/local-declaration-order-is-stack-order.md):
    declaring `info` before `range` puts `info` at sp+0x10 instead of sp+8 and
    the six-byte read's address is wrong for the rest of the function;
  - `off += tmp;` must be written BEFORE the seek that follows it in the
    original's instruction stream; with the seek written first, mwcc emits the
    call before the load of `tmp` and the two swap four instructions;
  - the final seek's argument needs the grouping `base + (off + 8 + range[0])`.
    Left-associative `base + off + 8 + range[0]` binds `base + off` first and
    the record arm's `add r3, r5, #8 ; add r1, r3, r1 ; add r1, r8, r1` comes
    out as a chain off r8 instead.

`tmp` is one local used by both reads: a 2-byte read into a zeroed u32 (so the
top half is clear) and later a 4-byte read, which is why the slot is
`str r4, [sp, #4]` zeroed at entry and why the compiler keeps a zero register
(r4) alive for the FS_SeekFile origin arguments.

Both functions are byte-identical to the image; there is no MATCH-capped
residue and nothing to park in src/pending/.
