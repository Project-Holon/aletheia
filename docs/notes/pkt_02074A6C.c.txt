==============================================

Solved here (filed in src/matched/):

  func_02074F3C 0x02074F3C  108 bytes EXACT

The 0x02074F3C / 0x02074FA8 / 0x02075014 / 0x02075080 family, the one lever that
mattered.  All four are the same body over a different function pointer from
their own pool:

    u32 f(u32 a, u32 b, u32 c) {
        u32 sz;
        u32 r = func_0207466C(a);
        if (r == 0) {
            if (c == 0) sz = 0;
            else sz = func_020742FC();
            r = func_02074E9C(a, <pool target>, sz, a, b);
            if (c != 0 && r != 0) func_02074694(a, r);
        }
        return r;
    }

Two spellings were wrong and each cost real time:

  * `u32 sz = 0; if (c != 0) sz = func_020742FC();` leaves the zero store
    UNPREDICATED (one byte of encoding: `mov r2, #0` instead of `moveq r2, #0`,
    and the branch moves).  The if/else spelling
    `if (c == 0) sz = 0; else sz = func_020742FC();`
    is what produces the original's `moveq r2, #0` in the then-arm slot.
  * `if (r != 0) return r; ...` (flat early return) allocates a/b/c to
    r6/r4/r5 and tests the callee's r0 in place; the original tests a
    materialised value (`movs r4, r0; bne`), which only happens when the
    zero case is written as the nested `if (r == 0) { ... }` block above.
    Declaration order inside the block matters too: the flat version with the
    locals swapped still came out 4 bytes long.

func_02075014 stays MATCH: its fifth site is a pool word naming 0x02075274, and
that address appears in exactly one literal pool in the image (its own), so the
`literal` class has no witness.  0x0207524C, the same kind of pool word in
func_02074F3C, does resolve (`literal x2`), so the family is not uniformly
blocked.

Still open, all four near misses of the same shape:

  func_02074A6C 0x02074A6C  44 bytes, compiled 48, every site resolved
  func_02074A98 0x02074A98  44 bytes, compiled 48, every site resolved
  func_02074AC4 0x02074AC4  36 bytes, compiled 40, every site resolved

All three are `return func_0207xxxx(a, b, c, 1, 0) == 0/nothing` wrappers.  The
extra instruction is the small constants: the original materialises 1 and 0 with
`mov r3, #1` / `mov ip, #0` as call-argument scratch and then rebuilds the
boolean from immediates (`cmp r0, #0` / `moveq r0, #1` / `movne r0, #0`), while
this front end keeps the same two constants live in callee-saved r4/r5 across
the call (`mov r5, #1` in the prologue, `movne r5, r4; mov r0, r5` after it),
which also forces an extra push/pop pair.  Enumerated and all rejected:

  return X == 0;                      `!X`                       X ? 0 : 1;
  if (X == 0) return 1; return 0;      int r = X; return r == 0;
  (X == 0) ? 1 : 0;                    u32 d = 0, e = 1; X(e, d)

Every spelling gives the same 4-byte-long, constant-shared form.  This is the
same failure mode as docs/idioms/a-small-constant-is-rematerialised-off-a-zero-
register-unless-an-argument-shares-it.md, seen from the other side: here the
argument /does/ share it and the original did not.  Recorded rather than ground
further, -O4,p is pinned and no source shape reached the original.

WALL (small-constant pooling, the known one).  All three wrappers
(0x02074A6C, 0x02074A98, 0x02074AC4) share it: the fourth argument 1 and the
fifth 0 are pooled into two callee-saved registers at the top (`push {r3, r4,
r5, lr}`) where the image materialises them at the call (`mov r3, #1` /
`mov ip, #0; str ip, [sp]`, `push {r3, lr}`).  Same for the boolean result,
which the compiler also computes out of the pooled pair.  This is
docs/idioms/a-repeated-small-constant-takes-a-callee-saved-register.md;
`== 0`, `!x`, a ternary, `(u32)` casts, a named result local and an early
return were all measured.
