1. TOOLING GAP (blocks a whole class, 41 call sites in this band)
-------------------------------------------------------------------------------

A ARM `bl` whose target is a `layout/symbols_sdk.json` address cannot be
resolved.  match.py refuses with:

    ISA conflict for func_02082EA4 at 02082EA4: the source declares arm, the
    image says thumb (layout/symbols_sdk.json).  Fix the symbols: block
    (address from name); refusing to resolve the call at +0044.

The image is right and the tool is wrong: 0x02082EA4 sits inside MI_CpuCopy
(0x02082E24, size 752, `thumb: false`) and the site's own word is
`0xEBFC920E`, an ARM BL (cond 1110, 1011), not a BLX.

Cause: `sdk_addresses()` is defined twice in tools/match.py (line 1161 and
line 1329).  The second definition wins and returns `{addr: (name, thumb)}`,
a tuple, while its only caller `isa_evidence()` (line 1524) does

    th = sdk_addresses().get(addr)
    if th is not None:
        return ("thumb" if th else "arm"), "layout/symbols_sdk.json"

A non-empty tuple is always truthy, so **every** address in
symbols_sdk.json is reported as thumb.  The first definition
(`out.setdefault(e["address"], bool(e["thumb"]))`) is the shape the caller
expects.

Consequence: any source that declares an SDK-catalogued ARM9 target as
`arm` is refused before it compiles, and declaring it `thumb` would make the
harness write BLX where the image holds BL, i.e. a guaranteed DIFF.  A
workaround exists only for tail calls, which go through an ABS32 pool word
and so never reach the branch check -- that is why src/matched/func_021665E4.c
(`func_02082EA4(g_021AA80C, a, 6);`) compiles EXACT while a normal
`func_02082EA4(dst, src, n);` call cannot.

Census over the 626 not-yet-matched ARM functions of 129 bytes and up:
  - 103 of them (16.5%) contain a direct `bl` to an ARM9 address that
    isa_evidence() mis-reads as thumb because sdk_addresses() catalogues it
    (41 sites; MI_CpuCopy at 0x02082EA4 is 30 of them);
  - a further 77 sites point at ARM9 `loc_` labels with no func_ label and
    no SDK entry: those resolve (no conflict, note "no image evidence for the
    ISA") but then have no independent witness, so they cap at MATCH.

Parked source: scratch/ov009/o60/func_0215E620.blocked.c -- a clean 152-byte
ring-buffer consumer, EXACT except for two `func_02082EA4` calls.  Move it
into src/matched/ once the isa_evidence()/sdk_addresses() mismatch is fixed.

2. func_0215F5B4 @ 0x0215F5B4 -- DIFF, instruction multiset identical
-------------------------------------------------------------------------------

132 bytes.  Byte-swaps the u16 at +2 and the u32 at +4 of a packet header
and forwards them (plus three untouched arguments and the fourth) to
func_0215E024.  Every instruction is reproduced; 23 bytes differ because
MWCC scheduled `lsl ip, r7, #0x10` (the (u16) conversion of the swapped
halfword) four slots earlier than the image, rotating the rest of the
block.  Same registers, same opcodes, one instruction transposed.

The image places the conversion at +0058, immediately before
`orr r4, r5, r4` (which frees r5); the build places it at +0048, right after
`orr r7, r7, ip` frees ip.  Declaring v16 `u16` and converting at the
assignment gives the build's order; declaring it `unsigned int` and writing
`(u16)v16` at the call site makes the compiler drop the conversion entirely
(128 bytes).  Next spelling to try: read the two words through a
`struct { u16 pad; u16 h; u32 w; } *` so the loads are typed member accesses.
Source kept at scratch/ov009/o60/func_0215F5B4.diff.c.

Re-measured after the sdk_addresses() fix: still 132 bytes, still exactly 23
bytes out, still the single transposed `lsl ip, r7, #0x10`.  Eight further
spellings were compiled and all landed on 23 (or worse): struct-member loads
(`struct { u16 pad; u16 h; u32 w; } *`), operand order swapped in both ORR
chains, `unsigned int` holding the computed value with `(u16)` at the call
(128 bytes -- the cast is dropped because the value is provably 16-bit),
`short`/`int` for the halfword, `#define` byte-swap macros, and computing
v16/v32 through an `unsigned int` temporary.  The one spelling that reaches
exactly 132 bytes and matches every other instruction is in
src/matched/func_0215F714.c-adjacent scratch file
scratch/ov009/o60/v_b.c (`u16 v16;` assigned at the assignment, then passed
uncast).  Residue is a pure list-scheduler tie-break: both `and r4,r4,#0xff`
and `lsl ip,r7,#0x10` are ready after `orr r7,r7,ip` and the image picks the
AND first.  No source-level lever found; park as a scheduler wall.

6. What actually paid on this band (measured, 12 EXACT in ~79 compiles)
-------------------------------------------------------------------------------

- Read the whole body, then write it: ten of the twelve closed on the first or
  second compile.  func_02180334 needed six (all variations of the loop
  bound), func_02183E50 five, func_02195158 thirteen (it never closed), and
  the three 136-to-156-byte functions that did close with one compile each
  were the ones whose body was a straight-line store list or a single loop.
- **Local declaration order is a first-class lever, not a style choice.**
  MWCC hands out the low callee-saved registers in declaration order, so
  swapping two `int` locals can flip 4 to 8 bytes of a function that is
  otherwise instruction-for-instruction correct.  Measured twice on this
  band: func_0215D7FC went from 6 bytes out to EXACT purely by declaring
  `old` before `t`; func_02183EE0 matched 30 of its 34 instructions only
  after `int i;` was declared before `int n = 0;`.  When a diff shows only
  two register names exchanged across a long run of instructions, swap the
  declarations before touching the expressions.
- `if (f(x) == 0) return 0; return 1;` is NOT the same build as
  `return f(x) != 0;`.  The two-return form if-converts to
  `moveq r0, #0` / `movne r0, #1` -- zero first -- which is the image's order
  in func_02183E50; the `!= 0` form emits `movne` first and is 2 bytes out.
  `return f(x) ? 1 : 0;` and `!!f(x)` are 4 bytes out.  When a function ends
  on a boolean return, always try the two-return spelling.
- When a call's result must survive the next statement because r0 is about to
  be used as a load destination, the register-colouring tie shows up as a
  one-instruction difference.  If the image has an extra `mov rX, r0` right
  after a call, the callee's result is being kept in a named local.
- Check whether the callee's incoming r0/r1 are still intact at a `blx`:
  if they are, the hook really is called with the caller's own parameters,
  and writing `hook()` with no arguments costs 30+ bytes of scratch-register
  colouring.  This alone took func_02195158 from 45 bytes out to 7.
- `ldrb` vs `ldrsb` is the single most common 2-to-6 byte residue.  Whenever
  the image has `ldrb`, the pointer expression must be `unsigned char *` --
  both the loop bound in func_02180334 and the continuation bytes in
  func_0218022C needed a cast, and each cast alone flipped 2 and 6 bytes.
- `x + 1 > n` is NOT interchangeable with `x >= n` at this compiler: writing
  `max + 1 > n` inline in the loop condition (letting MWCC hoist it) is what
  produced the image's `add sl, r3, #1` before the loop and fixed the whole
  register permutation of func_02180334 (32 bytes -> 2).  Do not introduce a
  `lim = x + 1` local; MWCC folds it back and the registers scramble again.
- A shared-key pattern: three near misses (0215C814, 02195158, 0215D898) are
  all at 2-to-12 bytes and all of them are if-conversion or register-colouring
  coin flips with every opcode already right.  Expect roughly one such
  near-miss per three closed functions on this band.

3. Idioms that paid, measured on this band
-------------------------------------------------------------------------------

- `unsigned char` (not `char`) for a local byte buffer: the image loads
  `ldrb` and then shifts with `asr`.  With `char` the build emits `ldrsb` and
  the six bytes of the three loads differ (func_0217F824).
- A "skip trailing zeros" loop reproduces only with the two tests in the
  image's order, `while (a[n-1] == 0 && n != 0)`, even though `n != 0` is
  the safe order; the entry `b`-to-test plus body-before-test rotation
  follows from it (func_0217D448).
- Unsigned comparison: `lo`/`hi` in the image means the *parameter* is
  unsigned.  Two `int` lengths gave `lt`/`gt` on the length compare and cost
  four bytes (func_0217D448).
- When an `if`/`else` pair comes out with its blocks inverted (`bge` where
  the image has `blt` and the two bodies swapped), rewriting it as
  `if (success) {...} else/fallthrough-not-found` -- success first in source
  order -- is what fixes it (func_0215E23C).
