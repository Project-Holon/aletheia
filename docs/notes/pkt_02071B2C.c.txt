   Everything reproduces, including `mov r4, #0` and the first `mov r0, r4`.
   The single residue is the very last call: the original rematerialises
   `mov r0, #0`, ours reuses the pooled r4 (`mov r0, r4`) - 4 concrete bytes,

   docs/idioms/a-repeated-small-constant-takes-a-callee-saved-register.md.
   Tried and rejected (all give `mov r0, r4`): declaring either call's
   parameter `void *` and passing `(void *)0`, both as pointers, the head as a
   pointer with the tail as u32, and the tail call spelled `0u`.
   Note 0x020731E0, 0x02073D7C and 0x02075858 have no witness outside this
   range, so this function is also MATCH-capped on three sites regardless.

2. func_02072320 0x02072320 84 bytes, compiled 68, no relocations at all

     o->f0  = 0x1000;
     o->f14 = 0x1000;

     (b) `-i->f2e * -i->f28` is folded to `i->f2e * i->f28` and both `rsb`
         instructions vanish; the original keeps them
         (`rsb r2, ip, #0` / `rsb r1, r1, #0`).  Declaring f28 or f2e `u16`
         vs `s32` changes nothing here.
   The sibling leaves 0x02071C14 (128) and 0x0207229C (132) are the same
   family with `smull` 64-bit scaling plus a `sub #0x1000` bias, and were not

--- 0x0207229C: DIFF (132 bytes original against 128 compiled, 0 relocations)

The smull family member the earlier section left unreduced.  The C is:

    typedef unsigned short u16;
    typedef int            s32;
    typedef long long      s64;

    struct S { u8 pad_00[0x18]; s32 f18; s32 f1c; s32 f20; s32 f24; s32 f28;
               u16 f2c; u16 f2e; };
    struct D { s32 f00; s32 f04; u8 pad_08[8]; s32 f10; s32 f14;
               u8 pad_18[0x18]; s32 f30; s32 f34; };

    void func_0207229C(struct D *d, struct S *s)
    {
        d->f00 = s->f18;
        d->f14 = s->f1c;
        d->f04 = 0;
        d->f30 = (s->f2c * -(s32)((s64)s->f24 * s->f18 >> 12)) << 4;
        d->f34 = (-s->f2e * ((s32)(s->f1c + ((s64)(-s->f28) * s->f1c >> 12))
                              - 0x1000)) << 4;
        d->f10 = 0;
    }

Settled by the bytes: the first three stores are `d->f00`, `d->f14`, `d->f04`
in that order with the two zeros sharing one `mov r2, #0`; both products are
`s64` (`smull`, and `umull` comes out the moment the struct fields are u32 -
the sign has to come from the field type, not a cast); the `>> 12` is a
logical 64-bit shift folded to `lsr #0xc` + `orr ..., lsl #20`, which is what
mwcc emits for `s64 >> 12` when only the low word is live; `f2c`/`f2e` load
with `ldrh` and feed a 32-bit `mul`; both results shift left by 4.

Residue, 4 bytes: the scheduler places the second statement's operand loads
(`ldr ip, [r1, #0x1c]` and the negated `f28`) *before* the `str r3, [r0,
#0x30]` that belongs to the first, so the original re-reads `s->f1c` after
that store (`ldr r1, [r1, #0x1c]`) - two loads where the compiled version
needs one, 33 instructions against 32.  The compiled `adds r1, r4, r1` also
carries flags the original's `add r1, r1, r4` does not.  Tried: u64 against
s64 (umull/smull, settled), `(u64)-(s32)f28` (which forces an extra
`asr #0x1f` + `mla` sign-extension pair and is wrong), u32 against s32
fields, and `* 16` against `<< 4`.  No locals were added: the original's
plan uses only r0-r4 + ip/lr, so a spill would show.

    struct SRC { u8 pad_00[0x18]; s32 f18; s32 f1c; u8 pad_20[4];
                 s32 f24; s32 f28; u16 f2c; volatile u16 f2e; };
    struct DST { s32 f00; s32 f04; u8 pad_08[8]; s32 f10; s32 f14;
                 u8 pad_18[0x18]; s32 f30; s32 f34; };

    void func_02071C14(struct DST *d, struct SRC *s)
    {
        s32 a, b;
        s32 e;
        s32 g;

        d->f00 = s->f18;
        d->f14 = s->f1c;
        d->f04 = 0;

        e = (s32)s->f2e;
        g = s->f28;
        a = ((0 - (s32)s->f2c) << 11) - (s->f24 * (s32)s->f2c);
        d->f30 = (s32)(((s64)s->f18 * a) >> 8) + ((s32)s->f2c << 15);

        b = (g * e) + ((0 - e) << 11);
        d->f34 = (s32)(((s64)b * s->f1c) >> 8) + ((s32)s->f2e << 15);

        d->f10 = 0;
    }

This is the `>> 8` / `<< 15` variant of the family (pkt_02071DD4's L2), not the
`>> 12` one: the shift pair is `lsr #8` + `orr ..., lsl #24` and the bias term
is `field << 15`, added LAST in both statements.

FOUR levers paid, in the order they did, all measured from 84 bytes out:

 L-A  f2e IS `volatile`, AND its first use is bound to a local `e`.  The image
      reads f2e TWICE -- `ldrh r2, [r1, #0x2e]` at 0x02071C38, shared by the
      `mul` and the `rsb`, and `ldrh r1, [r1, #0x2e]` at 0x02071C7C for the
      `<< 15` alone.  Plain (non-volatile) f2e CSEs the two into one load and
      is 124 bytes, 4 short; plain `volatile` with no local gives THREE loads
      (the `rsb` gets its own) and is 132, 4 long.  volatile + `e` is 128.
      84 -> 79 out.
 L-B  HOIST f2e's READ ABOVE THE f30 BLOCK.  `e = (s32)s->f2e;` written before
      the `a` statement is what puts the first f2e load at +0x24, between the
      f24 load and the first `mul`, and spends the callee-saved registers the
      image spends.  79 -> 45 out (39 under the pin).
 L-C  HOIST f28's READ TOO, into its own local `g`.  The image's
      `ldr r6, [r1, #0x28]` sits at 0x02071C50, BEFORE the f30 store, which is
      what makes the push a three-register `{r4, r5, r6, lr}`.  Assigning `g`
      either beside `e` or immediately before the `d->f30` statement gives the
      same answer.  39 -> 15 out.
 L-D  THE SECOND smull's OPERAND ORDER IS `b * s->f1c`, not `s->f1c * b`
      (pkt_02071DD4's L1, the commutative-64-bit tell).  15 -> 13 out.
