WALLS (in-lane chains that cannot close)
----------------------------------------
* **0x020120B4 -> 0x0201240C -> 0x02012444** was the lane's best chain and it
  broke at the first link.  0x020120B4's original is a *real* call with a frame
  (`push {r3, lr}` / `ldr r0, [r0, #8]` / `blx` / `pop {r3, pc}`, 10 bytes) where
  mwccarm 1.1p1 turns the same one-statement body into a Thumb tail call (12
  bytes, `ldr r3, [pc]; bx r3`).  The packet note's five spellings are joined by
  nine more this pass - a variadic callee, a no-prototype callee, an explicit
  `return;`, a `u64`-returning callee, a `char`-returning callee, a struct local,
  a `(void)v` use, and the field read through a second pointer - and all fourteen
  give the same 12-byte tail call.  0x0201240C and 0x02012444 nevertheless
  graduated: their sites to 0x020120B4 resolve through the `label` class (there
  is an outside branch at 0x020120C8), so this wall cost the lane nothing.
* **0x02010DF4 and 0x02010DCC, the rotated loop.**  docs/notes/pkt_02010DB4.c.txt
  documents 21 spellings; thirteen more were tried here (the goto loop with an
  explicit peeled test, `for (;;) { if (i >= 13) break; ... }`, the break after
  the call, the `continue` guard, `while (13 > i)`, an `unsigned char` counter,
  `int i` initialised at its declaration, the `s64`/`u32` bound forms).  The
  closest remains the note's 1-byte residue: `for (i = 0; i < 13; i++) { if (i >=
  13) break; f(i); }` reproduces 31 of the original's 32 bytes and differs only
  in the back edge (`blt` to the body in the original, to the top test here).
  The `continue` spelling (`if (i >= 13) continue;`) gets 4 bytes.  Nothing
  reached a two-test loop.  0x02010DB4 therefore stays parked.
* **0x020111BC**, 34 bytes: two independent residues, full write-up in
  docs/notes/func_020111BC.c.txt (guard registers and the 64-bit-to-32-bit
  return copy).  It is *not* an attestation problem - all four sites resolve.
* **0x0200F234**, the packet pkt_0200F17C switch: the dispatch, the 7-entry jump
  table and all five arms reproduce byte for byte, but the original loads each
  small argument out of the literal pool (`ldr r0, [pc, #imm]`) where every C
  spelling gives `movs r0, #imm`, and the pool carries a seventh word (0x0E) that
  no instruction loads.  Full write-up in docs/notes/func_0200F234.c.txt.
* **0x0200F17C**, 0x02010AC4 and 0x02010C34 are band members by their *leading
  code* only: 22, 30 and 62 bytes of code, but their extents run to 184, 212 and
  356 bytes (jump tables with the case bodies laid out after them).  The band
  size column is the first code run, not the function.  0x0200F17C is already
  written up (docs/notes/pkt_0200F17C.c.txt, 86 sites).  0x02010AC4 and
  0x02010C34 are switches on a field (`ldr r0, [r4, r5]` with r5 = 0x1d4, and
  `ldr r0, [r5]` with the state advanced inside an arm) and were not attempted;
  the next pass should treat them as their true extent, not as 30 and 62 bytes.

ARTIFACTS (not functions, not counted)
--------------------------------------
Six of the lane's 73 entries are linker veneers of the `ldr pc, [pc, #-4]` form
(one instruction plus the pointer word the load uses), 8 bytes each:

| address | pointer word | target |
| --- | --- | --- |
| `0x020053E4` | 0x020053E8 | 0x0273154C |
| `0x02005420` | 0x02005424 | 0x027315D0 |
| `0x02005428` | 0x0200542C | 0x027314F0 |
| `0x02005454` | 0x02005458 | 0x027315C0 |
| `0x02005B6C` | 0x02005B70 | 0x02704364 |
| `0x02006D3C` | 0x02006D40 | 0x027047C0 |

They carry `func_` labels in the generated listings (the `.global func_020053E4`
/ `ldr pc, pool_020053E8` pattern in asm/arm9/src/000_02004000.s, and the same
in 004_02010BB8.s), which is why the band screen classified them as ready rather
than as artifacts - the artifact class in scratch/brief_band_0_64.md is written
for the `ldr ip, [pc]; bx ip` shape.  No C spelling produces them, so they are
recorded here and filed nowhere: the brief's rule ("do not attempt them and do
not count them") applies to the whole family.

Two of them cost the lane two MATCH entries: 0x020053EC's sites to 0x02005420
and 0x02005428, and 0x02005440's site to 0x02005454, cannot resolve through the
`veneer` class even in principle, because rule 4 of attest_veneer() wants the
veneer's pointer word to name code inside a region and all six pointers land in
0x0270_xxxx / 0x0273_xxxx, which no region in layout/layout.json covers
(`match.veneer_at()` returns None for every one of the six; checked directly).
The other four (0x020053E4, 0x02005454, 0x02005B6C, 0x02006D3C) *do* attest as
`label x1` from outside the caller's range, which is why 0x020053EC's first
site resolves and its two veneer sites do not.
