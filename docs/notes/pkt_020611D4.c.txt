0x020611D4 (80 bytes, arm9, ARM, packet pkt_020611D4, lane r2b-2).  The
function is a linked-list search that splices the found node out.  It has NO
relocation at all (every offset is an immediate), so there is no evidence
question: the only thing between it and a manifest entry is the shape of the
search loop.

  020611E8  cmp  r2, r1

  020611F0  cmpne r3, #0                ;   if (not found) test p
  020611F4  bne  #0x20611E4             ;   if (not found && p) loop
  020611F8  cmp  r3, #0
  020611FC  moveq r0, #0
  02061200  bxeq lr

  02061208  str  r1, [r0, #0x24]
  0206120C  ldr  r1, [r3, #8]
  02061210  str  r1, [r0, #0x28]
  02061214  ldr  r1, [r3, #0xc]
  02061218  str  r1, [r0, #0x2c]
  0206121C  mov  r0, #1
  02061220  bx   lr

The loop body is if-converted: the update (`p = p->f0c`) and the loop test
are both predicated on "not found", and the back edge is the only branch.  A
`break` out of the loop cannot produce that - the found case has to leave
through the SAME block as the p == 0 case, and the found case is written as
a conditional ASSIGNMENT, not as a branch out.

NEVER THE SAME BLOCK TWICE

Every spelling below reproduces the guard (`cmp r1,#0` / `cmpne r3,#0` /
`beq`), the epilogue and the splice byte for byte; only the loop block
differs, and it differs the same way each time - a real conditional branch
on the found test plus an unpredicated update, six instructions instead of
five, 4 bytes long, so every offset after it shifts:

  +0010  ldr r2, [r3]          | ldr  r2, [r3]
  +0014  cmp r2, r1            | cmp  r2, r1
  +0018  ldrne r3, [r3, #0xc]  | beq  <found>        <- extra branch
  +001C  cmpne r3, #0          | ldr  r3, [r3, #0xc]
  +0020  bne  <loop>           | cmp  r3, #0
                               | bne  <loop>

THE LEVER THAT CLOSED func_0206164C, and the one it does NOT close
-------------------------------------------------------------------------------

docs/notes/pkt_0206164C.c.txt recorded a 10-byte residue on the two 60-byte
mirrors and swept NINE declaration orders against it, correctly concluding
that "declaration order moves the residue but never removes it".  That is
true and the conclusion drawn from it -- "the pointer-to-lr preference is an
allocator decision" -- is what made the row look closed.  It is not an
allocator decision.  The lever is WHERE THE FIRST ZERO IS MATERIALISED:

    image:      mov r3, #0          <- i owns the literal
                ...
                mov lr, r3          <- j is a COPY of it

`int i; int j = 0; for (i = 0; ...)` gives the two `mov`s the other way round
in every declaration order, because both zeros are independent literals and
the allocator is free to pick which one is materialised first.  Writing

    int i = 0;
    ... ;
    int j = i;          /* not `= 0` */
    for (; i < 5; i++)  /* empty init clause */

makes `j` textually depend on `i`, so `i` necessarily owns the literal, and the
file is EXACT.  Both mirrors closed this way.

THE SECOND HALF OF THE LEVER is declaration order, and the two mirrors disagree
about it even though they are written from one template:

    func_0206164C (save):     i, t, j     -> t in ip, j in lr     EXACT

Using either order in the other function is 10 or 15 bytes out.  So the earlier
note's declaration-order sweep WAS finding a real signal; it was just swept
against the wrong baseline, since with `j = 0` no order can be right.

func_020614D4 (0x020614D4, 348 bytes + 28 bytes of pool = 376 extent) -- OPEN
-------------------------------------------------------------------------------

Newly attempted in this lane; no previous note exists for it.  Reached
size-exact at 348 on the first compile and 258 concrete bytes out after the

WHAT IT IS.  The multi-cell renderer's OTHER allocator, over the descriptor
bank rather than over the flat arena: `size` is rounded up to 16 bytes (zero
meaning 16) and refused at or above 0x7FFF0, then

  * `which != 0` walks the TWO-entry table at 0x020A8158.  For each live
    descriptor with room, it dispatches on that descriptor's halfword kind at
    +0x10 (`ldrh r5, [lr, #0x10]`, cases 0 and 3 against a null default) to
    pick a SECOND descriptor -- g_020A819C for kind 0, g_020A8184 for kind 3 --
    and requires the second to have room for HALF the request (`cmp r5, r3,
    lsr #1`).  On success it bumps the first descriptor's +0x00 by the full
    size and the second's by half, and returns the first's base plus the old
    cursor.  This is a PAIRED ALLOCATION: a main block and a half-size
    companion, which is what a 4bpp/8bpp character-plus-attribute pair looks
    like.
  * `which == 0` walks the FIVE-entry table at 0x020A8150 and allocates
    downward from +0x04, one descriptor, no companion.
  * the result is packed exactly like func_020616CC's, plus the `which` bit:
    `orr r0, r0, r1, lsl #31` puts the table selector in bit 31.

STRUCTURAL FACTS ALREADY PINNED by the byte comparison (these are worth keeping
even though the function is open, because they took the pass):

  1. +0x10 is a HALFWORD (`ldrh`), not a word.  Declared `u32` the dispatch
     compiles as `lsl #0x10 / lsrs #0x10`, four extra instructions.
  2. The two second-stage descriptors are hoisted OUT of the loop: the image
     loads g_020A8184 into r8 and g_020A819C into sb BEFORE the loop head at
     0x02061514, alongside the table pointer in r0.  Reading them inside the
     arms costs two pool loads per iteration.
  3. The null default arm's pointer is the LOOP COUNTER'S ZERO (`mov ip, r7`
     where r7 was set by `mov r7, r4` from the counter's `mov r4, #0`), the
     same derive-the-second-zero-from-the-first shape as func_0206164C above.
  4. Both success paths assign the ok flag BEFORE the stores (`mov r0, #1` at
     0x02061580 precedes the two `str`s), not after.

branches to three separate one-instruction blocks:

    cmp   r5, #3
    beq   02061554          -> mov ip, r8 ; b 02061560

Every spelling compiled here instead predicates the select (`moveq lr, r6 /
beq / mov lr, r5 / cmp / movne lr, r2`), which is shorter and reshuffles every
