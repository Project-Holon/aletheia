Levers this run added to the last wave's list
---------------------------------------------

1. A `void` return is what keeps a loop-carried value in r0.  func_0204E388
   tail-stores `func_02045A98()` and never copies r0, so the only local the
   loop carries is the counter; declaring the function `u16`-returning makes
   the last converted unit live across the loop and adds a callee-saved `sb`
   to the frame (136 -> 140 bytes and 71 concrete bytes wrong).
2. `u8 ch = *p; p++;` beats `u8 ch = *p++;` when the loop test already loaded
   the same byte: the post-increment form emits its own `ldrb r0,[r6],#1` and
   loses the `and r0,r0,#0xff` that reuses the test's `ldrsb` (four bytes).
3. `(ch << 8) + *p` and `(ch << 8) | *p` differ by one byte (`add` against
   `orr`) and are otherwise identical output: when the diff is a single
   instruction in the third byte, check the operator before anything else.
4. A signed loop counter against an `unsigned` index is what produces the
   SINGLE `popls` guard plus a `blo` back-edge (func_0204BD94).  Writing the
   obvious `if (count <= 0) return;` in front of the `for` emits both `pople`
   and `popls` -- two predicated epilogues, four bytes of layout.
5. Multiple `return 1` exits must all be `goto` to one label at the end
   (func_02036A50): plain `return`s predicate each one inline and the frame
   shifts by 25 bytes.  This is the same lever as last wave's, confirmed on a
   second function.
6. A boolean argument computed from a call compiles to `movs r3,#1; cmp r0,#0;
   bne L; mov r3,r7` -- the value must be passed as an EXPRESSION
   (`func(...) != 0` straight into the argument), never through a named local:
   a local gets a stack slot and adds `sub sp, #8`, which shifts the whole
   frame (func_0200B2A4, 170 -> 162 bytes).
