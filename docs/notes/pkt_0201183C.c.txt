WHAT THE FUNCTION IS.  A fixed-point-to-float record unpacker, the sibling
of src/pending/func_02011B8C.c in the same packet and the same soft-float
family as src/matched/func_0202BFF0.c.  It allocates one flat float buffer
sized from the record's three optional channel arrays, hands the buffer to
func_0204944C to be filled, then walks it converting every float back to
4.12 fixed point into up to three Vec3 arrays hanging off the record.

  s->f14 = q >> 12                 saved at entry, stored again at exit
  n   = func_0209C2B0(s->f0c, 0)   element count
  tot = 8 + 0xc*n  per SET flag of s->f30 / s->f2c / s->f28
  k   = 0 + 0xc*s->f18 per the SAME three flags (f18 re-read each time)
  f   = func_02030734((u16)((s->f00 & 0x7fff) | 0x8000), k, 0,
                      &data_020A7270)
  func_0204944C(s->f04, s->f08, tot, k)
  for (i = 0; i < s->f18; i++)
      per SET flag, three channels into s->f24[i] / s->f20[i] / s->f1c[i]
  func_020307B0(f);  s->f14 = q >> 12;

THE POOL, read from asm/arm9/src/004_02010B80.s (pool_02011B7C..B88):
  0x000002BD  0x00007FFF  0x020A7270  0x45800000
0x45800000 is 4096.0f and it is held in r7 across the whole loop;
0x020A7270 is the heap handle passed as func_02030734's FOURTH argument
(it is NOT zero -- passing 0 costs the pool word and a relocation site);
0x00007FFF is the tag mask; 0x000002BD is the 0x8000-or'd tag constant the
`ands r1, r0 / adds r0, r0, #1 / orrs r0, r1` triple builds.

THE CONVERSION IDIOM, which is the whole body of the nine repeated blocks:
      x > 0 ? 0.5f - x * 4096.0f : x * 4096.0f + 0.5f
spelled `(s32)(...)` so the tail is `blx _f2s`.  Note the ASYMMETRY: the
positive arm is `_fsub(0.5f, product)` (r0 = 0.5f, r1 = product) and the
negative arm is `_fadd(product, 0.5f)`.  That is what the bytes say at
0x020118EA..0x02011912 and at all eight repeats; it is not the symmetric
round-half-away-from-zero it looks like, and writing it symmetrically
swaps the operand registers in the `_fsub`.  0.5f is `movs #0x3f /
lsls #0x18`, rematerialised at every one of the nine blocks, never pooled.

LEVERS ALREADY MEASURED AND CONFIRMED (all in the best source below):
  * the record's Vec3 arrays are THREE separate pointers at +0x1c, +0x20,
    +0x24 and the flags gating them are +0x28, +0x2c, +0x30 -- in the
    REVERSE pairing: f30 gates f24, f2c gates f20, f28 gates f1c.  Get the
    pairing wrong and the three blocks' field offsets all shift.
  * `tot` uses `n` (one register, three multiplies) while `k` RE-READS
    s->f18 at each of its three sites.  A shared `s32 cnt = s->f18;` local
    loses the three `ldr r3, [r5, #0x18]` the image keeps.
  * `q >> 12` is computed ONCE at entry into a local and stored to s->f14
    only at the exit.  Storing it at entry as well hoists the whole
    prologue and is 4 bytes long.
  * the struct must have NO field between +0x14 and +0x18 (an earlier
    draft with a spare pointer there put every offset 4 too high and cost
    the entire prologue).

THE 72-BYTE RESIDUE, one decision.  The original's frame is `sub sp, #0x3c`
and the compile's is `sub sp, #0x1c`: 32 bytes, eight stack slots.  The
image gives EACH of the nine conversion blocks its OWN stack slot for the
byte offset it computes -- sp+0x18, 0x1c, 0x20, 0x24, 0x28, 0x2c, 0x30,
0x34, 0x38 -- via `lsls r0, r6, #2 / str r0, [sp, #N]`, and then RE-LOADS
both the offset and the float from it inside each arm:

  0201193A  lsls r0, r6, #2        ; offset
  0201193C  str  r0, [sp, #0x1c]   ; its own slot
  0201193E  ldr  r0, [r4, r0]      ; the float, for the compare
  02011942  blx  _fcmp
  02011946  bls  ...
  02011948  ldr  r1, [sp, #0x1c]   ; offset re-loaded
  0201194C  ldr  r1, [r4, r1]      ; float re-loaded, for the multiply

i.e. the float is loaded TWICE per block, once for the compare and once
inside the taken arm, off an offset that is spilled rather than kept live.
1.1p1 -O4,p CSEs the two loads into one and keeps the offset in a register,
which is the 72 bytes and the 32-byte frame both.
