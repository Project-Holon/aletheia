C. Class blockers found (worth a rule in the next brief)
--------------------------------------------------------

1. Only overlay targets whose address has NO independent witness may be
   declared in the symbols: block.  Declaring `func_021F4EC0 0x021F4EC0
   thumb ov135` for a *bl* from inside ov135 was accepted, but every
   name-resolved overlay callee that is not declared defaults to isa=arm
   and match.py then raises
   "ISA conflict for func_X at Y: the source declares arm, the image says
   thumb".  Fix is the region+isa token on the symbols: line - that flipped 5
   sites (func_021F9088, func_021F90A0, func_02201DC0, func_02201DD8,
   func_021F99D0) from ISA refusal to EXACT/EXACT*.

2. Exact reproductions recorded this wave, all with a plain
   `extern void func_XXXXXXXX(void); void f(void){ func_XXXXXXXX(); }`:
   the compiler emits `ldr r3, =T; bx r3` (the pool word written with the odd
   address for a Thumb target, the even one for ARM).  9 pure thunks closed
   this way in one batch (func_021F4894, func_021FC3D0, func_021FD0F4,
   func_02200290, func_02200EC8, func_0220052C, func_021FE254, func_022026BC)
   plus func_021F9254 and func_022026C4's siblings with fixed arguments.  This
   is the cheapest class in the overlay by far and dozens more sites of it are
   still open in ov135.

3. Hardware-register stores written as `*(u16 *)0x04000050 = 0;` reproduce
   exactly (one pool word per distinct address); offsets folded into one
   address (`*(u16 *)(0xADDR + off)`) do not.

4. Tooling gap, not ours: layout/matched/ov010/pkt_02156BCC.json and
   pkt_02156BCC_b.json both define func_02156BCC@0x02156BCC in region ov010,
   which makes load_manifest_entries() raise SystemExit for ANY run whose
   resolution path loads the manifest (seen as
   "manifest shards disagree: func_02156BCC is in both ..." and an empty
   verdict for func_021F8F5C, whose 12 bytes are otherwise reproduced).
   Whoever owns ov010 needs to drop one of the two shards.

A. What paid, in order of yield
-------------------------------

1. NAME-RESOLVED ov135 CALLEES MUST CARRY THE REGION AND ISA TOKEN.  Wave 2
   found this (its note C.1) but did not generalise it far enough: it is not a
   special case for one or two sites, it is the default.  EVERY `bl` from an
   ov135 source to an ov135 address fails with
   "ISA conflict for func_X at Y: the source declares arm, the image says
   thumb" until the callee is declared.  Adding
   `func_021F4EC0  0x021F4EC0  thumb  ov135` to the caller's symbols: block
   flipped 13 sites in this lane in one pass.  The cheap-class table in the
   brief should read: a `bl` to a same-region function is only cheap if you
   declare the callee first.

2. ONE SOURCE SHAPE CLOSES A WHOLE DISPATCH CLASS.  The five state-table
   dispatchers are byte-identical apart from their table word:

       extern void *g_TABLE[];
       void func_X(u8 *p)
       {
           ((void (*)(u8 *))g_TABLE[*(u32 *)(p + 0x28)])(p);
       }

   This closed func_021F51F0, func_021F74E4, func_021FC174, func_021FFEB4 and
   func_02200C80 (20 bytes each, tables 0x02203B0C, 0x02203BBC, 0x02203CF0,
   0x02203E58, 0x02203E94) - all five were open in wave 2's DIFF list as "one
   unsolved shape".  The declared `data ov135` symbol on the table is what
   witnesses the pool word; without it each site caps at MATCH.

3. THE 0x28 STATE-SETTER FAMILY IS A GENERATOR, NOT A LIST.  ov135 holds 79
   functions that write the state word at +0x28; 24 of them are one of three
   skeletons, parameterised only by constants:

     A. callee(p [+ off]); *(u32*)(p+0x28) = S; *(u32*)(p+0xf8c) = 0; return 2;
        8 sites (func_0220163C .. func_02201E1C)
     B. func_021F4BE0(p, a, b, c, d);  *(u32*)(p+0x28) = S; return 2;
        6 sites (func_021F6384 .. func_022007E0); arg3 is a literal-pool word
        (0x1ad, 0x126, 0x16a, 0x12e are all data pointers)
     C. build(p, ...); func_021F4E98(p, X, Y); return 2;
        X = 0x10 for the func_021F7538 group, X = 0x17 for the func_021FF318
        group - the single byte the first attempt got wrong (10 21 against
        17 21), so read that immediate off the listing, do not carry it over.

4. A CALLEE CALLED WITH NO ARGUMENT LEAVES r0 ALIVE.  func_02201C08 is
   `ldr r0, pool(0xf8c); movs r1, #0; str r1, [r4, r0]; blx 0x021C89F0` - the
   BLX carries 0xf8c in r0, not p.  That is not an argument: the callee takes
   none, and MWCC does not reload r0 for a no-argument call.  Declaring
   `extern void func_021C89F0(void)` and calling it bare reproduces the bytes;
   declaring it `(u8 *p)` and passing p costs 5 divergent bytes.  Same reading
   for any blx whose r0 is a pool constant rather than the object pointer.

5. A PRE-INCREMENT, NOT A RELOAD.  func_021FC7E0 / func_021FF0E8 / func_0220090C
   are one source shape three times.  The image is
   `ldr r1,[r4,r0]; adds r1,r1,#1; str r1,[r4,r0]; cmp r1,#0x2d; ble`, i.e.

       if (++*(s32 *)(p + 0xdfc) > 0x2d) { *(s32 *)(p + 0xdfc) = 0; ... }

   Wave 2 read the middle pair as a redundant reload/store and parked it; it is
   a pre-increment, and all three close in one compile.

6. SWITCH, NOT IF/ELSE, WHEN BOTH ARMS BRANCH FORWARD.  Where the image is
   `cmp r1,#1; beq CASE1; cmp r1,#2; beq CASE2; <exit>; CASE1: ...; CASE2: ...`
   the source is a plain `switch` with the exit left as the fall-through
   default (func_02201B18).  Where the image is `cmp r1,#1; bne ATTEMPT2` the
   source is really `if`/`else if` (func_021F5CD4).  Where the image is a
   compare chain in ascending case order with two arms sharing one body, the
   cases were written in that same order (func_021F89B4).

7. A SHARED TAIL IS A SHARED TAIL.  func_021FC668 reproduces as
   `if (k == 1) {...} else if (k == 2) {...}` followed by one
   `func_021FCBF0(p); return 2;` - not as a `switch` and not with the tail
   call inlined into the first arm.  MWCC lays the tail after the second arm
   and has the first arm jump to it.
