Everything is right except the operand order of the final `adds`.  The
original accumulates INTO the register holding the table address (`adds r0,
r0, r2`); the compiled form accumulates into the register holding the scaled
index (`adds r0, r2, r0`).  This is exactly
docs/idioms/commutative-operand-order-names-the-temporary.md, and the usual
fix -- write the other operand second -- does not work here, because writing
`b[(u32)func_020189F0_Table + o]` swaps the WRONG add: it reassociates the
`a + a*4` scaling instead and goes from 1 wrong byte to 5.

WHAT TO TRY NEXT
----------------
The shape the original wants is "table address is the accumulator, index is
the addend".  The two levers not yet tried, both of which would change which
value the compiler treats as the running temporary rather than merely
reordering the text:

  1. Declare the table as a pointer OBJECT rather than an array, e.g.
     `extern const s8 *const func_020189F0_Table_p;` and index
     `func_020189F0_Table_p[o]` -- a pointer load puts the symbol in a
     register as a value, which may make it the natural accumulator.  Note
     this changes the relocation from an ABS32 against the array to one
     against a pointer word, so it must be checked that the site still
     resolves before the byte count means anything.

  2. Give the function a second statement that uses the table address first,
     so it is already live in a register when the add happens.

Neither is obviously right, and the function is 16 bytes, so this is a low
priority: it is recorded here because the EVIDENCE status changed (the table
