Fills out[0..count) with a scaled sample of the shared s16 table at
0x02021B38.  A phase counter starts at 0 and advances by `step` each
iteration, wrapping through 16 bits (the `lsls #0x10` / `lsrs #0x10` pair
at the bottom of the loop).  The table index is phase >> 4 -- an ARITHMETIC
shift, so the phase is signed -- and the table STRIDE IS 4 BYTES, not 2:
the original scales the index by 4 (`lsls r1,r0,#2`) and then reads a
halfword (`ldrsh r0,[r0,r1]`), so the s16 entries sit one per 4-byte slot.
Reading it as a packed s16 array is the single easiest way to lose this
function; it costs 2 bytes at +0x1A and nothing else, so it looks like
noise.

Each sample is multiplied by the s32 amplitude in 64 bit through _ll_mul
(contract r0:r1 * r2:r3 -> r0:r1), then rounded and narrowed twice: the
64-bit splice (`adds` #0x800 / `adcs` the zero pool word / `lsls #0x14` /
`lsrs #0xc` / `orrs`) recovers the low 32 bits of (product + 0x800) >> 12,
and the trailing `asrs #0xc` takes that down to the s16 that is stored.

Four spellings are load-bearing.  Each was isolated against the bytes and
each is worth more than it looks:

  - the phase is s16, not u16.  `asrs r0,r5,#4` at +0x18 is the only
    evidence, and a u16 phase gives `lsrs` there.
  - the table stride is 4: the subscript is `[(phase >> 4) * 2]` on an s16
    array, i.e. every other halfword.  See above.
  - `phase` must be INITIALISED BEFORE `i`, and both must be assigned in
    statements rather than in their declarators.  With declarator
    initialisers, or with `i` assigned first, the two `movs #0` at
    +0x0A/+0x0C swap registers and the whole loop follows -- 15 differing
    bytes instead of 8.  Declaration order alone does not do it; it is the
    order of the two assignment STATEMENTS that pins r5 to phase.  This is
    the same lever as docs/idioms/assign-the-loop-counter-before-the-loop-
    bound-or-zero-costs-a-pool-word.md, pointing the other way.
  - the loop is a pre-tested `while (i < count)`, not a `do/while` behind
    an `if (count == 0) return;` guard.  Both compile to the same 92
    bytes, but the guard form emits `beq` at +0x10 where the original has
    `bls`.  One byte, and it is the only tell.

Where the diff lives: 8 bytes across +0x18..+0x24, which is the index
computation and the two spill reloads feeding _ll_mul.  The original uses
r0/r1 there (`asrs r0` / `lsls r1` / `ldr r0` / `ldrsh r0` / `ldr r2` /
`ldr r3` / `asrs r1`), mwcc uses r2/r3 for the index pair and r0/r1 for
the reloads -- the operand pair handed to _ll_mul is swapped end for end.
Everything else is identical, including the whole rounding splice, the
`strh`, the phase wrap and both loop edges.

  - the multiply operand order, both ways, with and without a named local

  - hoisting the amplitude into an s64 local before the loop, and
    declaring the parameter itself s64: much worse (28 and 31), so the
    sign-extension really does happen at the call site inside the loop.
  - dropping the `(s64)` cast on the table operand: 15, so both operands
    are explicitly widened.

BLOCKER, separate from the diff: the ABS32 pool word at +0x54 names the
table at 0x02021B38 and has no witness outside this range.  Evidence class
`literal` -- the word appears in no other literal pool in the image, and
being plain data it can never be label-, veneer- or matched-attested.  So
even a byte-exact version of this function would cap at MATCH rather than
EXACT until something else in the image loads the same table address, or
the data region is decompiled.  Worth knowing before spending budget on
the remaining 8 bytes: closing them buys a park, not a shard entry.
