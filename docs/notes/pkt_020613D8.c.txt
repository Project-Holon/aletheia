pkt_020613D8 - DIFF residues for the two multi-cell renderer rows (lane 5, 0-64 byte band)
=========================================================================================

Neither of these two rows is one of the band's 0-64 byte targets: they are the
packet's two larger functions (0x020613D8, 116 bytes, and 0x02061460, 108
bytes), left in src/pending/ as DIFF by an earlier wave.  Rule 2 of the band
brief keeps DIFF sources out of src/pending/ and in the packet's note, so lane
5 moved them here verbatim; their own headers carry the residue write-ups.

  func_020613D8 - DIFF, 8 bytes: the compiler cross-jumps the two calls'
    identical two-instruction tails (`str ip, [sp]; bl func_02061390`) into one
    shared block where the original keeps both copies (128 compiled against
    136).  Arm bodies, argument registers and the branch are otherwise
    byte-identical.
  func_02061460 - DIFF, 6 bytes (3 instructions): the register holding the
    zero.  The original materialises the loop counter's zero first (`mov r5,
    #0`) and derives the flag store's zero from it (`mov lr, r5`, ...); this
    compiler materialises the loop's zero into lr first and gives the counter a
    second `mov r5, #0`.  Sixty-four type/guard/compare spellings and ten
    statement shapes were compiled; the best is six bytes.

The packet's own 0-64 byte rows are func_0206164C and func_0206168C (60 bytes
each, DIFF, 10 concrete bytes of register assignment -- see
docs/notes/pkt_0206164C.c.txt) and func_020616CC (308 bytes, still open, the

VERDICT: DIFF, 276 compiled against 316 in the image (a 40-byte shortfall, 213
concrete bytes), CLOSED for this budget -- the residue is register allocation
and address rematerialisation, not source shape.  Do not re-derive as-is.

WHAT IT IS
A bump allocation step against the {cur, end} pair at 0x02146B74 (the same
global src/matched/func_02061808.c exposes as struct Pair02061808).  `size` is
rounded up to eight bytes, zero meaning eight; `dir == 1` allocates off `cur`,
any other value off `end`; `flag` picks the alignment the pad is derived from
(16-byte when clear, 8-byte when set).  The packed result is the allocated
offset over eight in the low halfword and the rounded size over eight in the
high halfword, or zero when the arena cannot satisfy the request.

THE RESIDUE, both sites
The original push is `{r4, lr}` with `off` in r4 and `ok`/`cur` sharing lr;
the compile needs `{r3, r4, r5, lr}` because it keeps the address of
0x02146B74 in lr for the whole body and spends r5 on `off`.  The original
instead re-materialises the address from the pool six times (0x020616FC,
0x02061724, 0x02061754, 0x02061778, 0x02061798, 0x020617C4) against a single
ABS32 at 0x02061804, which is what leaves it a register short of the compile.
Both spellings of the field access were tried (an inline `g_02146B74.cur` read
per use and a named `cur` local): each reproduces the arithmetic exactly and
neither changes the address strategy.  The second site is the `flag` test in
the `dir == 1` arm, where the original predicates the 16-byte pad arm
(`andeq/rsbeq/andeq` then `beq`) and falls through the 8-byte one, while the
compile predicates the 8-byte arm instead; swapping the source polarity does
not move it.

typedef unsigned int   u32;

    u32 end;
};

u32 func_020616CC(u32 size, u32 flag, u32 dir)
{
    u32 n;
    u32 off;
    u32 len;
    u32 addr = 0;
    u32 ok = 0;

    if (size == 0)
        n = 8;
    else
        n = (size + 7) & ~7u;
    if (n >= 0x7fff8u)
        return 0;

    if (dir == 1) {
        u32 cur = g_02146B74.cur;

        if (flag == 0)
            off = (16 - (cur & 0xf)) & 0xf;
        else
            off = (8 - (cur & 7)) & 7;
        len = n + off;
        if (g_02146B74.end - cur < len) {
            ok = 0;
        } else if (flag != 0 && cur + len >= 0x10000u) {
            ok = 0;
        } else {
            addr = cur + off;
            g_02146B74.cur += len;
            ok = 1;
        }
    } else {
        u32 end = g_02146B74.end;

        if (end < n) {
            ok = 0;
        } else {
            if (flag != 0)
                off = (end - n) & 7;
            else
                off = (end - n) & 0xf;
            len = n + off;
            if (end - g_02146B74.cur < len) {
                ok = 0;

                ok = 0;
            } else {
                addr = end - len;
                g_02146B74.end = addr;
                ok = 1;

The residue is sharper than the note above records, and one line in it is
wrong: dsi/1.1p1 does not "predicate the 8-byte arm instead" -- it predicates
BOTH arms and emits no branch at all.  With the else-half of the function
deleted, the whole dir==1 half reproduces the original instruction for
instruction, same registers, same push {r4, lr}, except for that one block.

WALL 1 -- the pad if/else in the dir == 1 arm (4 bytes)

  ORIGINAL 02061700..02061724
    cmp   r1, #0
    ldr   lr, [r2]          ; cur
    andeq r2, lr, #0xf     \
    rsbeq r2, r2, #0x10     } if (flag == 0) off = (16 - (cur & 0xF)) & 0xF;
    andeq r4, r2, #0xf     /
    beq   02061724          <- branch over the else arm
    and   r2, lr, #7       \
    rsb   r2, r2, #8        } else off = (8 - (cur & 7)) & 7;   NOT predicated
    and   r4, r2, #7       /

  Every spelling tried produces instead
    andeq r2,lr,#0xf / rsbeq r2,r2,#0x10 / andeq r4,r2,#0xf
    andne r2,lr,#7   / rsbne r2,r2,#8    / andne r4,r2,#7      (no beq).

  Ruled out by compile, all two-armed-predicated: if/else and `? :` in both
  polarities and both source orders; one and two statements per arm; a shared
  temp local in both arms; `off = B; if (!flag) off = A;` and the mirror;
  do{}while(0); while/break; comma operator; a leading null statement; the
  shared statement `len = n + off` written in both arms; switch with case
  0/default; `flag == 0 && (off = A) || (off = B)`.
  `else if (flag != 0)`, `else { if (1) ... }` and `else { if (flag) ... }` do
  produce the beq, but then give the else arm its own `cmp` and a `ne`
  predication -- the original's else has neither a compare nor a predicate.
  An inline `goto` past the else is folded away before if-conversion.  A
  twelve-instruction micro test of the plain if/else also predicated both
  arms, so this is not a register-pressure artefact of the surrounding body.

WALL 2 -- pool-address hoisting, only when BOTH halves are present

  The original re-materialises the address of 0x02146B74 six times, each load
  scheduled at its use; the address is never live across a block.  As soon as
  the C contains the else-half, the compiler CSEs that pool load to entry as
  `ldr lr, [pc]` at +0x20, inside the `if (n >= 0x7FFF8) return 0;` sequence,
  and keeps it live for the whole function: push becomes {r3,r4,r5,lr}, ok is
  pushed onto r1 and off onto r5.  That single decision is the size difference
  and ~200 of the differing bytes.  Ruled out: volatile struct (288 bytes,
  still hoisted), a named cur/end local per half, no named local at all,
  two-statement arms.

  With only the dir == 1 half in the file the hoist never happens and the
  register plan matches the original exactly, which is what pins the trigger to
  the presence of the second, structurally disjoint half.
