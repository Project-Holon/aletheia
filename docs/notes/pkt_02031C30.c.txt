What the two spots are:

**case 4's `if (q->a == q->b)` arm.**  The original does not if-convert it:
`beq 0x02031D78` sends the equal path to an out-of-line block
(0x02031D78 `add r0, r2, #1` feeding 0x02031C78 `strb r0, [r5, #0x1e]`, i.e.
the state++ store shared with case 0's tail), and the rest of the arm stays
inline.  Every spelling tried if-converts it instead (`addeq r0, r2, #1` +
`strbeq` + `beq`), which is the same three instructions but laid out inline,
and that layout then shifts everything after it by 4 bytes:

  * `if (q->a == q->b) { p->state++; break; }` -> predicated (addeq/strbeq/beq)
  * the same with `return 0` instead of `break` -> predicated `moveq r0, #0` +
    `popeq`
  * `if (q->a != q->b) { body } else { p->state++; break; }` + a trailing
    `p->state++; break;` -> the arm is a real branch, but the extra tail block
    makes the two epilogues land 4 bytes late

**case 1's fall-through.**  The original branches to 0x02031D74, which is
case 4's tail `b 0x2031C70` - one shared branch instruction for both arms'
`p->state++; break;`.  The closest C emits its own `b #0x2031c70` instead, so
the two arms do not share the tail.  Both spots are block-merge decisions, not
wrong expressions: the moment case 4's arm goes out of line (0x02031D78), the
shared tail at 0x02031D74 appears and case 1's branch should pick it up.

Levers that did land, worth keeping:

  * The dispatch value must be read once into a local before the switch
    (`ldrb r2, [r5, #0x1e]` then `cmp r2, #5; addls pc, pc, r2, lsl #2`).
  * Every arm that ends "state++ and return 0" must `break` and share the one
    `return 0` after the switch, or the epilogue is duplicated per arm.
  * The `cmpne`-fused test (`movs rN, r0; cmpne rN, #1; beq`) is what
    `if (r != 0 && r != 1)` gives; the positive `if (r == 0 || r == 1)`
    spelling is folded to an unsigned range test (`cmp r6, #1; bhi`) and is
    wrong.  All four `func_02032CD0` result tests must be written negated.
  * The 4th/5th arms' shared block `if (tmp == 1) p->state++;` is written out

  * Argument order matters for which object each call gets: func_02032CD0 and
    func_020331A4 take the FIRST parameter in cases 3 and 5 and the SECOND in
