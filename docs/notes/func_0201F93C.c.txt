The one residue
---------------

The compile is 144 bytes against the image's 148, and the difference is
entirely how the fifth (halfword, stack-passed) parameter is allocated:

  original                              every compile
  push {r3, r4, r5, r6, r7, lr}         push {r4, r5, r6, r7, lr}
  sub sp, #8                            sub sp, #0xc
  r5 = desc, r6 = b, r7 = c             r6 = desc, r7 = b
  d spilled to [sp+4]                   c spilled to [sp+4], d to [sp+8]
  heap rematerialised three times,      heap loaded once, `ldr r5,[sp,#0x20]`
  `add r0,sp,#0x20; ldrh r0,[r0]`,      as a word, kept in r5 for all uses
  with one of the three kept in r5
  across two consumers

That is: the original refuses to cache a stack-passed parameter in a
callee-saved register and reloads it at each use, spending one register
fewer and therefore one spill slot fewer; mwccarm caches it and spills the
third register parameter instead.  The four missing bytes are exactly the
extra `sub sp` word plus the saved `adds`/`str` around the second spill.

What was tried, and what it produced
------------------------------------

  * `u16 heap` parameter, used directly at all three sites: one `ldr`
    (word) load into r5.  This is the shape above.
  * `u32 heap` parameter with an explicit `(u16)heap` at each site: the
    narrowing appears, but as `lsls #0x10 / lsrs #0x10` off the cached r5,
    not as a reload; strictly further away (the same cast that *is* the
    answer for 0x020371D8, see the idiom note, is the wrong answer here
    because the value already lives in a register).
  * callee prototypes retyped so every consumer takes `u16`: no change,
    still one cached word load.
  * a local `u16 h = heap;` feeding the two calls while the alloc and the
    halfword store use `heap` directly, both with `h` assigned after the
    struct copy and before the allocator call: CSE'd back into one load
    both times.
  * reordering the +0x2f / +0x30 / +0x34 stores: moves two bytes, does not
    touch the allocation.
  * `volatile u16 heap` as a *diagnostic only* (not a candidate answer): it
    does reproduce the prologue exactly, `push {r3, r4, r5, r6, r7, lr}` /
    `sub sp, #8`, which confirms the residue is only the caching decision.
    But it then keeps `add r5, sp, #0x20` (the *address*) live and reloads
    `ldrh r0,[r5]` at every use, where the original recomputes the address
    each time and caches one of the three *values* in r5.  So volatile is
    both unshippable here and still not byte-identical.

Classification
--------------

By docs/idioms/a-materialised-shift-temporary-is-not-reachable-from-c-or-

*allocator* decision, reachable through nothing in the documented flag
matrix.  No flag sweep was run here, because that matrix is already closed
project-wide.
