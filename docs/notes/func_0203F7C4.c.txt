func_0203F7C4 @ 0x0203F7C4, packet pkt_0203F7C4, family gf_standard.c (ARM).
Untouched before wave 5; this is the first write-up.

DIFF at 128 concrete bytes out of 304, right size, right control flow, right
call sequence, right stack layout, every constant and every relocation right.
The residue is entirely inside one block: the 2D cross product between the
second VEC_Subtract and VEC_Normalize.

WHAT IT IS
----------
The SIGNED perpendicular distance from a point C to the line through A and B,
in 20.12 fixed point, with the sign taken from which side of AB the point
falls on.  Six plain-integer coordinates arrive and are shifted into 20.12 on
entry; the last two come off the stack at sp+0x58 and sp+0x5c, which is what
fixes the arity at six.

    a = (ax<<12, ay<<12, 0)      at sp+0x30
    b = (bx<<12, by<<12, 0)      at sp+0x24
    c = (cx<<12, cy<<12, 0)      at sp+0x00
    a = a - c                    VEC_Subtract(&a, &c, &a)
    b = b - c                    VEC_Subtract(&b, &c, &b)
    d = (a.y, a.x, 0)            at sp+0x18   NOTE: no negation, see below
    f.z = a.x*b.y - b.x*a.y      the 2D cross, both products 20.12 rounded
    cross = f.z + 0
    VEC_Normalize(&d, &d)
    f = b - a                    VEC_Subtract(&b, &a, &f)   at sp+0x0c
    dist = VEC_DotProduct(&d, &f) >> 12
    if (dist < 0) dist = -dist
    if (cross <= 0) { sign = -1; dist = dist * sign; }
    return dist

Three readings that are NOT obvious and are pinned by the bytes:

  * `d = (a.y, a.x, 0)` really has NO sign flip.  A perpendicular would be
    (a.y, -a.x, 0) or (-a.y, a.x, 0); the original stores the two loads
    straight through (`ldr r0,[sp,#0x34]; str r0,[sp,#0x18]` and
    `ldr r0,[sp,#0x30]; str r0,[sp,#0x1c]`) with no rsb anywhere.  The sign
    is recovered afterwards from the cross product instead, which is why the
    tail takes the absolute value and then re-signs it.
  * the vector at sp+0x0c is written TWICE: first (0, 0, cross) field by
    field, then wholesale by VEC_Subtract(&b, &a, &f), which discards it.
    The first three stores are dead and are in the source anyway -- they are
    emitted, so they are written.  Only `cross` survives the overwrite, in a
    register.
  * the final negation is a MULTIPLY, not an rsb:
        mvnle r1, #0        ; r1 = -1
        mulle r1, r0, r1
        movle r0, r1
    Writing `dist = -dist` gives `rsble r0, r0, #0` and is eight bytes short.
    The -1 must be bound to its own local inside the branch and multiplied:
        if (cross <= 0) { sign = -1; dist = dist * sign; }

DECLARATION ORDER, WHICH IS THE WHOLE STACK LAYOUT
---------------------------------------------------
Later declaration sits at the LOWER stack address
(docs/idioms/local-declaration-order-is-stack-order.md), so the address order
c@0x00, f@0x0c, d@0x18, b@0x24, a@0x30 means the source declares

    struct VecFx32 a; struct VecFx32 b; struct VecFx32 d;
    struct VecFx32 f; struct VecFx32 c;

Getting this wrong is a 134-byte diff on its own; with it right, everything
from +0x0000 to +0x0078 (the whole prologue, all six shifts, all nine stores
and BOTH VEC_Subtract calls) is byte-exact.

/* earlier source, no helper, 292 bytes against 304, 145 concrete bytes out, 1.1p1 */

    typedef signed int   s32;

    typedef s32 fx32;

    extern void VEC_Normalize(const struct VecFx32 *a, struct VecFx32 *out);
                                                          /* 0x0207CCA4 */

                               const struct VecFx32 *b);  /* 0x0207CA68 */

    s32 func_0203F7C4(s32 ax, s32 ay, s32 bx, s32 by, s32 cx, s32 cy)

        VEC_Subtract(&b, &c, &b);

VEC_Subtract's direction (a - b into out) was read off 0x0207CA00 itself, not

WHAT IS LEFT: TWELVE BYTES AND THE SCHEDULE OF ONE BLOCK
---------------------------------------------------------
The compile is 292 bytes against 304.  Three instructions are missing, all of
them in the cross-product block, and the original's shape is:

    +0088  ldr r0, [sp, #0x30]      ; a.x, loaded ONCE
    +0094  mov r1, r0               ; <- MISSING: a second value holding a.x
    +0098  ldr r0, [sp, #0x28]      ; b.y
    +00A0  smull r3, r0, r1, r0
    ...
    +00A8  add r2, r7, #0           ; <- MISSING: a live-range split of the
                                    ;    register-resident zero (r7 has held
                                    ;    0 since +0x0010 and is about to be
                                    ;    clobbered by the b.x load)
    +00D4  sub r1, r1, r7           ; the raw difference
    +00E0  add r7, r1, r2           ; <- cross = difference + that zero
    +00E4  str r1, [sp, #0x14]      ; f.z = the RAW difference, not `cross`

So f.z and the compared value are two DIFFERENT values in the original: f.z
gets the bare subtraction and `cross` gets it plus a zero that lives in a
register across the entire function (the same zero as a.z, b.z, c.z, d.z,
f.x and f.y).  Every attempt to say that in C folds the `+ 0` away.

best, from 145.  Read that carefully -- `volatile fx32 cross` buys the twelve
bytes by giving the value a memory home, and a pile of synthetic temporaries
buys a few more, but neither is a plausible source shape and neither converges.
The size is reachable by accident in several ways; the SCHEDULE of the block
(stores of d and f interleaved BEFORE both smulls, in the order f.x, d.x, f.y,
d.y, d.z) is not reachable by any of them.  Every compile hoists the first
smull above the stores, because nothing in C makes the stores depend on it.

THE INLINED HELPER: THE READING THAT ACTUALLY WORKS
----------------------------------------------------
The two shapes above -- a.x needing a SECOND live value, and the difference
needing a second consumer -- are both what an inlined helper with its own
locals produces.  Writing the cross product that way collapses the residue
from 145 bytes out at 292 to 55 bytes out AT THE RIGHT SIZE:

/* best source, 304 bytes against 304, 55 concrete bytes out, 1.1p1 */

    static inline fx32 mulfx(fx32 p, fx32 q)
    {
        return (fx32)(((s64)p * q + 0x800) >> 12);
    }

    static inline fx32 cross2(const struct VecFx32 *p,
                              const struct VecFx32 *q)
    {
        fx32 px = p->x;
        fx32 py = p->y;

        return mulfx(px, q->y) - mulfx(q->x, py);
    }

and in the body, in place of the `cross = 0; cross = cross + (...)` block:

        f.z = cross2(&a, &b);
        cross = f.z + a.z;

`static inline` is load-bearing on both helpers: plain `static` emits two
real calls.  `px`/`py` are the two locals that give a.x and a.y their extra
live values -- `mov r1, r0` at +0x0094 is `px` -- and `cross = f.z + a.z`
supplies the second consumer, a.z being a zero that is already resident.

WHAT IS STILL LEFT: 55 BYTES, +0x00A8..+0x00D4 AND +0x00DC..+0x00E4
--------------------------------------------------------------------
Only the SECOND mulfx and the zero copy, and it is an issue-order
difference, not a register one.  The original interleaves:

    original                         compiled
    add r2, r7, #0                   lsr r7, r1, #0xc
    ldr r7, [sp, #0x24]              adc r0, r0, #0
    ldr r3, [sp, #0x34]              orr r7, r7, r0, lsl #20
    adc r0, r0, #0                   ldr r2, [sp, #0x24]
    smull ip, r3, r7, r3             ldr r1, [sp, #0x34]
    adds r7, ip, #0x800              ldr r0, [sp, #0x38]
    lsr r1, r1, #0xc                 smull r3, r1, r2, r1
    ...                              ...

The original starts the second multiply's two loads BEFORE finishing the
first product's 64-bit normalisation, and parks the register-resident zero
in r2 in the gap that opens up.  Every compile finishes the first product
first and then issues the second, which also makes it load a.z from
sp+0x38 instead of reusing the zero already in a register.

Varying the helper's internal bindings does not move it: binding all four
operands (px, py, qx, qy), binding only qx, and splitting mulfx's product
into a named s64 temporary all give exactly 55 bytes out at 304.  Sourcing
the added zero from c.z instead of a.z also gives exactly 55; from f.x,
d.z, or a `cross = 0` local it drops to 300 bytes and 115 out, and from a
literal `0` to 296 and 110 out -- so `a.z` / `c.z` (a zero read from a
vector the subtract has already written) is the right class of operand.

WHERE A NEXT ATTEMPT SHOULD LOOK
---------------------------------
Not at the declarations, the tail, the store schedule or the first
multiply: all solved and byte-exact.  The open question is one block,
+0x00A8..+0x00E4, and one question about it: what makes the compiler start
the second mulfx's loads before finishing the first one's normalisation.

Two of the obvious levers were tried in this lane and BOTH are dead ends;
do not repeat them.

  * Restructuring cross2's subtraction does nothing.  All four of
        fx32 r1 = mulfx(px, q->y); fx32 r2 = mulfx(q->x, py); return r1 - r2;
        fx32 r2 = mulfx(q->x, py); return mulfx(px, q->y) - r2;
        fx32 r1 = mulfx(px, q->y); return r1 - mulfx(q->x, py);
        return -mulfx(q->x, py) + mulfx(px, q->y);
    give EXACTLY 55 bytes out at 304, identical to the baseline.  The
    commutative-order idiom does not reach this residue: the order the two
    products are created in is already right, it is the INTERLEAVING of the
    second one's loads with the first one's normalisation that is wrong.

  * Running the permuter against a manually inlined copy does not work, and
    the reason is itself the finding: hand-inlining the two helpers is NOT
    the same code.  Writing
        px = a.x; py = a.y;
        f.z = (fx32)(((s64)px * b.y + 0x800) >> 12)
            - (fx32)(((s64)b.x * py + 0x800) >> 12);
    with px/py as ordinary locals of func_0203F7C4 gives 296 bytes and 142
    out -- WORSE than the 292-byte spelling that has no helper at all, and
    far worse than the 304/55 the `static inline` version reaches.  The
    helper's value numbering survives inlining in a way no spelling in the
    caller's own scope reproduces, so there is no equivalent flat source for
    the permuter to chew on.  (This is the mirror image of
    docs/idioms/four-shift-pairs-for-one-offset-are-an-inlined-u16-helper.md:
    there the repeated truncation betrays the helper, here it is the extra
    live value and the issue order.)

Still untried, and now the only avenues left:
  * giving mulfx a third, unused parameter or an extra consumer of its
    64-bit intermediate, to change its inlined value count
  * a cross2 that returns the two products separately (by out-pointer or as
    a small struct) and subtracts them in the caller
  * a differently-shaped mulfx -- an unsigned or u64 intermediate, or the
    rounding add folded into the caller -- since the rounding `+ 0x800` and
    the `>> 12` are what the normalisation sequence is made of
