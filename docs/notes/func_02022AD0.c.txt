Established facts:

  - func_02022D88(ctl, which) returns a pointer into a table whose
    layout is:  s16 x[0xC0] at +0,  s16 y[0xC0] at +0x180,  and a u32
    flag at +0x600.  The 0x300-byte hole between y[] and flag is real:
    the original scales the hoisted 0x180 constant by `lsls #2` to reach
    the flag, so the offset is 0x600 and not the 0x300 a packed struct
    would give.  Getting this wrong costs `lsls #1` and cascades.
  - `s16`, not u16: the accesses are `ldrsh` with a register offset,
    which is the only spelling that exists for a signed halfword load
    (see idioms/ldrsh-register-offset-is-signedness.md).
  - The packed halfword written to the window register is
    `((x << 8) & 0xff00) | (u32)(u8)y`, computed in u32 with NO
    intermediate (u16) cast.  Adding one inserts a spurious
    `lsls #0x10 / lsrs #0x10` pair into all six copies (48 bytes).
  - The VCOUNT compare is signed (`bge`), so `line` is s32.
  - `next = line + 1; if (next > 0xbf) next -= 0xc0;` reproduces the
    original's `cmp #0xbf / ble / subs #0xc0` exactly; a modulo does not.
  - ctl fields: +4 mode (compared against 1), +8 sel (the main/sub
    engine selector).  Each of the three blocks tests flag then sel,
    giving the 2x2 tree that is written out six times in the original
    and which mwccarm cross-jumps back together on its own.

The residue: 8 bytes at +0x00CC..+0x00D6, the SECOND of the three
func_02022D88 blocks (the `mode != 1` path's first call).  The original
emits

    adds r3, r0, #0 ; lsls r5, r5, #1 ; movs r6, #6 ; adds r1, r3, r5

and the compile emits

    movs r6, #6 ; adds r3, r0, #0 ; lsls r5, r5, #1 ; adds r0, r3, r5

i.e. the `movs r6,#6` is hoisted one slot too early and the sum lands in
r0 instead of r1.  Blocks one and three are byte-identical, and they
differ from block two only in that they end in `return` while block two
falls through into block three.  Tried, all held at 8 bytes:

  - reading ctl->sel before / between / after the three array reads in
    block two (block one's order, `sel` first, is confirmed correct by
    its own byte-exactness, and copying it into block two changes
    nothing);
  - reading p->flag first, so the flag load leads the block;
  - binding block two's returned pointer to its own named local, and to
    a nested-scope copy, to lengthen its live range past the merge;
  - hoisting `next * 2` into a scaled local once for all three blocks
    (the original re-derives the scale inside each block, so this is
    wrong in the other direction and costs more).

The lever wanted is whatever makes mwccarm defer the 0x180 constant
materialisation in a block that is NOT terminated by a return.  Both
neighbours prove the C is right; this is one scheduling decision.
