1. unwitnessed callee -- the hard blocker
-----------------------------------------

                                witness outside 02050DB8..02050ED4"

  0x0206168C carries a `func_` label but no branch anywhere in the image
  reaches it from outside this range, it appears in no literal pool, and no
  manifest entry defines it.  0x0206168C lives in packet pkt_020613D8, which
  is NOT this lane's (this lane owns pkt_02050C30, pkt_02062114, ...).  Filing
  the callee is the fix and it is a sibling lane's row; do not reach into it.
  Everything else in the function -- including the other eight sites, which
  resolve [label]/[literal]/[matched] -- is fine.

2. five-instruction register swap in the 16-entry search loop (20 bytes)
------------------------------------------------------------------------
  +00D8  mov r1, #0            | mov r2, #0
  +00DC  ldr r2, [r0]          | ldr r1, [r0]
  +00E0  ldr r0, [r2, r1, lsl #2] | ldr r0, [r1, r2, lsl #2]
  +00E8  streq r4, [r2, r1, lsl #2] | streq r4, [r1, r2, lsl #2]
  +00F0  add r1, r1, #1        | add r2, r2, #1
  +00F4  cmp r1, #0x10         | cmp r2, #0x10

  The original holds the array pointer in r2 and the index in r1; the
  compiler here does the opposite.  The `cmp r0, r5` operand order (element
  on the left) is a real tell and IS reproduced by binding the element to a
  named local first:

      u32 t = a[i];
      if (t == (u32)p) { a[i] = 0; break; }

  Without that local the compare comes out `cmp r5, r0` and the diff is 11
  bytes instead of 9.  Ruled out for the remaining r1/r2 swap: declaration
  order of `int i; u32 *a;` swapped; a separate `u32 j` index; `i = 0;`
  hoisted above `a = arr_02146A88;`; pointer-walk form `*(a + i)`; `void *t`;
  drawing `arr_02146A88[i]` inline (78 bytes); initialising `a` at its
  declaration (206 bytes).
