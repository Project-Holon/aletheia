Paints a run of the 0xc0-byte array at out+0xc0 with a two-value pattern.
The descriptor is three fields: two u8 bounds at +0 and +1 and a u16 flag
at +2.  The split point is

    split = (hi - lo) * num / den + lo

with the division going through _s32_div_f (0x0209C0A4).  The bounds are
then ordered, and this is where the two arms differ in more than order:

  - lo <= hi (the FALL-THROUGH arm; the original's `bhi` jumps forward to
    the other one): the run is [lo, hi) and the paint value is the flag
    halfword's own value, loaded straight into the loop register.
  - lo > hi: the bounds swap, and the paint value is the INVERSE sense of
    the flag: 1 if the flag is zero, 0 if it is not.

The loop then walks the run writing the current value into out[0xc0+i],
and at the one index equal to `split` it flips the value (0 <-> 1) --
flips the LIVE variable, not a per-iteration temporary: the flipped value
persists for the rest of the run, which is what makes this a two-tone fill
rather than a single odd byte.

Four spellings are load-bearing and were each isolated against the bytes.
A future pass should start from these rather than rediscover them:

  - the bounds are UNSIGNED.  The compare at +0x16 is `bhi`, not `ble`.
    Typing lo/hi as s32 gives `ble` and a 56-byte diff that hides
    everything else.
  - the ordering test is `if (lo <= hi)` with the swap arm as the `else`.
    Written the other way round (`if (lo > hi)` first) the compiler emits
    the arms in source order and 33 bytes go wrong, because the original's
    `bhi` is a forward branch over the fall-through arm.
  - the split is `quotient + lo`, in that operand order (`adds r0,r0,r6`).
    Writing `lo + quotient` puts lo in the left slot and costs 2 bytes at
    +0x14.  Binding the quotient to its own named local `q` before the add
    is what pins it; see docs/idioms/commutative-operand-order-names-the-
    temporary.md.
  - the loop must assign back into the SAME variable it tests (`near`),
    not into a per-iteration temporary `v`.  The `v` form compiles 80
    bytes (2 short) with 32 differing: the original keeps one loop-carried
    register, and a temporary lets the compiler rematerialise instead.
    The two constants must also be hoisted into named locals `one`/`zero`
    declared in that order -- the original materialises both ONCE before
    the loop (`movs r6,#1` / `movs r3,#0` at +0x32/+0x34) and selects
    between them with register moves inside it.  Declaring them in the
    other order swaps r6/r3 and costs 2 more bytes.
  - inside the flip, the test is `if (near == 0) near = one; else near =
    zero;`.  The inverted polarity flips the `bne` at +0x3C.

because every arrangement still defines `near` in the arms.
