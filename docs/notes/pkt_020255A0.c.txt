WHAT IT IS.  The bmp_oam grid CONSTRUCTOR, the mirror of func_0202570C
(EXACT*, src/matched/func_0202570C.c).  Allocates the 0xCC-byte grid
object, derives the cell grid from the source bitmap's pixel extents,
then for every cell of the rows x cols grid creates a resource
(func_0204A7A0) and an actor (func_0204B294), sets the actor's byte
field (func_0204B6F4) and clears it (func_0204BA20).

SEMANTICS FULLY RECOVERED.  Everything below is byte-evidenced.

1.  THE GRID OBJECT IS TWO PARALLEL POINTER ARRAYS, not an array of
    structs.  The cell cursor advances by FOUR bytes per cell
    (`lsls r1, r7, #2` at +00D2) and both stores reach off the same
    register: `str r0, [r6, #0x68]` at +00EA for the resource and
    `str r0, [r6, #4]` at +012C for the actor.  So act[] starts at +4,
    res[] at +0x68, and 0x68 - 4 = 0x64 = 25 pointers.  Writing it as
    one array of 0x6c-byte cells compiles 12 bytes long and 213 bytes
    out; the `u8 *` cursor spelling below is what gets the size right.

2.  THE TWO LOOP COUNTERS ARE u8, and so are cols and rows.  Every
    iteration ends with the `lsls #0x18 / lsrs #0x18` truncation pair
    (+0142/+0144 for the inner, +0150/+0152 for the outer).  u32
    counters compile 8 bytes SHORT; that one change took the file from
    356/364 to size-exact.  The permuter found the rows one on its own
    (`type:l(rows:u32->u8)`, -4 bytes out).

3.  THE CELL GEOMETRY IS 32 x 16 PIXELS.  cols = width/32 and
    rows = height/16, each ROUNDED UP, and the rounding is spelled as a
    SIGNED remainder test: `lsrs r2,r0,#0x1f / lsls r1,r0,#0x1b /
    subs r1,r1,r2 / movs r0,#0x1b / rors r1,r0 / adds r0,r2,r1 / beq`
    is `(s32)func_020437DC(bmp) % 32 != 0`.  An unsigned `& 31` test is
    three instructions shorter.  The same quartet with #0x1c/#0x1c is
    the % 16 for rows.

4.  struct Param's x and y ARE s16.  `movs r0,#4 / ldrsh r1,[r4,r0]` at
    +00EC/+00EE and `movs r0,#6 / ldrsh r1,[r4,r0]` at +00FA/+00FC:
    register-offset ldrsh is the only encoding there is, and it is the
    signedness tell (docs/idioms/ldrsh-register-offset-is-signedness.md).

5.  struct Param's fc at +0x0c is a WORD narrowed at the use, not a byte
    field: `ldr r1,[r4,#0xc]` then `lsls #0x18 / lsrs #0x18`.  An
    `ldrb` would be four bytes shorter.

6.  THE POINT OBJECT IS ZEROED WITH FOUR HALFWORD STORES through one
    pointer (`add r1,sp,#0x2c / movs r0,#0 / strh r0,[r1] ..
    strh r0,[r1,#6]`).  Assigning the members individually emits two
    `strb` for +6/+7 and loses the prologue; the `u16 *q = (u16 *)&pt;`
    cursor spelling is what reproduces it.

7.  func_02025A9C's ARGUMENT ORDER IS (sys, param->f14, engine), NOT
    (sys, engine, param->f14).  The original loads `ldr r1,[r4,#0x14]`
    then `ldr r2,[sp,#0x18]` at +00C4/+00C6; the other order swaps the
    pair.  Worth 4 bytes.  Note this makes func_02025A9C's second
    parameter the system handle and its third the engine selector, which
    is the reverse of what docs/notes/pkt_02025A9C.c.txt assumed from
    that function alone; the caller is the stronger evidence.  (Both
    orders compile the same bytes INSIDE func_02025A9C, since it uses
    each argument exactly once, so this does not disturb that lane.)

8.  func_0204B294's fourth argument is sys->slot[mode]: `lsls r3,r3,#2`
    on the mode then `adds r3,r5,r3 / ldr r3,[r3,#0xc]` reads the same
    three-word slot array func_02025538 seeds with -1 and func_02025B18
    releases.

9.  gModeTable's BASE IS 0x0209F87C, not 0x0209F880.  This function's
    pool word is 0x0209F87C and it indexes `[r0, mode*12]` for the first
    member, while func_02025A9C's 0x0209F880/0x0209F884 are base+4 and
    base+8 of the same symbol.  The record is {0x130, a, b} and the
    three rows are {0x130,0,1}, {0x130,3,4}, {0x130,6,7} (asm/arm9/main.s
    lines 269209-269217).  Declaring the base here also UPGRADES
    func_02025A9C's two sites from `sole-ref` to `literal`, because
