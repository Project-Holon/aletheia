Three-component fixed-point relaxation: for each of b->_08, b->_0C and
b->_10,

    b->f = b->f + FX_Mul(a->w, a->f_src - b->f)

with a->w an s16 at a+0x0C (re-read per component, because the store to b
may alias it) and FX_Mul the ordinary two-operand SDK inline, which here
compiles to a plain smull because both operands are runtime s32.

Under -O4,p -proc arm7tdmi the C at the end reproduces every instruction
except one, repeated three times:

    original   mov r2, #0x800 (once, hoisted above the first smull)
               adds r4, ip, r2
    compiled   adds r3, ip, #0x800

That is, the original keeps the FX_Mul rounding constant in a register and
adds it in register form; mwcc here always picks the immediate form, in
every spelling tried: + 0x800, + (fx64)0x800, + ((fx64)1 << 11), and a
named fx64 local for the product. The knock-on effect is the register
allocation: the original needs one more live value and so pushes
{r4, lr}, while the compiled form has r3 free and pushes {r3, lr} as
alignment padding. Identical finding in func_02056460, which needs the
same constant twice rather than three times.

The three-component body is straight-line, not a loop: writing it as
for (i = 0; i < 3; i++) over fx32 v[3] members is not unrolled at -O4,p
(76 bytes, an indexed loop), so the source really does spell the three
components out.
