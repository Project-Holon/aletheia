pkt_020113F0 (0x020113F0, 0x02011400) - documented near miss, no source filed
=========================================================================
Both are four-instruction pool-added table lookups:

    020113F0  movs r2, #0x18          ldr r2, [r1, r0]  style
              muls r2, r0, r2
              ldr  r0, [pc, #4]        <- 0x0209DF24
              adds r0, r0, r2
              ldrb r0, [r1, r0]
              bx   lr

    02011400  lsls r2, r0, #2
              adds r2, r0, r2          (stride 5)
              ldr  r0, [pc, #4]        <- 0x0209DF10
              adds r0, r0, r2
              ldrb r0, [r1, r0]
              bx   lr

Two independent blockers, both measured:

1. codegen.  `base[(u32)sTbl + idx * 24]` compiles to five bytes that differ in
   *placement*: mwccarm hoists the PC-relative pool load above the multiply and
   uses r3 (`movs r2,#0x18; ldr r3,[pc,#8]; muls r2,r0,r2; adds r0,r3,r2`)
   where the original loads the pool into r0 *after* the multiply.  Same four
   instructions, same size, same pool address - a scheduling difference, not a
   shape difference.  Spellings tried: `base[(u32)t + idx*n]`,
   `base[idx*n + (u32)t]`, a bound `u32 off = idx*n;` local, and a
   `*(u8*)((u32)base + off + (u32)t)` pointer form; all five.

2. evidence.  Both table bases (0x0209DF10 and 0x0209DF24) are named by exactly
   one literal pool word each in the whole image, and that word is inside the
   function under test, so the `literal` class has no outside witness and the
   entry caps at MATCH even with perfect codegen.  They are adjacent, but
   declaring them as one symbol does not help: a site is attested by the
   *symbol* address (match.py's `attest()` looks the bare target up in
   pool_words), so the +0x14 addend form cannot borrow the sibling's pool.
