C is straightforward (a "call, and if PXI is busy, spin-wait and retry"
loop) and every instruction reproduces except the one at +0x30. That is a
tooling limitation, not a C problem: `resolve_relocations()` in
`tools/match.py` only encodes an ARM branch relocation (`_ARM_BRANCH`,
covering PC24/CALL/JUMP24) when `kind != "thumb"` (see the `elif rtype in
_ARM_BRANCH:` arm around line 1605). An ARM caller's direct `blx
#immediate` into a Thumb callee, which is exactly what the original has
here (0x02004490 is a two-instruction Thumb stub, `svc #3; bx lr`), is
never attempted: the resolver leaves the site wildcarded and the compiler
emits a plain `bl` (opcode/condition byte 0xEB...) where the original has
a `blx` (condition nibble 0xF...), which is a concrete, unmasked byte
difference outside the 24-bit displacement field. The doc note in
`docs/MATCHING.md` around "R_ARM_THM_CALL / R_ARM_THM_XPC22" describes the
Thumb-caller-into-ARM-callee rewrite; the symmetric ARM-caller-into-Thumb
case does not appear to be implemented. Any packet whose small ARM
leaves call directly into a Thumb stub (SVC wrappers observed at
0x02004490 in this packet) will hit the same wall; not something a C
rewrite can fix.
