WHAT THE FUNCTION IS.  It rebuilds the wipe's per-scanline window table, one
row for each of the screen's 0xC0 lines.  sub_02022D88 hands back the buffer
whose two s16 arrays live at +0x300 (left edge) and +0x480 (right edge), 0xC0
entries each.  The loop has a mirror shortcut: while the row index is inside
the band (w->f14, 2 * w->f14] the pair is COPIED from the row 2*f14 - y
already written earlier in the same pass, and only outside that band is it
computed fresh through func_020237B8.  Both arms leave the pair in the same
two stack slots and the store back to row y is written once after the if/else.

THREE THINGS WERE ESTABLISHED AGAINST THE BYTES AND ARE WORTH KEEPING:

1. func_020237B8's fifth argument is &l (the LEFT edge) and its sixth is &r.
   The image stores r7 (which holds sp+0xc, the l slot) to [sp] and sp+8 to
   [sp,#4], so the fifth argument is the sp+0xc one.  Reversed, the two
   `strh` at the bottom of the loop write the wrong arrays and the function
   is 55 bytes out instead of 54 -- a one-byte difference in the score, which
   is exactly why it is worth stating: this is NOT diagnosable from the
   bytes-out number and only the argument-slot reading fixes it.

2. Both array bases are rematerialised per access (movs #3 / lsls #8 = 0x300,
   movs #0x12 / lsls #6 = 0x480) rather than kept live, which is what
   declaring them as members of one struct with a register-offset index
   produces (docs/idioms/thumb-immediate-reach-costs-an-adds.md).  Hoisting
   either base into a local is wrong: the permuter's own best point does that
   and pays for it.

3. The guard is TWO SEPARATE TESTS, not one `&&`.  The image spends a `bgt`
   over an unconditional `b` at +0x16 (four bytes) where a conjunction folds
   to a single conditional branch (two bytes).  That four-versus-two is
   exactly the size gap.

THE SIZE GAP AND WHAT CLOSES IT.  The source below compiles 98 bytes against
104.  `tools/permuter.py --mode hill --budget 800 --jobs 8 --types` closes it
at compile 219 with `temp(tmp=w->f10)`: hoisting w->f10 into a local before
the loop gives 104/104 exactly.  BUT IT CLOSES THE GAP THE WRONG WAY.  The
temp takes r7, and r7 is the register the image spends on `add r7, sp, #0xc`
-- the address of the l slot, materialised once outside the loop and reused by
every call.  So the size becomes right while bytes-out goes 55 -> 80, and the
whole mirror arm that WAS byte-identical stops being so.
