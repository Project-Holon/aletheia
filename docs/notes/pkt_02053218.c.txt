THE BLOCKER: `blx rN` and `pop {..., lr}; bx lr` in the same function
---------------------------------------------------------------------

The original contains ARMv5 register-form BLX:

    02053EC4  33 FF 2F E1   blx r3        (the vertex hook table call)
    02054268  34 FF 2F E1   blx r4        (the final hook table call)

and ARMv4T-style returns:

    02053E74  08 BD 41 F0   popeq {r4, r5, r6, r7, r8, lr}
    02053E78  1E FF 2F 01   bxeq  lr
    02054270  F0 41 BD E8   pop   {r4, r5, r6, r7, r8, lr}
    02054274  1E FF 2F E1   bx    lr

mwccarm ties the two together: a `-proc` that can encode `blx rN` returns by
popping into `pc`, and a `-proc` that returns through `lr` emits
`mov lr, pc; bx rN` for an indirect call.  Measured, not assumed, on a
four-line probe and then on the function itself, over all 32 `-proc` values
1.1p1 accepts:

    -proc arm946e  ->  0xE12FFF33 (blx r3) ...  pop {r4, ..., pc}
    -proc arm7tdmi ->  0xE1A0E00F + 0xE12FFF13 ...  pop {r4, ..., lr}; bx lr

    generic v4 v4t arm7tdmi arm710t arm720t arm740t arm9tdmi arm920t
    arm922t arm940t dbmx1 dbmxl   ->  mov lr,pc + bx,  pop lr / bx lr
    v5t v5te v6 v6t2 v7 arm7ej arm9ej arm926ej arm946e arm966e arm1020e
    arm1022e arm1026ej XScale pxa25x pxa26x  ->  blx rN,  pop pc

Not one of the 32 is in both lists.  `#pragma peephole off` does not change
the epilogue (`pop {..., pc}` survives it), and `-interworking` only picks
between the two v4T forms: with it arm7tdmi gives `pop lr; bx lr`, without it
`pop pc`.  All nine `dsi` builds 1.1 .. 1.6sp2 emit `pop {r3, pc}` under
arm946e for the same probe, so no compiler version in the collection closes
the gap either.

Both idioms in one binary is not impossible for the *image* -- it is impossible
for one `-proc` setting of this compiler -- so the original unit was built by
something this tree does not have (a later mwcc, or an assembler-assisted
source).  That also means the region cannot be reached from C as the toolchain
stands, whatever the C says.

This qualifies the existing idiom note
`docs/idioms/an-arm-epilogue-of-pop-lr-then-bx-names-a-proc-arm7tdmi-unit.md`,
which reads the `pop lr; bx lr` epilogue as a whole-unit `-proc arm7tdmi`
tell.  The tell is real, but it is not sufficient: the two arm7tdmi entries
that were actually matched (0x02058300, 0x0205841C) are blx-free.  Every
function in 0x020524E0..0x02057828 that contains a register BLX -- 24 sites,
0x020525FC through 0x02054D8C -- has the same contradiction, and all of them
are in the same unit as a function whose return says arm7tdmi.

WHAT THE FUNCTION DOES (recovered from the disassembly)
------------------------------------------------------

Written to `src/matched/func_02053E1C.c` while working and then removed, since
only EXACT may live there; the full text is at the end of this note.

It is a billboard/rig builder for the DS 3D engine:

* build a value for the hardware register at 0x040004A4 out of three bitfields
  of a packed u16 (`s->unk2E`, fields at bit 0/5/10), store it, read it back,
  and return early when the middle product shifts to zero;
* call a per-primitive hook `table[(*hw >> 9) & 3](verts[2*i], verts[2*i+1],
  &m2)` with `i = (s32)s->unk20 >> 4`, from the s16 vertex table at 0x020A1B38
  and the hook table at 0x020A7FE4;
* normalise one of two vectors of `s` (the choice is bit 6 of a word at
  `(*x->unk14) + 0x10`) into v0, negating it when the other one is chosen;
* build a reference axis (0, 0x1000, 0), replace it with (0x1000, 0, 0) when
  `VEC_DotProduct(v0, axis)` comes out outside +-0xCCD (the 0.8 fixed-point
  cosine limit), then two `VEC_CrossProduct` calls give an orthonormal basis
  which lands in m4's 3x3 part (identity translation row, so
  `MTX_Identity43_` first, `MTX_Concat43` after);
* fixed-point products to get the scale factors, a 3-way switch on bits 28..30
  of `q->0x48` choosing which axis is rescaled by `s->unk34`, then
  `MTX_Scale43_` (0x0207B5F4, declared thumb: it is reached by BLX in the
  original) and a second `MTX_Concat43`;
* two arms on bit 23 of `*q`: place the matrix at `s->08.. + s->38..` and
  `G3_LoadMtx43`/`G3_MultMtx43`, or subtract `q->04/08/0C`, push three words
  into the FIFO at 0x04000454/0x04000470 and multiply;
* pack two 5-5-5 colours (per-channel `a*b >> 5/15/25`) into 0x04000480;
* tail-call `table2[(*hw >> 11) & 1](P->0x7C, P->0x7E, 0)`.

Pools: 0x040004A4, 0x020A1B38, 0x020A7FE4, 0x00000CCD, 0xFFFFF333,
0x04000454, 0x04000470, 0x04000480, 0x020A7FDC -- nine words, which is the
36 bytes between 0x02054278 and 0x0205429C.


TWO SOURCE-SHAPE IDIOMS WORTH KEEPING (found while closing the gap)
------------------------------------------------------------------

1. A literal `0` at a call's argument position can be hoisted into a
   callee-saved register and kept live for the whole function, where the
   original rematerialises it at each use.  In this function the last argument
   is 0; written as a literal the compiler emits `mov r6, #0` in the first
   basic block and then uses r6 for every zero in the body (and displaces the
   vertex table to r7), which is four bytes and every later register number.
   Written as a *variable* assigned 0 just before the call (`e = 0; ... f(a,
   b, e)`) the hoist disappears and the sequence from instruction 0 on matches
   the original register for register.  The reference materialises zero at
   each use (`mov r3, #0`, `mov r0, #0`, `mov r1, #0`, `mov r2, #0`), so the
   source's last argument was a variable, not a literal.

2. mwccarm never pools a negated constant: `d > 0xCCD || d < -0xCCD` compiles
   to one pool word 0x00000CCD plus `rsb r1, r1, #0`, and no spelling of the
   negative side (`-3277`, `(s32)0xFFFFF333`, swapped operands, an unsigned
   literal) changes it.  The original has two pool words, 0x00000CCD at
   0x02054284 and 0xFFFFF333 at 0x02054288, so its second bound did not reach
   the compiler as a negation of the first.  Unresolved; the pool is four
   bytes shorter here than in the original for that reason alone.

A third, smaller residue: the FIFO stores go to 0x04000454 and 0x04000470,
0x1C apart, and the compiler folds them onto one base register
(`str r1, [r0, #28]`) where the original reloads both addresses from the pool.
