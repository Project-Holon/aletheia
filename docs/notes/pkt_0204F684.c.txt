func_0204F684: callee-saved register choice, 48 bytes in the image vs 44 compiled
==================================================================================

Closed near miss.  The function stores two signed halfwords into the 0x1c-stride
record at +0x12 and +0x14:

  image (48 bytes):   push {r3, lr}
                      mov  ip, #0x1c
                      mul  lr, r1, ip        <- scaled index in lr
                      ldr  r1, [r0, #8]      <- reloaded p->f8
                      ldrsh ip, [r2]
                      add  r2, r1, lr        <- address in a NEW register
                      ldrsh r1, [r3]
                      strh ip, [r2, #0x12]
                      ldr  r0, [r0, #8]
                      add  r0, r0, lr
                      strh r1, [r0, #0x14]
                      pop  {r3, pc}

  mwcc (44 bytes):    mov  ip, #0x1c
                      mul  ip, r1, ip        <- scaled index in ip
                      ldr  r1, [r0, #8]
                      ldrsh r2, [r2]
                      add  r1, r1, ip        <- address accumulated in place
                      strh r2, [r1, #0x12]
                      ldr  r0, [r0, #8]
                      add  r0, r0, ip
                      strh r1, [r0, #0x14]
                      bx   lr

Same instruction kinds, same count of arithmetic, same reloads: the image simply
spends the scaled index on lr (and therefore saves lr) where mwcc spends it on
ip and needs no prologue at all.  The extra push/pop is the whole 4-byte
difference.

Spellings tried, all landing on the ip form:

  * `*(s16 *)(*(u8 **)((u8 *)p + 8) + idx * 0x1c + 0x12) = *a;` twice
  * the same with the base bound to a local used by the first store only
  * the scaled index in a `u32 off` local
  * both source halfwords read into locals before either store
  * `struct Rec { u8 pad[0x12]; s16 x; s16 y; }` member stores
  * `struct Rec { u8 pad[0x12]; struct Pos pos; }` nested member stores

Its three siblings in the same packet (func_0204F5A8, func_0204F720,
func_0204F764, func_0204F794) all reached EXACT or EXACT* with the bitfield
spellings recorded in their files, so the packet is otherwise clean.

A one-bit bitfield write is a conditional set with no narrowing
----------------------------------------------------------------

func_0204F720 came back 48 bytes compiled against 40 in the image, over and
over, until the field was written as a 1-bit bitfield rather than a
read-modify-write of the halfword.  Three spellings that all failed by one
lsl #16 / lsr #16 pair:

  * `*q |= 0x200;` / `*q &= ~0x200;` in an if/else  (re-reads *q per arm)
  * `u16 v = *q; v = (u16)(v | 0x200); ...; *q = v;`  (explicit cast narrows)
  * `*q = (*flag == 1) ? (*q | 0x200) : (*q & ~0x200);`  (ternary narrows)

What reproduces the image exactly:

  struct Rec { u16 lo : 9; u16 b9 : 1; u16 hi : 6; };

  if (*flag == 1) {
      struct Rec *r = (struct Rec *)(... + idx * 0x1c + 0x18);
      r->b9 = 1;
  } else {
      struct Rec *r = (struct Rec *)(... + idx * 0x1c + 0x18);
      r->b9 = 0;
  }

giving `ldrh r0, [r2, #0x18]` / `orreq r0, r0, #0x200` / `bicne r0, r0,
#0x200` / `strh r0, [r2, #0x18]` -- one load, two conditional one-hot ops, one
store, no truncation.  Two things matter: the bit is a bitfield (a plain
halfword read-modify-write keeps a narrowing shift pair), and the address
expression is written *inside each arm*, so the condition is evaluated before
the address.  Hoisting the address into a local declared above the if moves it
first and the four instructions land in the wrong slots.

The same packet's func_0204F764 / func_0204F794 want the bitfield form too
(`r->b10 = (u16)*val;`), but there the `(u16)` narrowing must stay visible: the
image keeps both the lsl #16 / lsr #16 narrowing pair and the lsl #31 / lsr #21
bit write, four instructions apart.

Separately: this front end rejects mid-block declarations despite `-lang c99`
("expression syntax error" on the declaration after a statement), so a store
can never be squeezed between two declaration groups.

Re-derived in wave 4-2 (pkt_0204F684), same verdict, and these further
spellings were ruled out on top of the list above:

  * the two source halfwords read into `short` locals, into `u16` locals, and
    into `u32` locals, before either store
  * the two destination addresses bound to `short *` locals first, then one
    store per arm
  * the scaled index inline as `i * 0x1c` (that one is 4 bytes short of even
    the ip form, because the multiply then folds)
  * the record as `struct Ent { u8 pad_00[0x18]; u16 f0 : 5; u16 f1 : 4;
    u16 f2 : 1; u16 f3 : 6; u8 pad_1a[2]; }` with `e[i].f12` / `e[i].f14`
    member stores and with `&e[i]` bound to a local
  * the base re-read written as `((struct E28 *)*(u32 *)(a0 + 8))[i]`
    (the array form does produce the image's `mov #0x1c` + `mul`, which is
    where the stride comes from, but not the lr/ip split)

The stride is `i * 0x1c` with the multiply in its own register, so the record
type's sizeof must be 0x1c for the encoder to emit the image's `mov r0, #0x1c`
+ `mla` pair in the three sibling accessors - see src/matched/unit_0204F6B4.c,
which reproduces 0x0204F6B4..0x0204F720 (108 bytes, three unlabelled leaves).
