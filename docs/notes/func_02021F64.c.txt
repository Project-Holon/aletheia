The note above stops at 114/116 bytes with the residue described as
"`count` and `i` picking the wrong two registers" plus per-channel
scheduling freedom.  That diagnosis was wrong, and the function closes with
two changes, the second of them a single keyword.

1.  The "next step" this note proposes is correct and is what gets the size
    and the register allocation right: read the per-pixel bitfields off a
    pointer into `src[i]`'s own memory,

        int sr = ((struct Rgb555 *)&src[i])->r;

    rather than through a value-copy union.  With this and the loop counter
    declared `u16 i` (the image's `lsls #0x10 / lsrs #0x10` on the increment
    at +0x58), the compile is 114 bytes -- size exact -- and the whole
    function is byte-identical except for THREE bytes.

2.  Those three bytes were the three `>> 4`s:

        original   +003E/+004A/+0054   asrs r4, r4, #4
        compiled   +003E/+004A/+0054   lsrs r4, r4, #4

    `weight` was declared `u32`, which makes each `(t - s) * weight` an
    unsigned product and each `>> 4` a logical shift.  Declaring it `int`
    makes the products signed and the three shifts arithmetic.  That is the
    whole remaining residue; nothing about register allocation or channel
    scheduling was ever wrong.

    So the fifth-argument struct, the count and the destination index are
    unsigned, and the blend weight is signed:

        void func_02021F64(u16 *src, u16 *dst, u32 count, int weight,
                           struct Rgb555 color)
