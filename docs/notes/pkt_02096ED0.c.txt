LEVERS THAT DID WORK (keep these; they are what took the row from 696 to 672
bytes and from 71 to 101 byte-identical instructions):

  1. `const DB *src` on the second parameter is LOAD-BEARING.  With a plain
     `DB *src`, mwcc expands the opening 38-byte struct copy as
     ldrh / ldrh / add / subs / strh / strh / bne (7 instructions, +4 bytes);
     with `const DB *src` it expands it as
     ldrh r3,[r1,#2] / ldrh r4,[r1],#4 / subs r5,r5,#1 / strh r3,[r6,#2] /
     strh r4,[r6],#4 / bne -- 6 instructions, byte-identical to the original.
     This is the only lever that closed a real instruction-count difference.
  2. The rounding block reuses the pointer saved before the loop (`p = pb;`),
     not the decremented loop cursor: the original has `mov r4, lr` at
     0x02096F88 and its `i = p - b->buf` at 0x02097008 reads that copy.  Using
     the cursor instead is a real semantic difference and shifts the bytes.
  3. The rounding decrement is `if (*pa < 1) { ...borrow... } *pa -= 1;` --
     one shared `*pa -= 1` after the borrow, not an if/else with a copy in
     each arm.  Written as if/else, mwcc predicates the decrement
     (subcs/strbcs) and the body grows by two instructions.
  4. `base` must be a named local.  Spelling the same code with `a->buf` at
     every use makes mwcc rematerialise `r0+5` nine times, +20 bytes.
