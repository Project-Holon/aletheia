THREE THINGS FIXED THIS PASS, and they are the levers to keep:

L1  THE STACK RECORD IS ZEROED THROUGH A CAST POINTER, not through the
    struct members. `q = (u32 *)&c; q[0] = 0; q[1] = 0;` is what produces
    the image's `add r4, sp, #0` base plus `mov r3, #0` and the two
    `str r3, [r4]` / `str r3, [r4, #4]`. Writing `c.st0 = 0; c.st1 = 0;`
    (or going through a `struct CURSOR *p`, which folds) makes the stores
    plain `str r3, [sp]` / `[sp, #4]` with no base register at all, and the
    whole prologue reorders. A separate 8-byte state object declared beside
    the handle is NOT the answer either: it is dead-stripped, the frame
    shrinks to `sub sp, sp, #4` and the function comes out 100 bytes.

L2  THE LOOP IS A GUARDED DO-WHILE WITH THE CURSOR IN ITS OWN LOCAL.
    `ch = decode(&c.handle); if (ch != 0) { cur = &c.handle; do { ... }
    while (ch != 0); }`. The plain `while (ch != 0) { ... }` head does not
    reproduce the image's separate `add r5, sp, #8` at 0x02068118, which
    sits BEFORE the back-edge target 0x0206811C and so is the loop
    preheader, not the body.

L3  DECLARATION ORDER SETS pitch AND THE LINE COUNT. With the locals
    declared `q, decode, ch, n, cur` the count lands in r6 and pitch in r4,
    as the image has them. Declaring `cur` earlier (first, or between
    `decode` and `ch`, or between `ch` and `n`) moves the count to r4 and
    pitch to r5 and costs four more bytes in the tail arithmetic.
