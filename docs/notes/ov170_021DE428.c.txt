func_021DE428 (ov170): 45/264 bytes wrong, register allocation only
====================================================================

Near miss, left in no shard.  This is not a source bug: the whole function
compiles to the right sequence with the right sizes, and every differing byte
is a register-name choice inside the second half's per-entry loop, plus one
re-materialised constant.  The first 0x8A bytes (entry zeroing loop, the
b==0xff / func_021DDE20 gate, the whole default path and its func_021DDEFC
call) are byte-identical, and the two trailing entry writes match except for
the same r1/r2 swap.

The original loop body carries the 0x18-byte offset in r2 and the entry
pointer in r1:

    movs r0, #0x18
    adds r2, r5, #0        ; r2 = j
    muls r2, r0, r2        ; r2 = 0x18*j
    adds r0, r5, #0
    adds r0, #0x1e
    lsls r0, r0, #0x10
    lsrs r0, r0, #0x10
    adds r1, r4, r2        ; r1 = entry
    strh r0, [r4, r2]
    adds r2, r5, #0
    adds r2, #0x1d
    strh r2, [r1, #2]
    strh r0, [r1, #4]
    movs r0, #1
    strh r0, [r1, #6]

The compiler insists on the mirrored allocation (offset in r1, pointer in r2),
for every spelling tried: pointer local (`u8 *e = r4 + 0x18*j;`), direct
repeated `r4 + 0x18*j` expressions (CSEd identically), a block-local
`struct { u16 a,b,c,d; u16 z[8]; }` array, binding the `(u16)(j+0x1e)`
temporary to a named local, and reordering the local declarations.  The one
remaining extra instruction is at the end: the original keeps `1` in the
callee-saved r5 across the `func_021DDFD4` call that writes the base entry and
reuses it for the final r7-entry's `[r1,#6]`, while the compiler re-emits
`movs r0,#1` after the call; that is the whole 2-byte size delta.

Closest source (45 concrete bytes, dsi/1.1p1, -O4,p -thumb), for whoever picks
this up:
