1. The true extent -- 3156 is a region-tail artefact, not the function
----------------------------------------------------------------------
`tools/lane.py --band 3000 3300 --regions ov121` reports
    ov121  0x021DEFAC  3156  func_021DEFAC
because for the last label in a region it takes the size to the region end.
ov121 spans 0x021D6660..0x021DFC00 (asm/overlays/ov121.s header), so the
enumerator's 3156 bytes = 0x021DFC00 - 0x021DEFAC and runs through the whole
static data tail.

The real function:
  * code         0x021DEFAC..0x021DF4E2   (1334 bytes, Thumb)
  * inline pool  0x021DF33C..0x021DF350   (2 words: 0x289, 0xFFFF)
  * tail pool    0x021DF4E4..0x021DF4F0   (0x020A7370, 0x28A, 0x272)
i.e. one function ending at the `pop {r3,r4,r5,r6,r7,pc}` 0x021DF4E0, with its
literal pools.  `match.py one` compares 1352 bytes (0x548).  0x021DF4F0 onward
(0x400, 0x00020001, ...) is unrelated static data.

Note the listing is misleading past 0x021DF344: disasm.py lost sync at the
inline pool and emitted the code 0x021DF350..0x021DF4E2 as `.word` runs.  The
branch `bne 0x021DF350` at 0x021DF32E proves that run is code, and 0x021DF3A0
branches back to 0x021DF330.  Capstone (Thumb) is the reliable disassembler
here; the AGENT-BRIEF `show` output dumps the tail as raw bytes for the same
reason.  So: do not trust the `.s` listing for this function's tail.

3. The root: structure and current verdict
------------------------------------------
`python tools/match.py one --src src/pending/func_021DEFAC.c --func func_021DEFAC \
     --addr 0x021DEFAC --cc 1.1p1 --thumb --region ov121`
gives DIFF: compiled 1352 bytes (the correct size), 55 of 56 relocation sites
resolved.  The one unresolved site is
    +03EC ABS32 tbl_021DFB2C -> unresolved: 021DFB2C has no witness outside
          021DEFAC..0x021DF4F4
i.e. the 15-word Mon field-id table at 0x021DFB2C is named in the whole image
only by the pool word at 0x021DF344, which lies INSIDE the compared range.  So
even a byte-perfect body caps at MATCH, exactly the "CAPPED table" class in
docs/families/poke_tool.h section 9.  (The table is the ids
0x69,0x6A,0x6B,0x6C,0x33,0x34,0x2C,0x2F,0x30,0x31,0x32,0x66,0x67,0x68,0x2E,
one per set bit of p->f0c.)

The body (fully decoded, ~600 instructions) is the PokeTool summary builder:
guard/count pass, then for p->fb3 == 1 it copies a source record's fields into
a fresh Mon (func_020173F0 -> func_02017588), sets ~20 Mon fields through the
func_02017E40/0x02017E1C accessor pair (ids 6, 9, 0xa, 0xc, 0x13..0x18, 0x4c,
0x6f, 0x70, 0x73, 0x74, 0x77, 0x8e, 0x95, 0x96, 0x98, 0x99, 0x9a), draws it
(func_020185F0 / func_0202F2AC / func_020185C4) and frees or returns it.
p->fb3 cases 2 and 3 are short.  The 30-bit value rebuilt from six 5-bit
fields of the source bytes at +0x43..+0x48 is the rendered id/trainer value.

Where the WIP is stuck: the concrete residue is almost entirely STACK OFFSETS.
Original frame 0x50 / `push {r3,r4,r5,r6,r7,lr}`; my compile gets 0x4c /
`push {r4,r5,r6,r7,lr}`.  The original's scalar slots are
   0x18 v18, 0x1c v1c, 0x20 v20, 0x24 v24, 0x28 v28, 0x2c v2c,
   0x30 v30, 0x34 v34, 0x38 v38, 0x3c cnt, 0x40 buf[0x10]
while mwcc assigns cnt to 0x18 and scatters the rest.  Declaration order over
the range v18..v38/cnt/buf was tried in both directions (docs/idioms/
local-declaration-order-is-stack-order.md) and did not move cnt: for this
function mwcc's scalar stack assignment is NOT declaration order, so the exact
source declaration grouping (and probably which values really get homes versus
registers) still has to be recovered.  The init order the image wants is
cnt=0, found=1, i=0, zero=0 after the two parameter homes.

Next lane should start from src/pending/func_021DEFAC.c, fix the frame/stack
map first (all the call sequences already line up), and expect MATCH at best
because of the capped 0x021DFB2C table.
