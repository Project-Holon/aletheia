Signature, from its only caller (src/pending/func_0204BD3C.c):
  int func_02063138(struct Sub *s, u32 base, u32 count, u32 which);

Behaviour: reserve a span in one per-"which" 0x540-byte record's two
free-slot tables (0x500 bytes of fine-grained slots at 1x, then 0x40 bytes
of a second table at 1/4 granularity). 0xFFFF is the free-slot sentinel in
both. If both spans are free, stamp them with one shared running id
(counter at 0x02146BC4) via MIi_CpuClear16, record the bounds into *s at
+0x00.. +0x14, and return 1; otherwise leave *s untouched and return 0.
Table base is g_02146BC8[which] (array of 0x540-byte records).

Best attempt reached: all 4 relocation sites resolve cleanly (two calls to
MIi_CpuClear16 at 0x02082A48, the table base g_02146BC8, the counter
g_02146BC4), but the byte count itself is wrong: compiled 336-340 bytes
against a 348-byte original, and concrete bytes differ throughout the two
range-check loops.

What the diff shows: the original pushes only {r4,r5,r6,r7,r8,lr} (6 regs)
and, on either span failing, branches away to a small dedicated
"mov r0,#0; pop" block (two near-identical copies, one per span, the usual
shared-exit-written-out-in-each-arm shape). Every C shape tried here
instead gets predicated: mwccarm turns the early return into an inline
"moveq r0,#0; popeq {...}" and, doing so, needs two more callee-saved
registers (r3 and sb) to hold the loop pointer/bound pair that the
original keeps in ip/r3. The two behaviours (branch to a duplicated tail
vs. predicate the same tail inline) are both valid codegen for the same
C; something about how the two span checks are written source-side tips
the compiler one way rather than the other, and it was not found by:

  - reordering the `base + (count - 1)` terms to match operand order
    (closed the first 8 bytes of the diff exactly, real progress, kept);
  - splitting count-1 into its own local (made things worse, +4 bytes,
    reverted);
  - sourcing the clear-fill id argument from *s instead of a local (the
    original reloads it from s->id by ldrh for BOTH calls, not just the
    second; this was a real fix, kept in the version below).

The note above ends at "compiled 336-340 bytes against a 348-byte original"
and hands the next agent two guesses (a shared `static` helper for the two
span checks, and `first + count` instead of a second subscript).  Neither is
the lever.  Two other things are, and together they take the function from
340/226 to the original's exact 348 with 165 concrete bytes out -- every
instruction present, every branch target right, all four relocation sites
resolving, and the residue reduced to register naming.

LEVER 1: THE TWO FAILURE RETURNS NEED TWO DISTINCT LABELS AT THE END.

The note diagnoses this correctly -- "the original branches away to a small
dedicated `mov r0,#0; pop` block (two near-identical copies, one per span)"
where mwccarm predicates the return inline as `moveq r0,#0; popeq` -- but the
shapes it tried (a plain `return 0;` inside each guard, and a braced one)
both predicate.  What does not predicate is sending each span's failure to
its OWN label at the very end of the function:

    donea:
        if (ok == 0) goto faila;
        ...
    doneb:
        if (ok == 0) goto failb;
        ...
        return 1;
    faila:
        return 0;
    failb:
        return 0;
    }

That is 348 bytes on the nose.  ONE shared `fail:` label is NOT it -- with
one label the compiler has one copy to reach and cross-jumps the pair, which
is the four-byte loss all over again; the point is that the image really does
carry TWO copies of `mov r0,#0` / `pop {r4,r5,r6,r7,r8,pc}` (at 0x020631E0
and 0x02063270), so the source has to name two exits.  This is the exact
inverse of docs/idioms/a-shared-exit-block-is-written-out-in-each-arm.md: the
idiom says write the statements out per arm and let the compiler merge them,
and here writing ONE copy behind ONE label is what makes it merge too far.
Compare, all under `../2.0/sp2`:

    one `fail:` label, both gotos          344 bytes, 254 out
    plain `return 0;` in each guard        344 bytes, 254 out
    braced `{ return 0; }` in each guard   344 bytes, 254 out
    TWO labels, `faila:` and `failb:`      348 bytes, 201 out   <-

LEVER 2: THE FIRST SPAN'S CURSOR IS `volatile`, AND `ok` IS DECLARED FIRST.

Found by the AST permuter, not by hand:

  python3 tools/permuter.py --src d4.c --func func_02063138 --addr 0x02063138 \
      --arm --cc ../2.0/sp2 --mode hill --budget 500 --jobs 8 --types

  285 compiles, `volatile-add(p)`:      asm 9560 -> 1865, 201 -> 165
  498 compiles, `decl-order(p<->ok)`:   asm 1840, 160

`volatile u16 *p` on the FIRST span's walking pointer (not the second -- the
second's `volatile` costs four bytes and goes back to 352) stops the front end
from rotating the loop, which is what the asm score falling by a factor of
five measures: 9560 to 1840 is the whole first loop coming back into
alignment.  Declaring `int ok;` ahead of `p` is worth five more bytes.

THINGS MEASURED AND REJECTED THIS PASS, so they are not tried again:
  * `while (p <= last)` in place of `if (...) do { } while (...)` -- identical,
    348/201.  The guard-then-do-while and the while are the same code here.
  * the allocation id bound to a local (`id = g_02146BC4; g_02146BC4 = id+1;
    s->id = id;`) -- 344 bytes, 4 SHORT.  The note above is right that the id
    must be re-read from `s->id` for both calls, and it is also true that the
    two reads of `g_02146BC4` itself must stay two reads; binding either one
    loses the four bytes back.
  * the increment written first (`g_02146BC4 = g_02146BC4 + 1; s->id =
    g_02146BC4 - 1;`) -- 352 bytes, 4 LONG.
  * `volatile` on the second span's pointer as well -- 352 bytes, 4 long.
  * `../1.2/sp2` -- 356 bytes.  `1.1p1` -- 344 bytes.  `../2.0/sp2` is the
    only front end that reaches 348 on this shape, which is consistent with
    the cluster pin recorded in docs/families/cluster_02063000.h, though this
    row is not itself a clean pin tell (all three front ends predicate the
    return before lever 1, and all three keep the branch after it).
