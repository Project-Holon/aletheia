2026-09-21 -- pkt_020694D8, func_02069BA0 (0x02069BA0, 96 code bytes; the
listing extent runs 116 because the follower at 0x02069C00 is unlabelled).

VERDICT: DIFF, 96/96 bytes compiled, 14 concrete bytes wrong, SAME SIZE.
Not filed as a source; recorded here.

What the function is: an MSB-first bit reader over the 6-byte cursor object
{u8 *cur; signed char have; unsigned char acc;}. `n` bits are peeled off the
8-bit accumulator at +0x05, whose remaining count is the signed byte at
+0x04; on a short accumulator it pulls the next input byte, recurses for the
shortfall and ORs the already-taken high bits back on. The tail mask is
`acc & (u32)(mask >> (8 - n))` with `mask` a signed 32-bit local holding
0xff -- that spelling, and only that spelling, gives the original's
`mov r1, #0xff` / `and r0, r2, r1, asr r0` pair; `~0`, `0xff` as an unsigned
constant and `(signed char)0xff` all give `mvn r1, #0` instead.

The C below is byte-correct at every instruction; what is wrong is TWO
SCHEDULING DECISIONS, each a swapped adjacent pair, 8 bytes total:

  +0018/+001C  original  lsrge r2, r4, r1 ; strbge r1, [r0, #4]
               compiled  strbge r1, [r0, #4] ; lsrge r2, r4, r1
  +0038/+003C  original  mov r1, r6 ; mov r2, #8
               compiled  mov r2, #8 ; mov r1, r6

i.e. the image computes the shift before committing the new bit count, and
materialises the recursive call's argument before the literal 8; 1.1p1 -O4,p
does both the other way round.

Spellings measured under dsi/1.1p1 -O4,p -proc arm946e, all 96 bytes and all
the same 14 wrong bytes:
  - shift then store, store then shift, and both via a shared `shortfall`
    local;
  - `b->have = (signed char)(have - n)` with an explicit narrowing cast;
  - `have -= n` in place before the shift;
  - hoisting `held << shortfall` into `acc` before `b->have = 8` so the OR
    is `func_02069BA0(b, shortfall) | acc`.
An early-`return` in the then-branch instead of the merged `acc` is worse,
not better: 112 bytes and 95 wrong (the two arms stop sharing the mask tail).

Both differences are pure instruction ordering with identical size and
register allocation, which is NOT the "kept branches"/"kept constants" shape
that licenses a per-file front-end pin (docs/FRONTEND-PINS.md), so no
compiler was swept. If a later wave establishes a scheduling tell for this
family, this is the function to re-measure first.

ALSO: 0x02069BA0's listing extent runs to 0x02069C14 because the leaf at
0x02069C00 saves no lr and so carries no label. It is a 20-byte halfword
post-increment reader over the same object's +0x00 cursor:
    ldr r1,[r0] ; ldrh r2,[r1],#2 ; str r1,[r0] ; mov r0,r2 ; bx lr
Worth seeding into layout/function_starts.txt (integrator's file).

--- the C as measured ---

typedef signed int s32;
typedef unsigned int u32;
typedef unsigned char u8;

typedef struct Bits {
    u8 *cur;
    signed char have;
    unsigned char acc;
} Bits;

u32 func_02069BA0(Bits *b, s32 n)
{
    s32 have;
    u32 held;
    s32 mask;
    s32 shortfall;
    u8 *p;
    u32 acc;

    have = b->have;
    held = b->acc;
    mask = 0xff;
    if (have >= n) {
        acc = held >> (have - n);
        have = have - n;
        b->have = have;
    } else {
        shortfall = n - have;
        p = b->cur;
        b->cur = p + 1;
        b->acc = *p;
        acc = held << shortfall;
        b->have = 8;
        acc = func_02069BA0(b, shortfall) | acc;
    }
    return acc & (u32)(mask >> (8 - n));
}
