WHAT IT IS
----------
MSL's 32-bit integer-to-text conversion, i.e. __utoa/__ltoa: the printf back
end that turns one integer into its digit string.  It is the 32-bit TWIN of
func_02092C3C, which does the same job over a 64-bit value; the two are
field-for-field identical in their descriptor reads, their switch, their digit
loop, their prefix handling, their width handling, their 0x1FD cap and their
sign emission.  Treat them as one source template compiled twice -- that
reading is not an aesthetic judgement, it is forced by residue (b) below.

The row is NOT mid-prologue: unlike its neighbours 0x02092C3C, 0x02092F10 and
0x02093BE0, this function's own `push {r0, r1, r2, r3}` home area IS at
0x020929E8, so --addr 0x020929E8 is the right address to compile at.

SIGNATURE (unchanged from the twin's, measured in docs/notes/pkt_02092C3C.c.txt)
   u32 func_020929E8(u32 value, u8 *buf, struct Spec8 spec, u32 w6, u32 w7)
with Spec8 the 8-byte by-value descriptor (bytes 0..3 in r3, 4..7 in the first
caller stack word), read as ldrb [sp,#0x41] (b1, sign style), [sp,#0x43] (b3,
prefix), [sp,#0x45] (b5, conversion character), and the two trailing width
words at [sp,#0x48] and [sp,#0x4c].  buf is filled BACKWARDS, NUL first.

THE ONE SPELLING THAT MOVED THE NEEDLE (worth 44 bytes, carry it to the twin)
----------------------------------------------------------------------------
The conversion-character dispatch is a real `switch`, not an if/else chain.
The image's tree is a SIGNED binary search:

    cmp r8, #0x69   bgt ...   bge ...      ('i')
    cmp r8, #0x58   bgt ...   beq ...      ('X')
    cmp r8, #0x64             beq ...      ('d')
    cmp r8, #0x6f   bgt ...   moveq ...    ('o')
    cmp r8, #0x78   bgt ...                ('x')
    cmp r8, #0x75   blt ...   beq ...      ('u')

An if/else chain in source order gives a flat run of `cmp`/`beq` and comes out
44 bytes SHORT (532 against 588).  Written as

    switch (conv) {
    case 'i': case 'd': ... break;
    case 'o':           ... break;
    case 'u':           ... break;
    case 'x': case 'X': ... break;
    }

the tree is reproduced instruction for instruction, shape and branch order
included.  Note the cases are NOT dense from zero, so this is not the
dense-switch-table idiom; mwcc builds a comparison tree instead, and the tree
it builds is what the image has.  The same change takes func_02092C3C from
672 bytes to 720 bytes, i.e. size-exact, so it is a property of the template,
not of one function.

THE TWO REMAINING RESIDUES, BOTH NAMED
--------------------------------------
(a) ONE STACK SLOT SHORT.  The image is

        push {r3, r4, r5, r6, r7, r8, sb, sl, fp, lr}
        sub  sp, sp, #0x10

    -- four scalar slots, [sp]=start, [sp+4]=prefix, [sp+8]=w6, [sp+0xc]=neg,
    and the `push {r3}` is the alignment pad the fourth slot pulls in.  Every
    compile of this body is

        push {r4, r5, r6, r7, r8, sb, sl, fp, lr}
        sub  sp, sp, #0xc

    -- three slots, with w6 kept in a register.  This is ONE defect, not two:
    recovering the slot recovers the push list with it.  Everything tried to
    force w6 into memory was coalesced away by mwcc:
      * `w6v = w6;` with `width = w6v;` at the use               (no change)
      * the same plus a second read of w6v in the b0==2 arm      (no change)
      * a dead self-guard `if (w6v != w6) w6v = 0;`              (no change)
      * homing w6v in the prologue, before the early-return guard (no change)
      * declaration-order permutations over all six scalars      (no change)
      * `conv` widened from u8 to u32 to buy a fourth live value (no change)
    The permuter's `type` mutation set was run over every local as well.
    LEVER FOR THE NEXT LANE: the slot is probably not w6 at all.  Look for a
    value the ORIGINAL keeps in memory that this C never creates -- the
    likeliest candidate is a second copy of the buffer pointer, since the
    image writes `str r1, [sp]` (start) AND keeps r5 as the moving cursor,
    while the C has `start = buf; p = buf;` which mwcc coalesces to one value.

(b) THE INT_MIN GUARD IS SPELLED 64-BIT, AND IT IS DEAD CODE.  At +0x00DC the
    image has

        asr    r0, sl, #0x1f       ; r0 = (s32)value >> 31, so 0 or -1
        cmp    r0, #0x80000000
        mov    r0, #1
        cmpeq  sl, #0
        rsbne  sl, sl, #0
        str    r0, [sp, #0xc]      ; neg = 1

    This is EXACTLY the 64-bit twin's `hi == 0x80000000 && lo == 0` guard,
    with `hi` supplied by sign-extending the 32-bit value.  It can never be
    true: `value >> 31` is 0 or -1 and never 0x80000000.  So the 32-bit
    function carries a dead 64-bit test, which is the fingerprint of ONE
    source template compiled twice, once with a 32-bit value type and once
    with a 64-bit one.  The 32-bit spelling `if (value != 0x80000000u)` gives
    a two-instruction `cmp sl, #0x80000000 / rsbne` and is three instructions
    short.  Spellings tried for the 64-bit form, all WORSE:
        (s64)(s32)value != INT64_MIN                   600 bytes, 319 out
        -(s64)(s32)value != (s64)(s32)value            608 bytes, 335 out
        a local s64 v64 = (s32)value, then the compare 600 bytes, 319 out
        ((s32)value >> 31) == (s32)0x80000000 && !value 608 bytes, 326 out
        the same with neg = 1 moved after the guard    600 bytes, 312 out
    (against 592 bytes, 112 out for the 32-bit spelling).  The 64-bit form is
    NOT reachable by writing 64 bits in this one file: every 64-bit spelling
    drags a full 64-bit compare sequence in.  The likely original shape is a
    shared macro or an inline helper whose argument is widened at the call
    site, which this project's single-function compilation model cannot
    express.  Recording it here rather than burning another lane on it.

Both named residues above were declaration errors, not allocation ties:
  (a) the "missing slot" was the by-value descriptor.  It is MSL's 16-byte
      print_format {u8 justification_options, sign_options,
      precision_specified, alternate_form, argument_options, conversion_char;
      int field_width; int precision;}, not an 8-byte Spec8 plus two scalar
      words.  With the real struct the frame, push list and home-area reads
      come out right at once.
  (b) the dead 64-bit guard is literally `if (num != 0x8000000000000000LL)`
      on the 32-bit `long num` (MSL long2str compares against LLONG_MIN).
      It reproduces as written once (a) is fixed.
  Last 2 bytes: the digit pointer is `unsigned char *` (ldrb for *p != '0').
The file is src/matched/func_020929E8.c, a straight transcription of MSL
printf.c long2str; no permuter mutation was needed.  The same transcription
closed the 64-bit twin (src/matched/func_02092C38.c, real entry 0x02092C38),
double2hex (func_02092F0C.c), float2str (func_020934CC.c) and brought
