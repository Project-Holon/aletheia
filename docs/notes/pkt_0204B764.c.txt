func_0204B764 / func_0204B7C8 / func_0204B784: two-instruction scheduling residue
==================================================================================

Closed near miss, not a partial trace.  All three are aggregate struct copies
out of a cell actor, and each is byte-for-byte correct except for the order of
the two address-setup instructions that precede the first ldm/stm pair.

func_0204B764 (32 bytes, 0x0204B764), 20 bytes from actor+0x40 to the caller's
buffer:

  image:  push {r3, lr}
          add  ip, r0, #0x40      <- source address first
          mov  lr, r1             <- then the destination
          ldm  ip!, {r0, r1, r2, r3}
          stm  lr!, {r0, r1, r2, r3}
          ldr  r0, [ip]
          str  r0, [lr]
          pop  {r3, pc}

  mwcc:   push {r3, lr}
          mov  lr, r1             <- destination first
          add  ip, r0, #0x40      <- then the source
          (rest identical)

func_0204B7C8 (40 bytes, 0x0204B7C8) is the same copy of the 36-byte record at
actor+0x1c and fails the same way, at the same two instructions.  func_0204B784
(68 bytes, 0x0204B784) has the mirror-image residue: its source pointer is
already in r4, so the image starts the load (`ldm r4!, {r0, r1, r2, r3}`) and
computes the destination (`add ip, r5, #0x1c`) after it, while mwcc computes the
destination first.

What was tried, all 48 bytes / 32 bytes wrong at exactly those two slots and
identical everywhere else:

  * `*dst = *(struct Dsp *)(actor + 0x40);`
  * source bound to a local first (`struct Dsp *src = ...; *dst = *src;`)
  * a typed `struct Actor { u8 pad[0x40]; struct Dsp dsp; }` member access
  * a temporary struct local, then `*dst = tmp;`
  * casting both sides (`*(struct Dsp *)dst = *(struct Dsp *)(actor + 0x40)`)
  * a `static` copy helper taking (dst, src), inlined into the wrapper
  * `dst + 0` and `(u32)actor + 0x40` spellings of the base arithmetic

mwcc's struct-copy codegen always emits the destination move first here; the
image has the source's address first.  No flag change is permitted (the
compiler is pinned), and the residue is pure instruction scheduling, so these
are parked as notes rather than as source files.  If a later wave finds the
spelling, the three files are two instructions apart from EXACT.

Both functions are leaf-free: no calls, no data relocations, so nothing here is
blocked on evidence -- only on this ordering.

Re-derived in wave 4-2, same verdict, with these further spellings ruled out on
top of the list above (all 40 compiled bytes with the same two-instruction
residue, 8 concrete bytes):

  * the source address bound to a `u8 *` local, to a `void *` local, and to a
    `u32 *` local before the assignment
  * the destination written with an explicit `+ 0`
  * the argument read through a subscript (`((struct Blk *)src)[0]`)
  * `memcpy(dst, (char *)src + 0x1c, 0x24)` with the source bound first - the
    inlined memcpy does not produce the image's sequence either (it uses r0-r2
    and a different order)
  * an intermediate `u32 off = i * 0x28`-style offset local, a `short`/`u16`
    value local, and the destination member access through a typed struct

Stopped at round two: every shape lands on `mov lr, r1` / `add ip, r0, #0x1c`
with mwcc and on the reverse in the image, and the operands are the same
registers, so it is an emission order below the source text, not a C shape.
See also docs/notes/pkt_0204F150.c.txt, docs/notes/pkt_0204F684.c.txt and
docs/notes/pkt_0204F7DC.c.txt - the same hoist-the-address/defer-the-load
pattern, four functions in this region.

SUPERSEDED, wave 13 (2026-09-21)
================================
All three functions above are EXACT.  src/matched/unit_0204B764.c reproduces
the whole 0x0204B764..0x0204B7F0 range as one translation unit: 3 code
sections, 140 bytes laid out, 2 of 2 relocation sites resolved, verdict EXACT
under the default dsi/1.1p1 -O4,p.  The scheduling residue documented above is
a source-shape artefact after all, not an emission order below the source
text: the middle function binds its copy to a NAMED struct local
(`Struct36 s; s = *src; *(Struct36 *)(dst + 0x1c) = s;`) and the two wrappers
cast the base once and assign straight through it, which puts the source
address ahead of the destination move in every one of the three.

Separately, the file had been filed with one per-function header block per
function instead of a single `unit: yes` block with a comma-list of names, so
`manifest --verify` recorded only the LAST of the three and both 0x0204B764
and 0x0204B784 kept reading OPEN in the worklist although the bytes had been
reproduced.  The header now carries the house unit shape and the shard entry
is one `game_unit` row at 0x0204B764.
