WHAT IT IS
----------
A three-way fallback archive load.  Try the caller-supplied id, then the
id func_02013F2C maps for the current record, then a freshly built one,
each through func_02014A20(archive, member, &count, heap); stop at the
first that returns non-NULL, then hand the block plus a byte offset to
func_02014A80 and free it.

The heap argument in every attempt is the seventh stacked parameter's
low halfword masked to 0x7FFF and OR'd with a tag, then narrowed to u16:
the tag's low 16 bits are always zero, so it is dead in the value and
alive only in the codegen.  Note the *address* form for that read,
`add r3, sp, #0x20; ldrh r3, [r3, #8]`, not `ldrh [sp, #0x28]`: the same
"stacked argument reached through a pointer expression" idiom that
func_02017430 needs (see pkt_020173F0's note).

Two levers that were needed to get here, both worth reusing:
  - `id` is a u32 parameter cast to u16 at each call, not a u16
    parameter: that is what produces the `lsls #0x10 / lsrs #0x10` pairs
    at +0x42 and +0x82 rather than a bare `adds r0, r4, #0`.
  - o1 and o2 must be *declared* in the order o2, o1 (which fixes
    r7 = a1's product, r6 = a2's) but *assigned* o1 first (which fixes
    the multiply order).  Declaring-with-initialiser gets one or the
    other, never both; see the "declaration order decides which register
    a local gets" idiom.

RESIDUE 1 (10 bytes) -- the 0x10000000 tag is not pooled
--------------------------------------------------------
    ORIGINAL                       COMPILED
    ldr r5, [pc, #0xa0]            movs r5, #0xe1
    adds r5, r5, #1                lsls r5, r5, #0x1c

The original materialises 0x10000000 as the pool word 0x0FFFFFFF (the
sentinel the *second* block compares against, at 0x02014A0C) plus one.
This front end rematerialises it as movs+lsls and never notices the
pool word it will emit later for the compare.  Tried, all unchanged at
16 bytes: `0x10000000u`, `(u32)0xfffffff + 1`, `(0xfffffff + 1)`, and
binding the sentinel to a local shared by both uses.  Guarding the first
block on the sentinel as well (`a3 != 0 && a3 != 0xfffffff`) is much
worse, 167 bytes: it is not a missing test.
