THE 2 BYTES ARE THE LOOP-INVARIANT CALL, HOISTED
-------------------------------------------------
The note asserts, under "What is NOT in doubt, and is worth keeping":

    DWC_GetGsProfileId(p, tok) is re-called every iteration even though it

    changes the shape, so the original really does write it inside the body.

That is not so.  `temp(tmp=DWC_GetGsProfileId(p, tok))` -- lift the call to a
named local ABOVE the loop and read the local inside it -- is exactly the
hoist the note ruled out, and it takes the function from 170 bytes to 168,
the original's size, without losing either call: the pre-loop `<= 0` guard
call and the hoisted one are still two separate `blx` sites, because the
guard tests the call's value while the hoisted local feeds `id`.  The
original's second `blx #0x20598ec` at +0x5A is the hoisted one, not a
per-iteration one, and the loop body has only the array-record call.

A CAUTION ON THE --types ANNEAL RESULT
---------------------------------------
The anneal run reported a much better intermediate (68 bytes out at 166) and
a best of 105 out at 158, and BOTH are semantically invalid; they are not
usable and are recorded here only so the next lane does not chase them.  The
emitted C reads `tok` in `DWC_GetGsProfileId(p, tok)` BEFORE
`DWC_CreateFriendKeyToken(tok, a1, a2)` fills it, and initialises
`key_ = key` from an uninitialised `key`, having sunk the token construction
into a `do { } while (0)` below both reads.  The scorer cannot see this: an
uninitialised read is still a compile, and dropping a dependency frees the
allocator, which is why it scores well.  This is the failure mode the brief
warns about for `--types` results, and it applies to the block/copy mutations
too, not only to type changes: check the data flow, not just the verdict.

sweep: n/key/id/i reorderings all give 115 or 116, never less.
