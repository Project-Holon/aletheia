THE DIFFERENCE, EXACTLY
-----------------------
In the original, the inner switch lays its blocks out as
[type 0 / default][type 1][type 2] and the type-0 block keeps its own
`strh r0, [r3]` before branching to the shared priority/mosaic trailer:

  0203FE0C  strh r0, [r3]        <- type 0 stores through r3
  0203FE10  b    #0x203fe68
  0203FE14  ...  type 1, address in r2, read value in r1, unk_1a in r3
  0203FE38  b    #0x203fe60
  0203FE3C  ...  type 2, same allocation
  0203FE60  orr  r0, r0, r3, lsl #13     <- shared by types 1 and 2 only
  0203FE64  strh r0, [r2]
  0203FE68  <trailer>

mwccarm 1.1p1 -O4,p instead cross-jumps all three arms.  The type-0 arm
loses its own `strh` and branches straight into the shared store, which
costs exactly one instruction per inner switch, four instructions and
sixteen bytes across the function, and it forces every affine arm's
register allocation to agree with the type-0 arm's (address r3, read
value r2, unk_1a r1) instead of the original's rotation (address r2,
read value r1, unk_1a r3).  The register rotation is a consequence of
the merge, not an independent difference.

WHAT WAS TRIED
--------------
Six shapes, none of which prevents the merge while keeping the block
order:

  1. the C below (case 0 falling into default, macro register access):
     1860 bytes, merge happens.
  2. binding the pre-<<13 value of types 1 and 2 to a named u32 local:
     1860 bytes, identical output.
  3. binding tmpl->unk_1a to a named local at the top of each affine
     arm, to make it the first-defined temporary: 1860 bytes, identical.
  4. a `volatile u16 *` local for the register address, first in the
     affine arms and then in the type-0 arm: 1860 bytes, identical.
  5. `goto` out of the type-0 arm instead of `break`, to give it a
     syntactically distinct successor: 1860 bytes, identical; the goto
     is unified with the break before the cross-jumper runs.
  6. duplicating the type-0 body under a separate trailing `default:`:
     1872 bytes, but register pressure crosses a threshold and the
     prologue grows to `push {r3-r8,sb,sl,lr}` with a stack frame, so
     the whole function diverges.

One experiment is worth recording because it isolates the cause.
Writing the inner arms in source order `case 1, case 2, case 0/default`
compiles to exactly 1876 bytes, the right size, with the four inner
switch regions the only mismatching runs and every other instruction in
the function byte-identical.  With the type-0 arm placed last the
cross-jumper does not touch it: types 1 and 2 still merge with each
other, but type 2 does not merge forward into type 0.  So the merge is
strictly forward and strictly from the earlier block into the later one.
That version is wrong in block order (the original's dispatch falls
through into the type-0 block, which can only happen if that block is
written first) but it proves the merge, not the C, is what is missing.

A follow-up diagnostic separates the two remaining problems.  Compiling the
source order `case 1, case 2, case 0/default` (no merge, exact 1876 bytes)
with `tmpl->unk_1a` additionally bound to a named local at the top of each
affine arm leaves the affine arms still allocated as address r3, read value
r2, unk_1a r1, where the original is address r2, read value r1, unk_1a r3.
The schedule, the instruction sequence and the live-out set are identical;
only the three register names rotate.  So the register rotation is NOT a
consequence of the cross-jump and is not fixed by declaration order either.
Two independent effects remain:

  (a) with the type-0 arm written first, its store is cross-jumped away,
      costing one instruction per inner switch;
  (b) in the affine arms the address and unk_1a registers are transposed
      with the read-value register, in every shape tried.

(b) is the same class of dead end as docs/notes/func_0200EBD0.c.txt: identical
control flow, identical schedule, a pure register-class swap.  Anyone
returning to this function should attack (b) first, since (a) may well fall
out of whatever changes (b).

Two useful facts for whoever picks this up:

  * mwccarm sorts the compare chain of a small switch by case value but
    lays the case blocks out in source order.  Source order 1, 2,
    0/default still emits `cmp #0 / cmp #1 / cmp #2` in that order, only
    the branch targets change.  So the compare order in a listing says
    nothing about source order; the block order does.
  * `case 0:` immediately followed by `default:` is what produces the
    leading `cmp r4, #0 / beq`.  A bare `default:` drops that compare
    and a bare `case 0:` with no default adds a `b` after the chain;
    only the pair reproduces the original's six-instruction dispatch
    falling through into its own block.
