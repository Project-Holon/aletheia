VERDICT: DIFF under `--cc ../2.0/sp2`, 160 bytes compiled against the
original's 160, 44 concrete bytes wrong -- and the INSTRUCTION SEQUENCE is
IDENTICAL, opcode for opcode, in order. Every remaining difference is
REGISTER ALLOCATION. Not filed as a source; recorded here.

What the function is: initialise the 0x1C-byte request object at `o`
(state 0, cap 0x1000, payload pointer, aux word from r3, priority 0x7F,
flag byte 0), then dispatch on the two-field key at the head of `key`
(u8 tag at +0, u16 id at +2), looked up linearly in a 5-entry, 8-byte-
stride table at 0x020A8240 whose live length is the word at 0x020A821C.
A hit calls the entry's handler through `blx`; a miss, a zero count or a
null handler just returns. The table (from 030_0209666C.s) is
  020A8240 4D 00 41 4D 'M',0,'MA'  -> 02070360
  020A8248 4D 00 50 54            -> 02070948
  020A8250 4D 00 41 54            -> 02070830
  020A8258 56 00 41 56            -> 02070BD8
  020A8260 4A 00 41 43            -> 0206EB00
so the tag alphabet is the 0x4D/0x56/0x4A of func_02069E88 and
func_02069C14.

THREE things the derivation established, all load-bearing:

1. The two pool words 0x020A8240 and 0x020A8244 are TWO SEPARATE EXTERNS,
   not one symbol+offset. `ldr r3,[pc,#0x28]` / `ldr r3,[r3,r5]` with
   r5 = i*8 only comes out when the handler column is its own base
   `extern u8 sHandlerFns[]` indexed `*(void(**)(void))(sHandlerFns +
   (i << 3))`, while the key column is indexed normally as
   `sHandlerKeys[i].tag` / `.id`. Modelling the table as ONE array of
   8-byte structs collapses to a single pool word and 110+ wrong bytes;
   modelling the handler column as `void (*[])(void)` indexed `[i*2]`
   gives `lsl r1,r4,#1; ldr [r0,r1,lsl#2]` instead of `ldr [r3,r5]`.
   Exactly one byte-offset expression may appear in the body, or the
   compiler strength-reduces it into a second induction variable
   (`mov r5,ip` + `add r5,r5,#8`) and the function grows to 164 bytes.

2. The two key tests must be `if (...) goto next;` guards, NOT `&&` and
   NOT nested `if`s. Both those spellings let the compiler predicate the
   second test (`ldrheq r0,[r0,#2]` / `cmpeq r2,r0`) where the image keeps
   a second `bne 0x02069CF8`.

3. The FRONT END IS ../2.0/sp2 and this is the "kept branches" tell of
   docs/FRONTEND-PINS.md, measured: with the same C, dsi/1.1p1 -O4,p
   predicates that second guard, lands at 148 bytes against the original's
   160, and is 121 concrete bytes wrong; ../2.0/sp2 keeps the branch,
   lands at exactly 160 and is 44 wrong. The pin was NOT taken, because
   what is left is not a byte the pin explains.

WHAT IS STILL WRONG. The image saves five callee-saved registers
(`push {r3, r4, r5, r6, r7, lr}`, r3 for alignment) and uses r4 for the
key-table base, r5 for the scaled index, r6 for the hoisted tag, r7 for
the count and ip for the loop counter. The build saves three
(`push {r3, r4, r5, lr}`) and spends the caller-saved r3 -- freed by the
early `str r3, [r0, #0x14]` -- on the table base, so every register name
in the body is shifted. Two consequences visible in the diff:
  +003C  original  popls {r3,r4,r5,r6,r7,pc}   build  popeq {r3,r4,r5,pc}
  +0048  original  ldrb r3, [r4, ip, lsl #3]   build  ldrb r0, [r3, lr, lsl #3]
The `ls` versus `eq` on `cmp rN, #0` is the same allocation decision seen
from the condition side, not a signedness difference: `n` as s32 with
`n <= 0` gives `pople` and costs four more bytes, `n` as u32 with `n == 0`
gives `popeq`.

Measured and ruled out, all under the pin, all 160 bytes:
  - all six declaration orders of {tag, i, n}: 44 or 46 wrong, never fewer;
  - hoisting `key->id` into a local (the image RELOADS `ldrh lr,[r1,#2]`
    inside the loop, so it must not be hoisted; hoisting `key->tag` is
    required, since the image loads `ldrb r6,[r1]` once before the loop);
  - moving `n = sHandlerCount` before and after `tag = key->tag` (57 and
    46 wrong respectively);
  - `o->unk14 = a3` first versus in place.
The lever that would move it is whatever keeps r3 from being reused, i.e.
one more value live across the initialisation block. The third parameter
(r2) is not stored anywhere by the image and is written `a2` unused here;
if it is in fact live, that is the first thing to try next.

The C above was reproduced exactly (160 bytes, 44 concrete out under
`--cc ../2.0/sp2`).  ONE change took it to 34, and it is the note's own
prediction that the dispatched handler is not a nullary function:

    THE HANDLER TAKES `o`.  Declaring it `void (**)(Obj *)` and calling
    `(*(void (**)(Obj *))(sHandlerFns + (i << 3)))(o);` makes the object
    pointer live across the whole initialisation block, and the 0x7f/0x1000
    pair at +0014..+0020 becomes BYTE-EXACT (`mov r4, #0x7f` / `strb r4` /
    `mov r4, #0x1000` / `str r4`) where the nullary spelling put both
    constants in ip.  The frame also grows from `push {r3, r4, r5, lr}` to
    `push {r4, r5, r6, lr}`.  44 -> 34.

Passing more arguments is not better: `(o, key, a2, a3)` gives 37, `(o, key)`
gives 34, `(o)` alone gives 34.  So `o` is the load-bearing one and `a2` is
still not evidenced as live.

WHAT IS STILL WRONG, restated against the 34-byte build.  The image's frame is
`push {r3, r4, r5, r6, r7, lr}` -- five real callee-saved registers plus the
r3 alignment pad -- and the loop carries six values (r4 keys base, r5 i<<3,
r6 tag, r7 count, ip index, r1 key).  The build carries the same six but puts
the keys base in `lr` and the index in `r2`, needing only `{r4, r5, r6, lr}`.
Every one of the 34 bytes follows from that: same opcodes, same order, same
size, one fewer callee-saved register.  The `popls` vs `popeq` at +003C is the
same decision seen from the condition side and is NOT a signedness question
(`n < 1` and `n == 0` both give `popeq`, measured).

Ruled out this pass, all 160 bytes, all on top of the `(Obj *)` handler:
  - the handler pointer bound to a named `void (*fn)(Obj *)` local before the
    null test (34);
  - both key tests with the table operand on the LEFT of `!=` (34);
  - `tag` retyped `u32` (34);
  - `tag = key->tag;` before `i = 0;` (34);
  - `if (n < 1) return;` in place of `if (n == 0) return;` (35);
  - the keys base bound to a named `HandlerKey *kt` local, declared first
    (35) and declared after `n` (43);
  - `i = 0;` hoisted to the very top of the function and used as the zero for
    all four zero stores (44 with the nullary handler; not better).

The next lever is still one more value live across the loop, and the two
remaining candidates are (a) the handler's true arity beyond `o` -- something
the CALLEES at 0x02070360 / 0x02070948 / 0x02070830 / 0x02070BD8 / 0x0206EB00

RESOLVED, same pass: BYTE-CORRECT under the pin, parked at MATCH

The "next lever" named two lines above was right, and reading
`src/matched/func_02070BD8.c` (one of the five table handlers, already filed)
settled it: its signature is `void func_02070BD8(struct S *s, u32 a, u8 *src)`,
THREE arguments.  Spelling the dispatch

    (*(void (**)(Obj *, Key *, u32))(sHandlerFns + (i << 3)))(o, key, a2);

takes the function from 34 concrete bytes out to ONE, and `a2` -- written
unused in every earlier spelling -- is indeed live.  Measured arities:
nullary 44, `(o)` 34, `(o, key)` 34, `(o, key, a2)` 1, `(o, key, a2, a3)` 37,
`(o, a2, a3)` 168 bytes SIZE, `(o, a2)` and `(o, a3)` 164 bytes SIZE.

The last byte is the `popls` at +003C, and it IS reachable from C after all --
the earlier reading of it as pure allocation was wrong.  It is the loop's
ENTRY TEST, and it must be written as a comparison against the counter:

    n = sHandlerCount;
    i = 0;
    if (i >= n) return;

`if (n == 0) return;`, `if (n <= 0) return;` and `if (!(n > 0)) return;` all
give `popeq` (1 byte out); `if (n < 1) return;` gives 2.  This is the same
`i >= count` / `bls` lever docs/notes/pkt_0206A19C.c.txt records for
func_0206A2CC's entry test, on a different packet.
