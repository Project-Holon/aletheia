func_021BA168  0x021BA168  40 bytes target, 36 compiled  DIFF
------------------------------------------------------------------------------

    push {r3, r4}; movs r4, #0; movs r1, #0x1c
  loop:
    adds r3, r4, #0 ; muls r3, r1, r3 ; adds r2, r0, r3 ; ldr r2, [r2, #0x30]
    cmp r2, #0 ; bne next
    adds r0, #0x30 ; adds r0, r0, r3 ; pop {r3, r4} ; bx lr
  next:
    adds r4, r4, #1 ; cmp r4, #0x30 ; blt loop
    movs r0, #0 ; pop {r3, r4} ; bx lr

Semantics: scans the 0x30 records of 0x1C bytes starting at +0x30 and returns
the address of the first whose leading word is 0, else 0.  The C in
scratch/ov099/parked/func_021BA168.c reproduces the size and every instruction
multiset, but the compiler homes the `i * 0x1C` product in r2 rather than r3
and so prints the record address as `adds r3, r0, r2` where the original has
`adds r2, r0, r3`.  Two spellings of the address expression
(`p + i * 0x1C + 0x30` and `p + 0x30 + i * 0x1C`) were measured; both give the
same register choice.

    ORIGINAL   adds r3, r4, #0 ; muls r3, r1, r3 ; adds r2, r0, r3
    COMPILED   adds r2, r4, #0 ; muls r2, r1, r2 ; adds r3, r0, r2

Blocking class: codegen, register allocation of the scaled index.  6 bytes out.

------------------------------------------------------------------------------
the shared blocker: 0x0203C3EC
------------------------------------------------------------------------------

ov099 calls 0x0203C3EC from 0x021BF03C and 0x021BF06A with `blx`, so the target
is ARM.  It is not a matched entry, not a symbol of layout/symbols_sdk.json,
and not a `func_` label of arm9's listing, so no class attests it:
`matched` has nothing, and `sole-ref/code` wants a traced function start.  Both
entries turn EXACT by themselves the moment 0x0203C3EC is matched in arm9 --
no source change is needed.

func_021BE384  0x021BE384  54 bytes target  DIFF
------------------------------------------------------------------------------

Two null-guarded releases of the pointers at +0x00 and +0x08 through
sub_020307B0, then two arm9 calls that take the halfword at +0x10 (with
selector 1) and at +0x14 (with selector 6) twice each.

Everything matches but the double truncation of the field before the call.
The original converts the same word twice, once per argument:

    ORIGINAL   ldr r2, [r4, #0x10] ; lsls r1, r2, #0x10 ; lsrs r2, r2, #0x10
               lsls r2, r2, #0x10 ; lsrs r1, r1, #0x10 ; lsrs r2, r2, #0x10
    COMPILED   ldr r2, [r4, #0x10] ; lsls r1, r2, #0x10 ; lsrs r1, r1, #0x10
               adds r2, r1, #0                    ; lsls r0, r0, #0x10 ; lsrs r0, r0, #0x10

so the compiler in the original did not reuse the already-truncated first
argument for the second.  Measured spellings: `s->f10` with `u16` parameters,
and explicit `(u16)s->f10, (u16)(u16)s->f10` double casts; both fold.

Blocking class: codegen, redundant-conversion elimination.  8 bytes out.

compiles to 20 bytes against the original's 28 and 13 concrete bytes differ:
1.1p1 at -O4,p folds the `v == 3 || v == 4 || v == 5` chain into a range test

    COMPILED   subs r0, r0, #3 ; cmp r0, #2 ; bhi

it is worth nothing until 0x0203C3EC is attested, so it is parked rather than
spent on.
