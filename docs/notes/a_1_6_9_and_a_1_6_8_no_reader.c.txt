a/1/6/9 and a/1/6/8 (archive ids 169 and 168): no reader exists in the image
===========================================================================

Not a near miss and not a partial trace: this is a closed negative result, so
that the next agent does not spend another pass looking for an accessor that
is not there. It also records the two scans that were needed to make the
result trustworthy, because the obvious first scan is not sufficient.

Why a `bl` scan alone is not enough
-----------------------------------

214 (a/2/1/4) does have a reader, func_02168800 in ov010, and it is invisible
to any scan built on call instructions:

  02168800  ldr  r3, pool_02168808     /* = 0x02048F4C */
  02168802  adds r2, r1, #0
  02168804  movs r1, #0xd6             /* 214 */
  02168806  bx   r3

A one-section-per-function compiler cannot branch directly to another
function, so a tail call is always a pool word and a `bx`
(docs/idioms/tail-call-is-a-pool-word-and-bx.md). The fix is to enumerate, per
region, every pool word whose value is one of the twelve entry points above,
then every `bx` that reads one. Image-wide that yields exactly six such
thunks:

  arm9  0x02019B94 -> 0x02048F4C with id 0x11 (17)
  arm9  0x0201B764 -> 0x02048F4C with id 0x13 (19)
  arm9  0x0202A3AC -> 0x02048F4C with id 0x5C (92)
  arm9  0x0202A3BC -> 0x02048F4C with id 0x5D (93)
  ov010 0x02168800 -> 0x02048F4C with id 0xD6 (214)
  ov021 0x021BE148 -> 0x02048F4C with id 0xB3 (179)

None of them carries 168 or 169.

Third check: no immediate anywhere
----------------------------------

Independently of the call graph, every `mov`/`movs`/`movw` of #0xA8 or #0xA9
in the image was enumerated (185 sites, including the ones that only appear
as `.inst.n`/`.inst.w` with the mnemonic in the trailing comment, which a
naive parse of the listings drops). Every one of them is either a `__LINE__`
argument to the allocator at 0x02030734, a message id, or a struct offset;
none is in a function that touches the archive surface at all. A data table
of archive ids was looked for too, by scanning arm9 and every decompressed
overlay for 168/169 adjacency as u16 or u32: the only two hits are runs of
consecutive integers at 0x0209E98E and 0x0209EDC8, index sequences rather
than id tables.

What this means for the two archives
------------------------------------

a/1/6/9 (951 x 16 bytes) and a/1/6/8 (315 group lists) are, byte for byte,
the same pair of formats as a/2/1/4 and a/2/1/5, whose reader was found and
matched this pass (src/matched/func_02168800.c, src/matched/func_0216880C.c,
and the field decoder func_021684E8 that names every field). Per-offset
statistics agree across the pair:

  a/2/1/4  species max 645, move max 556, EV mask max 56 (popcount <= 4),
           nature max 23, item max 564, +14/+15 always zero
  a/1/6/9  species max 488, move max 466, EV mask max 52 (popcount <= 3),
           nature max 24, item max 327, +14/+15 always zero

and both group tables index their partner cleanly: a/1/6/8's member ids reach
950 against a/1/6/9's 951 records, a/2/1/5's reach 988 against a/2/1/4's 1000,
with zero out-of-range ids in either.

So the field map is settled by structural identity with an attested reader,
while the domain question "which facility" has no code answer in Black. The
honest statement is: same record type, no reader, unreferenced data. Do not
re-run the scans above; extend the search instead (the ARM7 image, or the
Download Play child binaries under extract/dl_rom/, neither of which is
disassembled in this tree) if the question is worth reopening.
