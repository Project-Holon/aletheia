REFUSED for this function, and the byte evidence points the other way.

The whole first 0xB0 is byte-exact under the pin except +0x00A4 (`add r0, r0,
r1` vs `add r0, r1, r0`); swapping the source to `(v1 + v0 * 3) >> 2` does not
move it, the front end normalises the commutative add, so that one is a
scheduling artefact of the real hole, not a spelling.

The real 4-byte hole is at +0x00D4, and it is the "kept branches" tell of
docs/FRONTEND-PINS.md RUNNING BACKWARDS. The `two:` block's u32 arm is four
instructions, inside the predication budget of
docs/idioms/an-arm-guard-block-of-five-instructions-or-fewer-is-predicated.md:

  addeq r1, r0, r3, lsl #2    bne  #0x207060c

=== 2026-09-21 (later run): the pin IS right, 256 bytes, 3 concrete bytes out ===

The earlier "NOT pinnable" verdict above is WRONG and is superseded. Under
`--cc ../2.0/sp2 --arm -O4,p -proc arm946e` the function now compiles to
exactly 256 bytes with only THREE concrete bytes differing, all in the `two:`
block. Everything from +0x0000 to +0x00D0 and from +0x00EC to the end is
byte-for-byte identical.

Three levers found this run, each worth carrying:

  1. `add r0, r0, r1` at +0x00A4 (the weighted average's accumulate) is NOT a
     commutative-normalisation artefact.  Spelling the quad tail as
         v0 *= 3; v0 += v1; return v0 >> 2;
     gives the image's `add r0, r2, r2, lsl #1` / `add r0, r0, r1` under BOTH
     front ends.  `(v0 * 3 + v1) >> 2` as one expression gives `add r0,r1,r0`.
  2. In the `two:` block the u32 arm must NOT compute its own pointer and then
     load both values off it: mwcc merges those into `ldm r1,{r0,r1}`.  Load
     one value by subscript off `base` and the other through the pointer.
  3. The s16 arm must be spelled with a SEPARATE pointer local and a SEPARATE
     byte-offset local, in that order, and v0 taken off the offset while v1 is
     taken off the pointer.  This is what put the register allocation right and
     took the residue from 7 differing bytes to 3.

Best body (`two:` block only; everything above it is the C already recorded in
this note, with lever 1 applied to the quad tail):

    two:
        w = base + idx;
        if (!(flags & 0x10000000)) {
            v0 = base[idx];
            v1 = *(u32 *)((char *)w + 4);
        } else {
            s16 *g = (s16 *)base + idx;
            u32 o = idx << 1;
            v0 = *(s16 *)((char *)base + o);
            v1 = g[1];
        }
        return (v0 + v1) >> 1;

RESIDUE, one coupled decision, three bytes:

      offset   ORIGINAL                       COMPILED (../2.0/sp2)
      +00D4    addeq r1, r0, r3, lsl #2       add r1, r0, r3, lsl #2
      +00E4    add   r1, r0, r3, lsl #1       lsl r2, r3, #1
      +00E8    lsl   r2, r3, #1               add r1, r0, r3, lsl #1

  The +0x00D4 `add` is the hoisted `w = base + idx`.  Hoisting it out of the
  `if` is exactly what buys the predication of the u32 arm's two loads (leaving
  it inside the arm makes 2.0 branch the whole arm and costs 4 bytes), but the
  hoisted statement itself is then emitted UNPREDICATED, while the image has it
  `eq`.  The +0x00E4/+0x00E8 swap is the scheduler putting the shorter-latency
  `lsl` first; it is the same decision, because the two blocks are laid out
  around the one branch.
