The cluster as a whole is now written up in docs/families/cluster_02098B44.h:

  0x0209A7A8  608 B  MSL ldexp() + scalbn()    EXACT*  src/matched/func_0209A7A8.c

func_0209A524 was EXACT on the first compile once `_dgr` (the name mwccarm
emits for a soft-double `>` test) was pinned to 0x0209B864 (__dcmp_2) in the
symbols: block; the body is upstream fdlibm floor() transcribed unchanged,
identified from the pool by huge = 1.0e300 (0x7E37E43C_8800759C) and the
0xBFF00000 that the |x|<1, x<0 arm returns.

func_0209A7A8 needed two changes from the upstream transcription, both of them
general lessons for this library region and both recorded in the family header:

  1.  `if (ok) { ...body... } return x;` compiles 4 bytes SHORT, because the
      compiler shares the one epilogue; the image duplicates the `return x`
      epilogue, which is what `if (!ok) return x;` at the top of the function
      produces.  Size went 608-against-612 correct at that point.
  2.  With the size right, exactly TWO concrete bytes differed, at +0x006C:
      image `orrs r0, r1, r0`, compiled `orrs r0, r0, r1`.  That is the
      commutative-operand-order idiom: the accumulator is the second operand,
      so the subnormal test is spelled `(lx | (hx & 0x7fffffff)) == 0` and NOT
      the `((hx & 0x7fffffff) | lx) == 0` upstream fdlibm writes.  Swapping the
      two operands took it straight to all-bytes-correct.  Anyone transcribing
      another fdlibm routine into this window from the public source will hit
      this same byte pair.

EXACT* on 0x0209A7A8 is an extent artefact only: the printed extent 612 runs
4 bytes past the compiled 608 because the NEXT function's home-area push at
0x0209AA08 (sin's, already covered by src/matched/unit_0209AA08.c) has no label
of its own.  All 608 compared bytes match and all 12 relocations resolve.
