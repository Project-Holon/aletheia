WHAT IT IS.  The per-texture-row setup of the 3D billboard rig: it is the
first thing both dispatchers call (src/matched/func_02053044.c and
src/matched/func_0205312C.c call it on `obj->f2c + index * 0x14`, so its one
argument is a 0x14-byte texture row), and it writes five geometry-engine
registers from that row:

    0x040004A8  TEXIMAGE_PARAM   one packed word, built below
    0x040004AC  PLTT_BASE        row->pltt >> (4 - (fmt == 2))
    0x04000440  MTX_MODE         3 (texture), then 1 at the end
    0x04000454  MTX_IDENTITY     0
    0x0400046C  MTX_SCALE        three words: sx<<12, sy<<12, 0

The TEXIMAGE_PARAM word is assembled from `row->addr >> 3` plus SIX bitfields
of the row's word at +0x0c, each one an equal-amount `lsl`/`lsr` pair in the
image, which is the bitfield tell (docs/idioms/shift-pair-with-no-matching-
type-is-a-bitfield.md; a mask would fold to `ands`):

    bits  0..3   -> word bits 26..29   texture format
    bits  4..7   -> word bits 20..22   size S
    bits  8..11  -> word bits 23..25   size T
    bits 12..13  -> word bits 16..17   repeat/flip S
    bits 14..15  -> word bits 18..19   repeat/flip T
    bit  16      -> word bit  29       colour-0 transparent
    plus a constant `orr ip, ip, #0x40000000` (bit 30, TexCoord transform).

The `cmp lr, #2` / `moveq r1,#1` / `movne r1,#0` / `rsb r1, r1, #4` quartet
at +0x6C is `4 - (fmt == 2)`, i.e. the palette base is shifted by 3 for the
4-colour format and by 4 otherwise.  The bytes give no other reading.

THE RESIDUE IS PURE REGISTER NAMING, and the instruction stream is otherwise
identical to the image one for one, +0x00 through the pool, with only three
instructions transposed (+0x30/+0x34/+0x3C, the `lsl #0xf` and `lsl #0x12`
against the `lsr #0x1c`).  The permutation is consistent:

    image ip -> compiled lr  x5      the running TEXIMAGE_PARAM accumulator
    image r3 -> compiled ip  x4      the 0x040004A8 pool pointer
    image r1 -> compiled r0   x4     the MTX_SCALE value
    image lr -> compiled r3  x3      the format field, live to the `cmp`

Two shapes are already RIGHT and must be kept:
  * `struct TexW w = p->w;` as a struct copy.  That is what produces the
    `str r7, [sp]` at +0x10, a dead store to the one spilled word the frame
    holds (docs/idioms/a-dead-store-to-a-spilled-local-survives-when-the-
    second-assignment-recomputes.md).  Reading the word as a plain u32 loses
    it.
  * `sx` and `sy` bound to locals BEFORE the three MTX_SCALE stores.  The
    image loads both halfwords back to back (`ldrh r1,[r0,#0x10]` /
    `ldrh r2,[r0,#0x12]` at +0xA4/+0xA8); writing `p->sx` and `p->sy` inline
    interleaves load and store and is worth 18 bytes (61 out instead of 43).
    Same lever as shape 4 of src/matched/func_02054718.c.
  * `int tmp = (p->addr >> 3) | ((u32)w.fmt << 26);` lifted out of the `|`
    chain -- the permuter's own `temp(...)`, worth 2 bytes.
