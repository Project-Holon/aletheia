1. What func_02060CD0 is
------------------------

The expanded-heap resize primitive of the NNS-shaped heap library block.  It
takes (heap, block, newsize), reads the block's 0x10-byte header at
block-0x10, and:

  - newsize == current size      -> return the size unchanged;
  - newsize >  current size      -> the "grow" arm: find the free block whose
    header sits exactly at block+oldSize, unlink it, absorb it, re-split the
    tail with func_020607E8(magic 0x4652) + func_020607B8, and zero the newly
    exposed bytes with MIi_CpuClear32 when the heap's flag word at +0x20 has
    bit 0 set;
  - newsize <  current size      -> the "shrink" arm: hand the tail extent
    {block+newsize, block+oldSize} to func_02060B6C, which splices it into the
    free list, and put the old size back if that call reports no merge.

Everything except two residue classes below reproduces exactly at the right
addresses with the right operands; the six relocation sites all resolve as
`label`.

    while-with-&& (both conjunct orders), for-loop with empty body,
    do/while with the bound test as the guard, do/while guarded by

3. What was learned that is not in the brief (also useful for the next agent)
-----------------------------------------------------------------------------

  - Declaration order fixes the callee-saved register map here, not liveness:
    declaring the loop cursor first, then the saved size, then the header
    pointer (`node; oldSize; hdr;`) is what puts node in r6, oldSize in r7 and
    hdr in r8 and matches the original's push list and every `mov r1, r6`-style
    operand.  Any other order shifts them and moves the whole function.

  - A u8 cast on a struct field to keep its mask: `((u8)heap->field_20 & 1)`
    emits `ldr r0, [r5, #0x20]; and r0, r0, #0xff; tst r0, #1`.  Writing
    `heap->field_20 & 0xff & 1` folds to a bare `tst r0, #1` and loses four
    bytes.

  - `hdr->size` read a second time in the sibling arm is NOT re-read: mwcc
    forwards the value it loaded for the first comparison.  A single
    `*(volatile u32 *)((u8 *)hdr + 4)` on the second read restores the fresh
    `ldr r1, [r8, #4]` (4 bytes) and is the only spelling found that does.

  - Two 2-word scratch pairs in one function are fine as int[2] (the register
    pressure keeps mwcc from caching either address); the two-scalar trick
    below is only needed where the address would otherwise be cached.

  - (Found while closing 0x02060E30, and worth trying on any function that is
    4 bytes long) mwcc caches the address of a stack object in a callee-saved
    register across an intervening call when both call sites name the SAME
    object, even for `sp + 0` which it can rematerialise for free.  Splitting
    the scratch pair into two separate scalars makes the two addresses
    different objects to its alias analysis, so each site rematerialises
    `add rN, sp, #0` and the shorter form comes out.  If a 4-byte "extra mov"
    ever shows up before a call, look for two sites naming one object's
    address.  The stack-order idiom is what lets the second site spell the
    base as `&firstMember - 1`.


4. What would close func_02060CD0
---------------------------------

Only the free-list walk's codegen shape (a) and the two register/schedule
residues (b) and (c).  (a) needs the C form whose `if (!B) exit` region mwcc
if-converts -- i.e. the source's loop must end the predicated body with the
back edge, which in every form tried either adds a branch or forces the
condition to be retested at the bottom.  A `while (node != 0 && node != end)`
written over a *pointer* bound of a struct type declared with the same layout,
a loop expressed with an explicit `label:` + `goto` back edge, or the sibling
library's own idiom (if the NNS source spelling is known) are the untried
ground.  (b) and (c) are allocation-only and should move with (a): the same
one-shape change that fixes the loop also decides which of r0/r1/r2
`info[0]`, `info[1]` and `remain` land in.

7. Second reading -- the residue is a branch fold mwcc will not make
-------------------------------------------------------------------

Still open.  Same pinned configuration (dsi/1.1p1, -O4,p, -proc arm946e,
ARM); the frontier C is now in src/pending/func_02060CD0.c (row 1 of the
table below) rather than only at the bottom of this note.

Method, because it is the part that is new: the loop was taken out of the
function and attacked in an isolated micro-harness -- a two-field struct
and one function `int f(struct MBlock *node, unsigned int end)` whose body
is the loop and nothing else -- so each spelling's codegen can be read
with objdump at once, and the spelling space could then be swept
mechanically instead of by vocabulary.  The harness reproduces every shape
section 2 records, which is the check that it is faithful; the two that
matter are quoted below.

New measured facts:

(a) The predicated chain IS reachable, and what decides it is the number
    of exits from the loop.

        if (node != 0) {
            while (1) {
                if ((u32)node == end) break;
                node = node->next;
            }
        }

    compiles to

        cmp  r6, #0
        beq  EXIT
        cmp  r6, r0
        ldrne r6, [r6, #0xc]
        bne  HEAD

    i.e. the guard's branch is gone and the UNCONDITIONAL back edge became
    the conditional one, reading the guard's flags.  mwccarm does this
    because the `break` is the loop's only exit, so it can treat it as the
    loop's own continuation test.  In the real function that form is 348
    bytes: exactly one instruction short, and the missing one is the
    `cmpne r6, #0`.

    The moment the loop has a second exit -- a second `break`, a
    `goto out`, or a real loop condition -- the same guard is emitted as
    an explicit branch instead and no predication happens:
    `while (node != 0) { if ((u32)node == end) break; node =
    node->next; }` is 356 bytes, 239 bytes differing.

    That is precisely the trap this residue sits in.  The original's loop
    has TWO tests and ONE branch, which is the single-exit shape, but the
    second test is on the value the advance produces, so it has to be its
    own statement, and its own statement is a second exit.

(b) The form that does produce the predicated chain AND a test of the
    advanced node is one instruction too long:

        while (node != 0) {
            if ((u32)node == end) break;
            node = node->next;
            if (node == 0) break;
        }

        cmp  r6, #0
        beq  EXIT
        cmp  r6, r0
        ldrne r6, [r6, #0xc]
        cmpne r6, #0
        beq  EXIT
        bne  HEAD

    356 bytes.  Everything the original has is here, byte for byte, plus
    one `beq EXIT` whose target is the fall-through of the `bne` -- the
    two branches are complementary on the same flags, so the fold the
    original shows is a redundant-branch deletion, and 1.1p1 at -O4,p
    does not perform it.  Writing the second test as the loop's condition
    instead (`do { ... } while (node != 0)`, or `while (node != 0)` with
    the first `break`) loses the other half: the predication goes and the
    back-edge `cmp r6, #0` stays unpredicated, 356 bytes again.
    So the two halves of the original's shape are reachable, never both.

(c) The closest spelling by byte count is still section 2's do/while with
    the guard on the `if`: 352 bytes, 30 bytes differing, and its one
    wrong instruction is the same `cmp r6, #0` in the slot the original
    has `cmpne r6, #0` in.  It is still not the source -- it spins when
    node == end -- so it is documented here and not filed.

(d) Sweep of the whole shape space.  4266 generated loop spellings (nine
    wrappers -- while, for, do/while, do/while(1), while(1), for(;;),
    do/while(node != 0), do/while(node != end), a labelled block -- x two
    outer guards (a leading `if (node != 0)` and none) x about 230 bodies,
    the bodies being every permutation of the three statements "test
    node == end", "test node == 0" and "advance" in five break, two goto,
    four `||`, one `&&` and two `continue` spellings plus four-statement
    combinations), compiled in the micro-harness and grep'd for the
    original's closing pair, a predicated `cmpne rX, #0` immediately
    followed by its `bne`.  Zero hits; 394 of the 4266 are CCERR, the
    `goto` bodies in wrappers with no `out:` label to jump to.  The shape
    simply does not occur in that space.

(e) Not a pragma and not a qualifier.  `#pragma peephole off` and `on`,
    `#pragma ipa off` and `on`, `#pragma opt_dead_code off`,
    `#pragma opt_common_subs off`, `#pragma optimization_level 3` and `4`,
    `#pragma inline on` are each byte-identical to no pragma, for both the
    `&&` form and the break form.  `volatile` on the node advance, a
    pointer cast of the bound, reading the word through a union (the
    sentinel/null idiom), an `if (0) break;` probe for the fold, and an
    inline helper for the test or for the advance all change nothing --
    the helpers are not inlined at all under this front end, they stay
    separate sections, and the probe's dead second exit is deleted before
    it can reach the if-converter.

(f) The idiom this leaves behind, which is worth knowing on its own:
    a `while (1)` / `for (;;)` loop with exactly ONE `break` compiles that
    break into the loop's continuation condition and predicates the body;
    with two exits the same compiler emits the break as a branch and
    predicates nothing.  A spelling that is four bytes short of an if-
    converted loop is usually this, not a missing statement.

Verdict: still open, and now for a reason that is specific rather than
lexical.  The original asks mwccarm 1.1p1 to delete an exit branch whose
target is the fall-through of the complementary back-edge branch and to
keep the predicated chain that branch reads, and this front end never does
that: it either predicates a break's whole region when the break is the
loop's single exit, or it emits both branches.  A C spelling in which the
advanced-node test is not an exit cannot be written, because the value it
tests is produced by the statement the predication has to cover.
