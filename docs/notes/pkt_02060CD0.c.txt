1. What func_02060CD0 is
------------------------

The expanded-heap resize primitive of the NNS-shaped heap library block.  It
takes (heap, block, newsize), reads the block's 0x10-byte header at
block-0x10, and:

  - newsize == current size      -> return the size unchanged;
  - newsize >  current size      -> the "grow" arm: find the free block whose
    header sits exactly at block+oldSize, unlink it, absorb it, re-split the
    tail with func_020607E8(magic 0x4652) + func_020607B8, and zero the newly
    exposed bytes with MIi_CpuClear32 when the heap's flag word at +0x20 has
    bit 0 set;
  - newsize <  current size      -> the "shrink" arm: hand the tail extent
    {block+newsize, block+oldSize} to func_02060B6C, which splices it into the
    free list, and put the old size back if that call reports no merge.

Everything except two residue classes below reproduces exactly at the right
addresses with the right operands; the six relocation sites all resolve as
`label`.

3. What was learned that is not in the brief (also useful for the next agent)
-----------------------------------------------------------------------------

  - Declaration order fixes the callee-saved register map here, not liveness:
    declaring the loop cursor first, then the saved size, then the header
    pointer (`node; oldSize; hdr;`) is what puts node in r6, oldSize in r7 and
    hdr in r8 and matches the original's push list and every `mov r1, r6`-style
    operand.  Any other order shifts them and moves the whole function.

  - A u8 cast on a struct field to keep its mask: `((u8)heap->field_20 & 1)`
    emits `ldr r0, [r5, #0x20]; and r0, r0, #0xff; tst r0, #1`.  Writing
    `heap->field_20 & 0xff & 1` folds to a bare `tst r0, #1` and loses four
    bytes.

  - `hdr->size` read a second time in the sibling arm is NOT re-read: mwcc
    forwards the value it loaded for the first comparison.  A single
    `*(volatile u32 *)((u8 *)hdr + 4)` on the second read restores the fresh
    `ldr r1, [r8, #4]` (4 bytes) and is the only spelling found that does.

  - Two 2-word scratch pairs in one function are fine as int[2] (the register
    pressure keeps mwcc from caching either address); the two-scalar trick
    below is only needed where the address would otherwise be cached.

  - (Found while closing 0x02060E30, and worth trying on any function that is
    4 bytes long) mwcc caches the address of a stack object in a callee-saved
    register across an intervening call when both call sites name the SAME
    object, even for `sp + 0` which it can rematerialise for free.  Splitting
    the scratch pair into two separate scalars makes the two addresses
    different objects to its alias analysis, so each site rematerialises
    `add rN, sp, #0` and the shorter form comes out.  If a 4-byte "extra mov"
    ever shows up before a call, look for two sites naming one object's
    address.  The stack-order idiom is what lets the second site spell the
    base as `&firstMember - 1`.


4. What would close func_02060CD0
---------------------------------

Only the free-list walk's codegen shape (a) and the two register/schedule
residues (b) and (c).  (a) needs the C form whose `if (!B) exit` region mwcc
if-converts -- i.e. the source's loop must end the predicated body with the
back edge, which in every form tried either adds a branch or forces the
condition to be retested at the bottom.  A `while (node != 0 && node != end)`
written over a *pointer* bound of a struct type declared with the same layout,
a loop expressed with an explicit `label:` + `goto` back edge, or the sibling
library's own idiom (if the NNS source spelling is known) are the untried
ground.  (b) and (c) are allocation-only and should move with (a): the same
one-shape change that fixes the loop also decides which of r0/r1/r2
`info[0]`, `info[1]` and `remain` land in.
