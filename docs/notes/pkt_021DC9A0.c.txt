func_021ECB60 @ 0x021ECB60 (ov170, Thumb) - SETTLED, EXACT, 20 bytes.
--------------------------------------------------------------------------------
The previous lane had 6 bytes of 20 out and called it "pure register naming":
the image forms `p + i` in r3 and the pooled constant in r1, the compiler
did the reverse.

It was not the naming.  The callee func_021EC060 takes THREE arguments, and
the forwarded byte is argument 1, not argument 0, so the value must land in
r1 and the incoming r2 must be left alone -- which forces the sum into r3:

    void func_021ECB60(char *p, int i, int f)
    {
        func_021EC060(p, *(unsigned char *)(p + i + 0x3DD2), f);
    }

The arity is readable straight off the image, in the sibling caller at
loc_021ECABE (0x021ECABE):

    ldr  r0, [r5, #0x2c]      ; argument 0
    movs r2, #1               ; argument 2 = 1
    adds r1, r0, r4           \
    ldrb r1, [r1, r7]          > argument 1 = the table byte
    bl   func_021EC060

and inside func_021EC060 the first thing it does is `cmp r2, #1`, so r2 is
a real third argument, not a scratch value.  In func_021ECB60 itself r2 is
never written: it arrives from the caller and is passed straight through.

RULE, for the next tail call that comes out "one register name wrong":
count the LIVE argument registers at the `bx`/`bl`, not the ones you think
the call needs.  If r0, r1 and r2 are all set at the call and one of them
was never written in the function, the callee has an argument you have not
declared, and the register difference is arity, not allocation.  A one-,
two- and three-argument spelling were all compiled here; only the three
argument one reproduces r3 (43 18 / 02 49 / 59 5c / 02 4b / 18 47).

Free lessons measured this lane (all of them cost a DIFF first).
--------------------------------------------------------------------------------
1. `blo`/`bhs` where you wrote a signed test, but the arms are in the right
   order: make the compared value `unsigned`.  Three independent instances
   this lane (021DD314, 021EDB1C, 021DF128); the signed spelling always
   produces `blt`/`bge` or the opposite-arm opcode and never matches.
2. `if (f(x)) return B; return A;` gives the arms in the ORDER the image
   shows only when the `then` block is the fall-through the image has.
   func_021E2140 wanted `if (f(p) == 0) return field; return 8;` -- the
   `if (f(p)) ...` spelling compiled the same 20 bytes with `beq` where the
   image has `bne` and moved the arms.
3. A 4-bit field is a bitfield, not a mask.  `p[0x1c] & 0xf` compiles to
   `movs r1,#0x1c; ldrsb ...; ands`, i.e. eight bytes of noise; a
   `struct { unsigned char a[0x1c]; unsigned char f : 4; }` gives the
   image's `ldrb r1,[r0,#0x1c] / lsls r1,#0x1c / lsrs r1,#0x1c`.
4. A `char` field the image reads with `ldrb` must be `unsigned char` in
   the source, or mwccarm emits `ldrsb` (func_021E78F4, func_021ED904).
5. Callees INSIDE the region need a `symbols:` entry with the region token
   or match.py refuses the call outright with "ISA conflict ... the source
   declares arm, the image says thumb".  Four functions failed on this and
   nothing else.  Callees outside the region (ARM9, other overlays) are
   witnessed by the cross-region branch index and need no entry -- but a
   pool word to an in-region Thumb function does.
6. Pool words that point at DATA are declared with a `data` token, not
   `thumb` (`g_021EFA28  0x021EFA28  data  ov170`), and resolve cleanly.

Two independent type facts, exactly the kind O33/O56 kept finding:

    int func_021DD210(unsigned char *p, unsigned a, unsigned b)
    {
        int d = a - b;
        if (d < 0)
            d = -d;

        return d < ((unsigned)p[0x15] >> 1);
    }

   compiles EXACT, so the two spellings are equivalent here.

func_021DEB14 @ 0x021DEB14 - SETTLED, EXACT, 44 bytes (new).
--------------------------------------------------------------------------------
The whole function is one signed-char lane with two truncations, and the
truncation pairs (`lsls rX,#0x18 / asrs`) are what the source has to make real:

    unsigned char func_021DEB14(unsigned char *p, int a)
    {
        signed char v = (signed char)p[0x19] + a;
        if (v < 0)
            v = v + (signed char)p[0x15];
        else if (v >= p[0x15])
            v = v - (signed char)p[0x15];
        return v;
    }

`v` being `signed char` is load-bearing: it is what emits the `lsls/asrs` pair in
each arm, and the return type `unsigned char` is what emits the final
`lsls r0,r2,#0x18 / lsrs r0,r0,#0x18`.  The `>=` arm compares `int v` against the
UNSIGNED byte (`blt` on the skip), and the `(signed char)` cast on the +0x15 byte
is what makes mwcc emit `ldrsb` in the first arm while the second arm keeps
`ldrb` plus an explicit sign-extend, which is the image.  A named `signed char f
= (signed char)p[0x15];` copy before the if is 30 bytes out - do not cache it.
