func_021DD314 @ 0x021DD314 (ov170, Thumb) - SETTLED, EXACT, 28 bytes.
--------------------------------------------------------------------------------
The previous lane had 1 byte of 28 out: the image branches `bhs`, the
compile branched `blo` from `if (b < 0x1e) {...} else {...}`.

It is a signedness question, and the answer is that the tested parameter is
UNSIGNED.  With `int b` the same if/else compiles the inverted branch as
`blo`; with `unsigned b` mwccarm emits `bhs`, which is the image.  Nothing
about the block order or the spelling changes the opcode:

    void func_021DD314(char **p, int a, unsigned b)
    {
        if (b < 0x1eU)
            func_02007664(*(int *)(*p + 4), a, b);
        else
            func_0201A9C8(*(int *)(*p + 8), b - 0x1eU);
    }

Measured on the same body: signed -> 03 da (blo), unsigned -> 03 d2 (bhs).
Nine spellings were compiled; only the unsigned one reaches EXACT, and the
`if (b >= 0x1e) {second} else {first}` rewrites change the block layout and
lose more bytes than the one they fix.

--------------------------------------------------------------------------------
func_021ECB60 @ 0x021ECB60 (ov170, Thumb) - SETTLED, EXACT, 20 bytes.
--------------------------------------------------------------------------------
The previous lane had 6 bytes of 20 out and called it "pure register naming":
the image forms `p + i` in r3 and the pooled constant in r1, the compiler
did the reverse.

It was not the naming.  The callee func_021EC060 takes THREE arguments, and
the forwarded byte is argument 1, not argument 0, so the value must land in
r1 and the incoming r2 must be left alone -- which forces the sum into r3:

    void func_021ECB60(char *p, int i, int f)
    {
        func_021EC060(p, *(unsigned char *)(p + i + 0x3DD2), f);
    }

The arity is readable straight off the image, in the sibling caller at
loc_021ECABE (0x021ECABE):

    ldr  r0, [r5, #0x2c]      ; argument 0
    movs r2, #1               ; argument 2 = 1
    adds r1, r0, r4           \
    ldrb r1, [r1, r7]          > argument 1 = the table byte
    bl   func_021EC060

and inside func_021EC060 the first thing it does is `cmp r2, #1`, so r2 is
a real third argument, not a scratch value.  In func_021ECB60 itself r2 is
never written: it arrives from the caller and is passed straight through.

RULE, for the next tail call that comes out "one register name wrong":
count the LIVE argument registers at the `bx`/`bl`, not the ones you think
the call needs.  If r0, r1 and r2 are all set at the call and one of them
was never written in the function, the callee has an argument you have not
declared, and the register difference is arity, not allocation.  A one-,
two- and three-argument spelling were all compiled here; only the three
argument one reproduces r3 (43 18 / 02 49 / 59 5c / 02 4b / 18 47).

Free lessons measured this lane (all of them cost a DIFF first).
--------------------------------------------------------------------------------
1. `blo`/`bhs` where you wrote a signed test, but the arms are in the right
   order: make the compared value `unsigned`.  Three independent instances
   this lane (021DD314, 021EDB1C, 021DF128); the signed spelling always
   produces `blt`/`bge` or the opposite-arm opcode and never matches.
2. `if (f(x)) return B; return A;` gives the arms in the ORDER the image
   shows only when the `then` block is the fall-through the image has.
   func_021E2140 wanted `if (f(p) == 0) return field; return 8;` -- the
   `if (f(p)) ...` spelling compiled the same 20 bytes with `beq` where the
   image has `bne` and moved the arms.
3. A 4-bit field is a bitfield, not a mask.  `p[0x1c] & 0xf` compiles to
   `movs r1,#0x1c; ldrsb ...; ands`, i.e. eight bytes of noise; a
   `struct { unsigned char a[0x1c]; unsigned char f : 4; }` gives the
   image's `ldrb r1,[r0,#0x1c] / lsls r1,#0x1c / lsrs r1,#0x1c`.
4. A `char` field the image reads with `ldrb` must be `unsigned char` in
   the source, or mwccarm emits `ldrsb` (func_021E78F4, func_021ED904).
5. Callees INSIDE the region need a `symbols:` entry with the region token
   or match.py refuses the call outright with "ISA conflict ... the source
   declares arm, the image says thumb".  Four functions failed on this and
   nothing else.  Callees outside the region (ARM9, other overlays) are
   witnessed by the cross-region branch index and need no entry -- but a
   pool word to an in-region Thumb function does.
6. Pool words that point at DATA are declared with a `data` token, not
   `thumb` (`g_021EFA28  0x021EFA28  data  ov170`), and resolve cleanly.

--------------------------------------------------------------------------------
func_021E2154 @ 0x021E2154 - SETTLED, EXACT, 24 bytes.
--------------------------------------------------------------------------------
O33's seven spellings all compiled the last load as `ldr r1,[r3,r1]`; the
image has `ldr r1,[r1,r3]` (Rn = the pool-loaded table base, Rm = i*12).
Every earlier instruction already matched, so only the Rn/Rm roles differed.

The spelling that flips them is a POINTER VARIABLE holding the element's
address -- take the address of the subscript, then dereference the member:

    extern struct Ent { void (*fn)(void *); int a; int b; } g_021EFA28[];
    int func_021E2154(unsigned char *p)
    {
        struct Ent *e = &g_021EFA28[p[0x12]];
        e->fn(p);
        return 10;
    }

with `g_021EFA28  0x021EFA28  data  ov170` on the symbols: line.  A direct
member access `g_021EFA28[i].fn(p)` (and six other spellings) encode the same
load with Rn = the index.  So: when only the two register FIELDS of one load
differ and both operands are already right, hoist the element address into a
pointer variable -- mwccarm then treats it as the base.

Free lessons measured this lane (each cost at least one DIFF first).
--------------------------------------------------------------------------------
1. A callee INSIDE the region that the image calls with `bl` needs BOTH a
   symbols: entry AND the region token, or match.py refuses with "the source
   declares arm, the image says thumb".  That includes callees that are
   already MATCHED (func_021EF660, func_021E8FC0) -- and SDK functions the
   sdk index knows are thumb (`func_0207D63C  0x0207D63C  thumb`).  Nine
   functions this lane first compiled as a bare usage error or ISA conflict
   for exactly this reason.  ARM9 callees the index does NOT know still need
   no entry, and that is the signal that they will cap at MATCH (see above).
2. An unsigned loop counter is not optional when the image has `blo`:
   func_021EF4C0, func_021EF4E4, func_021EF5C4, func_021EAAC4 all compiled
   `blt` from an `int i` and `blo` from `unsigned i`.  Four for four.
3. A pool word that holds a Thumb CODE pointer is passed as a plain integer
   literal of the odd address (0x021E01C5, 0x021E070D, 0x021E0E51) and
   resolves EXACT without any symbols: entry.  Declaring the target also
   works (func_021EA83C compiled EXACT both ways); the literal needs no
   header at all and never risks rule 1's even-address trap.
4. `cmp r0,#1` + `bne` on a callee's result: write the arm the image branches
   TO last, i.e. `if (v == -1) return 0xff; return v + 0x24;` (func_021EF224,
   0xff arm at the branch target) is EXACT, the `if (v != -1)` spelling moves
   the blocks and is out.  Same as rule 2 of the previous lane, confirmed on
   a second shape.
5. A run of same-shape wrappers is worth pattern-generating: six functions
   (func_021E2B48, func_021E3BF8, func_021E498C, func_021E4E6C, func_021E62BC,
   func_021E7258) share one 64-byte body that differs only in the mid call
   (func_021EF670 / func_021EF68C), the state byte and the selector pointer.
   One draft and five copies cost six compiles for 384 bytes.

--------------------------------------------------------------------------------
Lane O46, second half: lessons 6-8 (same packet, same session).
--------------------------------------------------------------------------------
6. When the image compares a CALL RESULT and the operand order is the only
   difference (`cmp r0,r5` in the image, `cmp r5,r0` compiled), give the
   result a LOCAL variable and test it: `unsigned char c = f(...); if (c != a)
   continue;` -- func_021EDB34, 48 bytes, 1 byte out for three spellings until
   then.  A cast in the call expression (`(unsigned char)f(...)`) does not do
   it, and neither does writing the comparison the other way round: mwccarm
   puts the non-lvalue operand first when the result is used directly.
7. When the image re-evaluates its bound at the bottom of the loop, write a
   `while`, not a `for`: func_021DD42C re-calls the length helper in both the
   entry test and the back edge, which a `for (; i < len(); i++)` also gives,
   but the entry test then has to be the SAME test the image has -- with
   `for` mwcc rotated the loop differently in two other functions.
8. Two more same-body sibling pairs landed the same way as the six-member
   wrapper family: func_021EE9C4 == func_021EE7C4 (48 bytes, selector
   0x021E066D, word 0xA168) and func_021EE520/func_021EEF74 share the SDK
   lookup.  Before writing a body, diff its neighbours' listings: a run of
   identical opcode shapes is one source with different constants.
