  * extern void DWCi_ChangeScene(void (*)(...) scene) -- the vendor-DWARF form
    the brief quotes -- does not parse in mwccarm 1.1p1 at all: "')' expected".
    The form every matched sibling in the region uses is void (*scene)()
    (0x021CCEE4, 0x021C1CFC, 0x021C29C4, 0x021C37D0, ...), and that is what builds.
  * DWCi_SceneSetSelectWay / DWCi_SceneSetRakuButton1 were declared extern int and

    relocations are function addresses and the call passes the bare names.

    was the real body error and it is the one that cost the iterations.

THE STRUCTURAL POINT (the actual finding)
  DWCi_GXlInvisible(1, 1) belongs INSIDE `if (Choose == 0)`, sharing the block with
  DWCi_COMMENTlDelete. The image's bne at 0x021CAAF4 targets 0x021CAB08, which is
  PAST the first GXlInvisible -- so a Choose != 0 path skips both calls:

    021CAAF4  bne #0x21cab08      <- jumps over COMMENTlDelete AND GXlInvisible(1,1)
    021CAAF8  bl DWCi_COMMENTlDelete
    021CAAFC  mov r0, #1
    021CAB00  mov r1, r0
    021CAB04  bl DWCi_GXlInvisible
    021CAB08  mov r4, #0          <- branch target, second GXlInvisible below

  With the call inside the guard, the literal 1 appears in mutually exclusive
  blocks, 1.1p1 rematerialises it at each site (mov r0,#1 / mov r1,r0 and
  mov r1,#1) and still pools the 0 into r4 -- exactly the image.

  With the call outside the guard, all three uses of 1 sit in one straight-line
  region, the pooler hoists 1 into r5 as well as 0 into r4, and the prologue
  grows to push {r3, r4, r5, lr} (208 bytes). That single misplaced brace is the
  whole 4-byte difference.

WHY THE FIRST READING OF THE RESIDUE WAS WRONG, and what it cost
  Written outside the guard, the image read as "pools 0 but not 1" -- a shape
  between 1.1p1 (pools both, 208 B) and 2.0/* (pools neither, 200 B), and
  therefore apparently a missing mwccarm build: the object is stamped
  4.0.0.1025, dsi/1.1p1 is build 1024 and dsi/1.2 is build 1026, and no 1.1p2
  (build 1025) is installed. That reasoning was internally consistent and wrong.
  Before blaming the build, sweep the C: the pooler only pools constants whose
  uses are in the same block, so a hoist-looking residue is a statement in the
  wrong place far more often than it is a front-end difference.

  What was measured chasing it, all flat, recorded so it is not repeated:
