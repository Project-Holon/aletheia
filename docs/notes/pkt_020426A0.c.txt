pkt_020426A0 -- the 16bpp/8bpp tile blitters, both 40 minutes in, both DIFF
=======================================================================

Lane 2 of the 513-1024 byte frontier probe.  Two bodies in this packet were
transcribed end to end and driven to a one-cluster residue:

    0x020426A0  584 bytes ARM   ->  146 instructions in both, 45 differ
    0x020428E8  572 bytes ARM   ->  143 instructions in both, ~10 differ

Neither is a size miss and neither is an algorithmic miss: in both cases the
whole body -- the two clip guards, the two register-blocked source layouts,
the func_020422D4 screen-size probe, the func_02040EE0 linear-index call and
the func_02040F84 arbitrary-map call -- reproduces.  What is left is
register allocation inside branch 2 (`flag != 0`) plus three scheduling
swaps.  The two bodies are the same routine at two bit depths (u16 stores
against u8 stores), so whichever is finished first almost certainly finishes
the other.

What both functions are
------------------------

A rectangle blit out of a source tile map into the screen buffer of a
0x2c-byte Surface slot (pixels at +0x00, screen-size code at +0x15 -- the
same two fields src/matched/func_02042E34.c reaches as slot+0x08 / slot+0x1d).
Arguments 5..11 are all on the stack, so the first stack argument sits at
[sp, #0x50] after `push {..., lr}` + `sub sp, sp, #0x28`:

    r0        Surface *s
    r1  x0    destination origin, x          (u8)
    r2  y0    destination origin, y          (u8, homed to [sp+0])
    r3  d     inner count, UNSIGNED          (u32: `bls`/`ble` tells you)
    [0x50] n  row count, UNSIGNED            (u32)
    [0x54]    source base pointer
    [0x58] sx source column origin           (u8, ldrb)
    [0x5c] sy source row origin              (u8, ldrb)
    [0x60]    source row stride              (word)
    [0x64]    source map height / clip bound (word, signed: `cmplt` in b2)
    [0x68] flag  selects the second source layout (u8, ldrb)

920428E8 is the same source with `u8 *pixels`, `u8 *src` and
`src[(sy + i) * stride + sx + q]` instead of the func_02040F84 call in

two `continue`s.

What is ruled out, with the evidence
------------------------------------

1. **The frame is not a frame problem.**  Both originals are
   `push {r4..r8, sb, sl, fp, lr}` + `sub` (0x2c for 0x020426A0, 0x44 for
   0x020428E8) with `sb`/`r9` printed differently by objdump; both of my
   builds reproduce the same 80-byte frame, the same 8 callee-saved
   registers and the same 10-word local area *once the func_02040F84
   argument order was corrected* (see 2).  A wrong frame was the single
   largest source of diff lines before that fix and it is gone.

2. **func_02040F84's argument order is (sx + q, sy + j, stride, lim), not
   (sy + j, sx + q, ...).**  In both originals branch 2 emits
   `and r0, r5, #0xff` (the `(sx + q) & 0xff` value, argument 1) at
   0x02042894 / 0x02042AD8 and loads argument 2 from the sy slot; with the
   two swapped the register allocator spills `syj` differently and the whole
   frame moves 4 bytes.  This one swap is what took 0x020426A0 from
   608 bytes / 44-byte frame to 584 bytes / 40-byte frame with 146
   instructions.  The 0x020426A0 build in this note is exactly this C.

3. **The u8 locals are not optional and not interchangeable.**  `u8` for
   i/j/q/y/yj/syj gives the originals' `blo`/`bhs` (unsigned) compares for
   the loop bounds and the masked clip tests, and `cmplt`/`addge` (signed)
   for the unmasked sums `(sy + j) < lim` and `(y0 + j) < height`.  Every
   `u32` counter spelling produced `blt`/`bge` at 0x020428BC/0x02042A08 and
   a 4-byte-shorter frame.  n and d must be `u32`/unsigned: with `int`
   mwcc emits `ble` where the original has `bls` (`cmp r8, #0` at
   0x02042840 / 0x02042A84).

4. **A named local versus an inline expression for yj/syj changes nothing**
   (scratch/_l2_v7.c: identical 79 diff lines).  Neither does declaring the
   locals at function scope instead of inside the block
   (scratch/_l2_v5.c), nor `volatile` (scratch/_l2_v6.c: the frame *shrinks*
   to 32 bytes, so that lever is wrong).

What the next attempt should try first
-------------------------------------

The residue is one allocator tie-break, not a missing statement: in the
original mwcc keeps the branch-2 inner counter in the *second* free
callee-saved register and reuses the first for the `sx + q` temporary,
while in every spelling above it does the opposite in 0x020426A0 and the
same thing in 0x020428E8.  The cheapest next lever is therefore to make the
two branches share one counter local (declared once, used by both loops)
and to give the branch-2 counter an explicit initialiser statement
(`q = 0;` before the `for (; q < d; q++)`) so the allocator's live range for
it starts where the original's does -- measure only `sub sp` and the
`mov r6, #0` / `mov r5, #0` line, both flip together with the swap.

Lane r5d: the declaration-order axis, swept (both rows still DIFF)
==================================================================

The lane above was worked exactly as it asked, and the answer is that the
lever is real but not sufficient.  Two new measurements:

1. **The shared counter with an explicit `q = 0;` does move the b2 inner
   counter to r6** -- mine now emits `mov r6, #0` (0x02042854, the original
   has it at 0x02042844) instead of `mov r5, #0`, exactly as predicted, and
   the `sub sp` / counter pair still flip together.  On its own it is worth
   nothing: 44 -> 45 differing slots.  Combined with 2 it is worth 13 slots.

2. **The stack slots are driven by the declaration ORDER of the five loop
   locals, and only by it.**  All 120 permutations of `u8 i, y, j, yj, syj`
   were compiled (scratch/r5d/sweep_decl.py) and the slot map read back out
   of the object each time.  The rule the sweep exposes:

   * the last four declared take `[sp,#0x14]`, `[sp,#0x18]`, `[sp,#0x1c]`,
     `[sp,#0x20]` in *reverse* declaration order;
   * `width`/`height` stay pinned at `[sp,#0x24]`/`[sp,#0x25]` in all 120;
   * the branch-1 copy of the `sy` parameter is pinned to `[sp,#0x4]` and
     the branch-2 `syj` is pinned to `[sp,#0x8]` in **all 120** orders --
     no ordering of the five source locals can move either one.

   The original has `sy`-copy at `[sp,#0x8]`, `j` at `[sp,#0x4]` and `syj`
   at `[sp,#0x20]`, so the residue is not reachable from declaration order
   alone; the pinned pair is the thing to explain next, not the order.

Best spelling for 0x020426A0 (scratch/r5d/p5.c = scratch/r5d/v2.c with the
five loop locals moved to function scope in the order)

    u8 j;  u8 syj;  u8 yj;  u8 y;  u8 i;  u8 q;
