HELPER's pointer parameter and the block body becomes byte-exact:

THE 20-BYTE RESIDUE, one decision, nine times plus the prologue.  It is
the OPERAND ORDER OF THE `_fadd` IN THE NEGATIVE ARM, worth 2 bytes at
each of the nine blocks.

  image   0201190A  3f 21    movs r1, #0x3f
          0201190C  09 06    lsls r1, r1, #0x18
          0201190E           blx _fadd            ; r0 = product, r1 = 0.5f
  compile          adds r1, r0, #0                ; product moved r0 -> r1
                   movs r0, #0x3f
                   lsls r0, r0, #0x18
                   blx _fadd                      ; r0 = 0.5f, r1 = product

The image's `_fadd` takes the product FIRST.  1.1p1 canonicalises the
commutative `+` so the product lands in r1 and 0.5f in r0, then pays a
`mov` to get there -- and it does this no matter how the source spells it.
The `_fsub` arm is unaffected and already byte-exact, because `-` is not
commutative and `_fsub(0.5f, product)` pins r0 = 0.5f.
