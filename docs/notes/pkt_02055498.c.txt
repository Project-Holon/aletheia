## 4. Correction to the arm7tdmi idiom

`-proc arm7tdmi` is not what makes this unit's `pop {..., lr}; bx lr` epilogue.
mwccarm 1.2 emits that two-instruction return under `-proc arm946e` as well
(func_02058300 ends `bx lr` and is reproduced byte-for-byte by both
1.1p1+arm7tdmi and 1.2+arm946e, and three of this unit's parked notes go from
DIFF to EXACT under it).  Both of the two visible differences that the idiom
file and the two neighbouring notes attributed to a missing build difference are
explained by the compiler tree alone:

* the two-instruction return: 1.2 does this at arm946e, 1.1p1 needs arm7tdmi;
* 64-bit constant folding: 1.2 materialises, 1.1p1 folds.

The unit is otherwise unchanged: register allocation, scheduling, literal pool
placement and the `stm`-folding that the two notes work around with `volatile`
are the same in both trees.

## 5. The same tree dissolves the blx / pop-lr contradiction

`docs/idioms/a-register-blx-with-a-pop-lr-return-is-a-toolchain-conflict-no-proc-value-emits-both.md`
and `docs/notes/pkt_02053218.c.txt` / `pkt_0205429C.c.txt` (0x02053E1C, 0x0205429C,
0x02054718 - the three packets immediately before this one) conclude that a
function mixing register `blx rN` with a `pop {..., lr}; bx lr` return cannot be
built by this tree at all: "The original unit was therefore built by a compiler
this tree does not have."  That compiler is the 1.2 tree.  A probe TU with three
indirect calls, compiled by tools/mwccarm/mwccarm/1.2/sp2/mwccarm.exe at
-O4,p -proc arm946e, contains both idioms in the same functions:

```
   0: e92d4000  stmfd sp!, {lr}
   4: e24dd004  sub   sp, sp, #4
   8: e1a02000  mov   r2, r0
   c: e1a00001  mov   r0, r1
  10: e12fff32  blx   r2                 <- ARMv5T indirect call
  14: e2800001  add   r0, r0, #1
  18: e28dd004  add   sp, sp, #4
  1c: e8bd4000  ldmfd sp!, {lr}          <- ARMv4T two-instruction return
  20: e12fff1e  bx    lr
```

The five dsi builds and 2.0 reproduce the idiom file exactly (`blx rN` with
`pop {rN, pc}`, or `mov lr, pc; bx rN` with `pop {..., lr}; bx lr`), so nothing

original's 1136 bytes under 1.2/sp2+arm946e (563 different).  The function is
not unreachable after all; its C needs re-tuning under the tree that produces
its idioms, and the same re-check is worth running on the recovered C for
0x0205429C and 0x02054718.
