THE CAP (this is the part to read first)

The function's own literal pool holds four data words, and they have no
witness anywhere in the image:

    0x0206C514  0x020A1974    0x0206C518  0x020A1975
    0x0206C51C  0x020A1976    0x0206C520  0x020A1977

`match.attest(0x020A1974, 'data', 0x0206C0C4, 0x0206C524)` returns None, and
so do the other three.  They are four adjacent BYTES, read as
`ldrb rN, [base, fp, lsl #2]` (0x0206C33C, 0x0206C340, 0x0206C384,
0x0206C3B0), i.e. four one-byte-per-four index tables of the same layout, and
nothing else in the 3.9 MB image names any of the four addresses: no literal
pool anywhere, no string boundary in front of them (0x020A1974 is not the
first byte after a terminator the string class can use), and no matched entry
covers them.  So

  * a body that declares them as symbols in the `symbols:` block gets four
    wildcarded relocation fields and the entry caps at MATCH with every
    concrete byte right, and
  * the only way to EXACT is to spell the addresses as integer constants
    (e.g. `*(const u8 *)(0x020A1974 + (idx << 2))`), which produces a plain
    pool word with no relocation, so the byte comparison still validates the
    address and the honesty rule is not bent -- but it is a deviation from
    the symbols-block convention and has to be said so in the header.

THREE STRUCTURAL FINDINGS, all of them new and all confirmed by the bytes:

1. THE DOUBLED `beq` IS AN INLINED HELPER'S OWN NULL TEST.  At
   0x0206BEE4/0x0206BEE8 the image has `adds ip, lr, #4` immediately followed
   by `beq #0x206bf10`, i.e. it tests `rec + 4` against zero -- which can only
   be false for `rec == -4`.  That is a redundant test the compiler kept.  The
   same shape appears in func_0206C024 as the notorious DOUBLE `beq` on one
   `cmp ip, #0` at +0x34/+0x38, which that note flagged as unexplained.  Both
   are one thing: the source calls a helper

       static u8 *gx_rec_lookup(struct GxRecTbl *t, u32 k)
       { if (t == 0) return 0; if (k >= t->n) return 0; ... }

   with an argument the CALLER has already null-tested (`rec` at +0xd8, or
   `rec + 4`), and mwcc inlines it without folding the second test away.
   Writing the helper as a real `static` does NOT reproduce this -- 2.0/sp2
   leaves it as an out-of-line `bl` (132 bytes, 73 out).  It has to be written
   out by hand at the call site, redundant null test included.

2. THE ZERO ARMS ARE `goto`s TO ONE SHARED `mov r2, #0`, NOT if/else.  With
   if/else (or the conditional operator), 2.0/sp2 if-converts every zero arm to
   a predicated `moveq r1,#0` / `movhs r1,#0` next to its branch, which is 8
   bytes short and leaves the value in the wrong register.  Explicit `goto`s
   to one shared label per lookup -- one for the inner two early returns, one
   for the outer `rec == 0` -- reproduce the image's `b #0x206bf14` /
   `mov r2,#0` / `cmp r2,#0` triple and the `bne #0x206bf28` / `mov r2,#0`
   pair exactly.  This is the `guards-separated-by-statements-share-an-exit-
   only-through-goto` idiom applied twice in one function, and it is worth
   ~40 concrete bytes here.  Going from if/else to gotos took this function
   from 69 concrete bytes out to 33.

3. THE LOOKUP READS ITS TWO SCALARS OFF THE OUTER POINTER, NOT THE INNER ONE.
   The image has `ldrb r0,[lr,#5]` and `ldrh r2,[lr,#0xa]` where `lr` is `rec`
   -- the same addresses as `t->n` and `t->off` on `t = rec + 4`, but off the
   other base.  Spelling them `rec[5]` and `*(u16 *)(rec + 0xa)` while the
   stride arithmetic still runs off `t` is worth 2 more bytes and, more
   usefully, pins which of the two pointers each field belongs to.  The same
   offsets read off `ip` (= rec) at +1 and +6 in func_0206C024 are what proves
   the +4: the two dispatchers are the same table four bytes apart.
