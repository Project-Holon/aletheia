pkt_0205250C - DIFF residues and one wall (lane 5, 0-64 byte band)
==================================================================

The packet carries the arm7tdmi `-proc` hint (layout/proc_hints.txt).  Lane 5
worked four of its rows; none reaches EXACT, and one of them is blocked by a
front-end conflict rather than by the C.

func_020528A8 @ 0x020528A8 (12 bytes) - DIFF, 4 concrete bytes + 1 wildcard
---------------------------------------------------------------------------
Image:

  020528A8  ldr   ip, [pc, #4]        ; = 0x020528D0, the tail-call target
  020528AC  ldr   r1, [pc, #4]        ; = 0x02052F58, the value argument
  020528B0  bx    ip                  ; tail call func_020528D0(a, 0x02052F58)
  020528B4  .word 0x020528D0
  020528B8  .word 0x02052F58

Every spelling tried (`(void *)func_02052F58`, `(u32)func_02052F58`, a
`void (*)(void)` parameter, and the value bound to a local first) compiles to
the same 20 bytes with the two loads in the other order and therefore the pool
words in the other order:

  ldr r1, [pc, #4] / ldr ip, [pc, #4] / bx ip / .word 0x02052F58 / .word 0x020528D0

mwccarm materialises a tail call's *argument* before the branch register; the
original does the opposite.  Separately, the ABS32 to 0x02052F58 stays
wildcarded: 0x02052F58 is a function address used as a value, and its only
mention image wide is this pool word, so only a `matched` entry at 0x02052F58
could attest it -- and 0x02052F58 is itself DIFF (below), so the site cannot
close.  func_020528BC @ 0x020528BC (12 bytes) is the identical thunk one tag
over (tail call func_02052984(a, 0x02052F90)) and fails identically, 4 bytes.

`-proc arm7tdmi` (the packet's own hint) gives the ARMv4T frame but emits
`mov lr, pc; bx r3` for the indirect call; `-proc arm946e` gives `blx r3` but
the `push {r3, lr}` / `pop {r3, pc}` frame instead of the `stmdb`/`sub sp` one.
Neither emits `blx r3` beside an `ldm sp!, {lr}; bx lr` return, which is
docs/idioms/an-armv4t-style-return-and-a-register-blx-name-a-1-2-front-end-not-a-proc-value.md:
the object came from a front end that is not one of the two `-proc` values this
project can select.  Not a C shape and not a flag sweep (the compiler is
pinned), so it is reported as a wall.  func_02052F90 is the same body against
the second installed pointer (0x020A8140).
