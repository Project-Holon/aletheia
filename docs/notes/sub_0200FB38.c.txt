THE VOID-RETURN CHECK
----------------------
docs/idioms/a-void-return-frees-r0-for-the-switch-dispatch-index.md
predicts exactly this shape of near miss (one register letter repeated
throughout, rest identical), but that idiom is specifically about a
switch dispatch index choosing r0 vs r1 depending on whether the callee's
result is live. This function has no switch and no callee call at all;
r0/r1 hold the object pointer and the loaded field value respectively,
and nothing downstream consumes either past the `str`. There is no
plausible non-void return here (the function has no useful value to
return, and the original never sets r0 to anything but the object
pointer, never to a status/bool), so the "return type" lever the idiom
describes does not apply to this function; it is excluded, not just
untried.

WHAT WAS TRIED
--------------
* `u32 *obj = (u32 *)ADDR; if (obj[0x2c/4] == 1) obj[0x2c/4] = 2;`
  -- the shape above, 5 bytes wrong (the swap only).
* Both fields addressed via `*(u32 *)(ADDR + 0x2c)` with no named
  pointer local -- worse, 8 bytes wrong, the compiler drops the `+0x2c`
  displacement into the load/store instead of keeping it as an operand.
* Splitting the load into a separate `u32 v = ...;` before the compare
  -- same 8-byte result as the no-local form.
* `void` return (matches the original, which never touches r0 as a
  result) tried throughout; a `u32`/`int` return type was not tried
  because there is nothing for the function to return: the original's
  last instruction before `bx lr` is the `str`, not a value load into
  r0.

CONCLUSION
----------
Flat at 5 wrong bytes for the closest shape (a direct r0/r1 swap with no
other difference). This reads as compiler register-allocation preference
for the pc-relative load ordering (pointer into r0 vs r1 is decided
before the field access, and this front end picks r1 first when nothing
else has claimed a register yet), not something source-level return-type
or statement-order changes reach. Leave at DIFF; no further C variation
queued.
