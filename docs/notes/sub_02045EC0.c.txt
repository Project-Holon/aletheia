Highest-fan-in open non-runtime address in the image, so worth closing.

WHAT IT IS
----------
Bring one 8-byte rectangle record up to date and hand it to 0x020457B0.
Where the record lives depends on the flag byte at +0x1B of the context:
set means the caller owns a table of them at +0x04 (indexed by the second
parameter, stride 8), clear means the one embedded in the context at
+0x08, which is first refreshed from somewhere else through the pair
0x0204960C / 0x020495F4 (an eight-byte read into +0x08, addressed by
handle +0x14).  The value 0x020457B0 returns is both this function's
return value and the third argument of the tail call to 0x02045CAC.

The embedded record is at +0x08 and the halfword read is at +0x04 inside
it, which is how +0x0C and +0x10 are fixed: `add r0, r5, #8` then
`ldrh r0, [r0, #4]` in one arm and `ldrh r0, [r0, #4]` off the table
element in the other, one shared load after the join.

WHAT THE C IS
-------------
    typedef unsigned char  u8;
    typedef unsigned short u16;
    typedef unsigned int   u32;

    struct Rect { u32 unk_00; u16 unk_04; u16 unk_06; };

    struct Ctx {
        u8          *unk_00;
        u8          *unk_04;
        struct Rect  unk_08;
        u32          unk_10;
        void        *unk_14;
        u16          unk_18;
        u8           unk_1a;
        u8           unk_1b;
    };

    extern void sub_02046180(struct Ctx *c, u32 idx);
    extern void sub_0204960C(void *h, u32 addr);
    extern void sub_020495F4(void *h, u32 len, const void *src);
    extern u32  sub_020457B0(u16 a, u16 b);
    extern void sub_02045CAC(struct Ctx *c, u32 idx, u32 r);

    u32 sub_02045EC0(struct Ctx *c, u32 idx)
    {
        struct Rect *r;
        u32 v;

        sub_02046180(c, idx);

        if (c->unk_1b != 0) {
            r = (struct Rect *)(c->unk_04 + 4 + idx * 8);
        } else {
            sub_0204960C(c->unk_14,
                (c->unk_10 + *(u32 *)(c->unk_00 + c->unk_1a * 4 + 0xc))
                    + (idx * 8 + 4));
            sub_020495F4(c->unk_14, 8, &c->unk_08);
            r = &c->unk_08;
        }

        v = sub_020457B0(r->unk_04, c->unk_18);
        sub_02045CAC(c, idx, v);
        return v;
    }

WHAT IS PINNED
--------------
  The two arms must both assign one `struct Rect *` and the halfword read
  must sit after the join, not be written out in each arm.  The original
  joins at the `ldrh r0, [r0, #4]` that both arms fall into, with the
  then-arm predicated (`ldrne`/`addne`/`addne`) and jumping over the
  else-arm.  That is the ordinary if/else shape with the *set* case
  written first; the polarity is what the predication records.

  The table element address is `c->unk_04 + 4 + idx * 8`, base then the
  constant then the scaled index, which gives `add r0, r0, #4` followed by
  `add r0, r0, r4, lsl #3`.  Spelling it `&((struct Rect *)c->unk_04)[idx]
  .unk_04` emits the two adds the other way round.

  The address handed to 0x0204960C groups as
  `(c->unk_10 + val) + (idx * 8 + 4)`, four terms in two pairs: the
  original builds `add r1, r0, #4` off the shift and `add r2, r3, r2` off
  the two loads, then joins them with `add r1, r2, r1`.  Written flat,
  `c->unk_10 + val + idx * 8 + 4`, it is three chained adds and a
  different register at every step.

  The accumulator order is the other tell: `add r2, r3, r2` puts the
  result in the *val* register, so the source is `c->unk_10 + val`, and
  `add r1, r2, r1` puts it in the *(idx * 8 + 4)* register, so the source
  is `sum + (idx * 8 + 4)`, not the reverse
  (docs/idioms/the-accumulator-of-a-commutative-chain-is-its-second-operand.md).

  The `*(u32 *)(c->unk_00 + c->unk_1a * 4 + 0xc)` form, base plus scaled
  index with the 0xC folded into the load, is what gives
  `add r1, r2, r1, lsl #2` then `ldr r2, [r1, #0xc]`.

WHAT IS LEFT
------------
    ORIGINAL                     COMPILED
    +0030  ldr r3, [r5, #0x10]   lsl r0, r4, #3
    +0034  add r1, r2, r1, lsl#2 add r1, r2, r1, lsl#2
    +0038  ldr r2, [r1, #0xc]    ldr r3, [r5, #0x10]
    +003C  lsl r0, r4, #3        ldr r2, [r1, #0xc]

Same four instructions, same registers, same everything downstream; only
the position of the shift differs.  The original fills the load-use slot
after `ldr r2, [r5]` with the `c->unk_10` load and computes `idx * 8`
after the table read; every spelling here fills that slot with the shift
and pushes both loads down one.

Tried, all still 11 bytes:
  - binding the table read to a local `val` before the call;
  - binding the whole left pair to a local `sum` before the call, so the
    shift cannot be part of the same expression;
  - binding all three loads to locals in the original's issue order
    (`c->unk_1a`, then `c->unk_00`, then `c->unk_10`) as separate
    statements ahead of the expression.
None of them moves the shift.  Source order does not reach this decision:
the scheduler places the shift by itself, so the lever has to be
something that makes `idx * 8` unavailable that early, or the
`c->unk_10` load more urgent.  The next thing to try is a spelling in
which the shift's operand is not simply the second parameter sitting in
a callee-saved register from the prologue.

THE ONE AXIS THAT MOVES IT: -proc
---------------------------------

residue at all.  Same instructions, same registers throughout, only the
issue order changes:
