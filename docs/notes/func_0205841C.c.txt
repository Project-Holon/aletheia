Kept as a record of how the near miss closed, since the earlier reading of
this note sent two later passes down the wrong path.

The function is a two-step 32-bit LCG on the global at 0x02146A8C writing
v->x and v->y, zeroing v->z, then calling 0x0207CCA4. The first pass had
the arithmetic right and was blocked on two things, both now explained:

- The "dead" mov r1, r0 is not dead. 0x0207CCA4 is VEC_Normalize, which
  takes (src, dst); the call is VEC_Normalize(v, v), so r1 really is the
  second argument. The sibling func_02058478 (same shape, three random
  components instead of two plus a zero) has the identical mov r1, r0 and
  confirms it.
- The epilogue bl / pop {r4, lr} / bx lr that -O4,p would not produce is
  not a source-shape question at all: this translation unit is built with
  -proc arm7tdmi, not -proc arm946e, and on ARMv4T mwcc cannot return by
  popping into pc under -interworking. See the idiom file on that.

One further step was needed: with both fixes the two output stores fold
into stmib r0, {r2, lr}, so the VecFx32 components have to be declared
volatile, which is the same stm-blocking trick the first pass had already
identified. Both functions are then byte-exact, and the pair verifies as
one unit over 0x0205841C..0x020584E0.
